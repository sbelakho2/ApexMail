### FINDINGS

### P1 services/mail-server/crates/worker-processors/src/email/processor.rs:3229 — self-hosted SMTP transport sends every message unsigned (no DKIM-Signature)

Ran:
```
python3 smtplib send → Mailpit raw: curl -s http://127.0.0.1:8025/api/v1/message/maJ7fr24HmoTjQ4dKMqvQ5/raw
```
Observed: the delivered message has `Return-Path`, `Received`, MIME headers, tracking and
`X-ApexMail-*` headers but **no `DKIM-Signature`** — for a verified domain whose DKIM key material
was generated by the product and whose public TXT record the fixture marks verified. Queue row
carried `domain_id=59381431-…`; worker `EMAIL_TRANSPORT_TYPE=smtp`, `DKIM_ENABLED=true`.

Expected: in `EMAIL_TRANSPORT_TYPE=smtp` (self-hosted relay) every outbound message of a verified
domain is DKIM-signed with that domain's key — the README's "email authentication via … DKIM" and
the domain readiness query ("must not be handed to the worker unsigned") both promise it.

Why it is a defect: `prepare_email` sets `dkim = Some(...)` only when
`route.is_dedicated()`; without a dedicated IP the planned route is `DeliveryRoute::SesShared`
and the code assumes "shared SES delivery is signed by SES BYODKIM". But this deployment's shared
backend IS the local SMTP relay, not SES (`TransportType::Smtp`), so nothing signs the message.
A self-hosted deployment therefore ships 100% unsigned mail (DMARC fail / spam foldering) while
all dashboards report the domain verified with DKIM enabled. The comment "Shared SES delivery is
signed by SES BYODKIM" is only true when the shared route actually goes to SES.

Suggested fix: key the signing decision off the actual transport backend, not the route: when the
resolved transport is SMTP (`email_transport_is_ses` false / `shared_backend_name() == "smtp"`),
build `smtp_dkim_config_for_domain(domain)` for `SesShared` too; keep the SES BYODKIM skip only
for the SES client. Mirror the same predicate in `resolve_sender_domain_id` / MTA admission if any
of them precompute this.

### P2 services/mail-server/crates/mta/src/servers/submission.rs:1758 + worker-processors/src/email/processor.rs:3155 — Reply-To from an SMTP submission is silently dropped

Ran:
```
MAIL FROM:<alice@mp-28589a20.test> ... DATA with headers:
From: Alice <alice@mp-28589a20.test>
Reply-To: helpdesk@mp-28589a20.test
X-Campaign: summer-test
To: Sink <flow1-hdr@dogfood.test>
```
Observed: `email_queue.headers` = `{"reply-to": "helpdesk@mp-28589a20.test",
"x-campaign": "summer-test"}`, but the delivered Mailpit message has `X-Campaign: summer-test`
and **no `Reply-To` header** at all (full header dump:
`/api/v1/message/VRATyy9cunPokkXiznCs97/headers`).

Expected: RFC 5322 Reply-To supplied by the authenticated sender survives to delivery (it is the
mechanism a support desk relies on; losing it sends replies to the From mailbox).

Why it is a defect: the MTA writes the submission's custom header map with raw lowercased MIME
names (`reply-to`), while the worker's `split_mime_headers` only recognizes `reply_to` /
`reply_to_mailbox` as the structured Reply-To field. The flat map (no `to`/`custom` keys) is
treated as a legacy custom-header map, and the custom loop then refuses `reply-to` because it is
in `PROTECTED_HEADERS`. So the header is dropped on every SMTP-submitted message in both paths
(not recognized as Reply-To, then rejected as custom).

Suggested fix: in `extract_custom_headers` (or `prepare_queue_payload`) map
`reply-to` → `reply_to` for the queue contract; or teach `split_mime_headers` to accept the
hyphenated alias and construct `PreparedEmail.reply_to`. Adding `reply-to` to the MTA's
`QUEUE_PROTECTED_HEADERS` alone would only make the loss explicit, not fix it.

### P3 services/mail-server/crates/worker-processors/src/email/processor.rs:3273 — submitted From display name is dropped

Ran: same flow-1 send with `From: Alice Sender <alice@mp-28589a20.test>`.
Observed: delivered `From: <alice@mp-28589a20.test>` (display name gone); queue `raw_headers`
still contains the original name, but `job.from` is the bare address and `from_name` is only read
from campaign metadata.

Expected: a display name supplied in a submission's From header is preserved (mail clients set it;
the MTA already parses and stores the original header in `raw_headers`).

Why it is a defect: message data supplied by the customer is silently altered on the wire — the
recipient sees a different sender identity than the one the customer sent. Given the reply-to drop
above, this is the second header-fidelity loss in the same pipeline.

Suggested fix: when building the queue payload, extract the origination `From` display name into
the structured header map (`from_name`) and have `prepare_email` prefer it for the MIME From.

### P3 services/mail-server/crates/worker-processors/src/email/transport.rs:789 — SMTP-mode sends never record the relay's acceptance id (`smtp_message_id` stays NULL)

Ran: after each SMTP-mode send, `select smtp_message_id from email_queue where id=…`.
Observed: `smtp_message_id` is empty for every delivered row (fcc8d805-…, 44d3ec27-…,
ad01d74e-…, 34166eb1-…), while `status='sent'`. The SES path records the provider message id;
the SMTP path only has the local `250 … id=<uuid>` for submission, which is not persisted as
`smtp_message_id`.

Expected: the queue records the downstream relay's acceptance identifier so an operator can
correlate a delivered row with the relay/Mailpit log (the column exists for exactly this).

Why it is a defect: terminal bookkeeping for the self-hosted transport loses the only link to the
relay's log; incident triage ("did our relay accept it, and as what?") is impossible from
ApexMail data. Delivery is still correct, so severity is low.

Suggested fix: have the SMTP transport parse the relay's `250` reply text (mail-send exposes the
response) and return it in the `DeliveryReceipt`, then persist it into `smtp_message_id` on the
same accept update.

### P1 services/mail-server/crates/tracking-service/src/routes/click.rs:192 — every tracked link to a host that is not an exact owned-domain match is redirected to the vendor homepage and the click is silently dropped

Ran:
```
send … <a href="https://sub.mp-28589a20.test/landing">  (subdomain of the tenant's own verified domain)
curl -i -A "Mozilla/5.0 Chrome/131.0" http://127.0.0.1:3001/c/ynoxye…
```
Observed: `HTTP/1.1 302 Found  location: https://apexmail.ee` — the recipient clicking the CTA is
sent to ApexMail's marketing homepage, and no click event is written (ClickHouse/Postgres have no
`clicked` row for this message). The same happened for `https://example.com/external?y=2` in
RUN 3.1. Only an exact match of a `domains.name` row (`https://mp-28589a20.test/landing?x=1`)
redirects correctly and is recorded.

Expected: the redirect goes to the URL the customer put in the email. The security goal
(no open redirect) is legitimate, but the product must support the normal cases: a link to
`www.<sending-domain>` / a subdomain, or to the customer's separate marketing site.

Why it is a defect:
- `verify_redirect_domain` authorizes only exact hostnames in `domains` or wildcard patterns in
  `tenant_settings.allowed_redirect_domains`. A grep of the api-server finds NO route/UI that
  writes `allowed_redirect_domains`, so a tenant cannot configure the allowlist through the
  product at all. `www.example.com` vs owned `example.com` is the most common real-world link,
  and it is blocked.
- The blocked-click branch returns the configured fallback (`TRACKING_FALLBACK_URL`, here
  `https://apexmail.ee`) and the click record is skipped (`validated.is_ok()` gate), so the
  customer sees no click in analytics and the recipient lands on the wrong site — silent
  functional loss in the core campaign loop.
- SMTP-submitted transactional mail (Flow 1) has its links rewritten unconditionally, so this
  affects non-campaign mail too, without any opt-out flag on the message.

Suggested fix: (a) treat any hostname under a tenant-owned domain as authorized (suffix match on
the registrable/owned name, not exact equality); (b) expose `allowed_redirect_domains` through the
tenant settings API/console so senders can authorize their link hosts; (c) when a destination is
blocked, still record the click with an explicit `blocked=true` reason instead of dropping it, and
return a 4xx/branded page rather than the vendor homepage so operators can see what happened.
If the product intends to require per-tenant link-domain setup, that must be surfaced before it
silently rewrites links (at minimum: refuse to rewrite/refuse the send for unauthorized hosts).

### P2 services/mail-server/crates/worker-processors/src/email/tracking.rs:271 — clicked events can never be attributed to a link (`link_id` is always empty → "unknown")

Ran:
```
docker exec apexmail-clickhouse clickhouse-client … --query "SELECT event_type, link_id,
  metadata FROM apexmail.events WHERE message_id='7905b92a-…'"
```
Observed: `clicked` row has `link_id=unknown`, `metadata={}` (Postgres `events.link_id` is the
literal string `unknown`; `link_url` is present only there).

Expected: every rewritten link carries its identity (the link row/index) so per-link click
analytics work — otherwise "which CTA did they click?" is unanswerable.

Why it is a defect: `TrackingPayload` (worker) has no `link_id` field, and
`encode_tracking_id` calls `serialize_payload(…, b"" as link_id, …)`. The tracking service then
decodes `link_id=None` and substitutes `"unknown"`; the Redis per-link URL cache
(`links:{tenant}:{message}`) is also skipped because `d.link_id` is `None`. Every click event in
the system is therefore unattributed by design of the encoder, not by missing input.

Suggested fix: give `TrackingPayload` a `link_id`, mint it per anchor (stable index or a hash of
the original href) during `rewrite_links`, and pass it through the v3 envelope; keep the tracking
service's existing `unknown` fallback only for legacy tokens.

### P2 docker-compose.yml:362 + api-server ses_notifications.rs — the deployed stack can neither accept a signed SES notification nor demonstrate authoritative bounce/complaint suppression

Ran:
```
POST /v1/ses/notifications with a realistic SES Bounce SNS envelope → 503 "SNS notifications are not configured"
DSN to bounce server 2525 → bounce_events authoritative=f (no suppression)
ARF to FBL server 2526 → complaint_events authoritative=f (no suppression)
select * from suppressions → no row for the bounced/complained addresses
```
Observed: every ingestion route writes an observation and refuses to suppress. The SES route is
hard-off (`SNS_ALLOWED_TOPIC_ARNS` empty) and un-signable locally; the self-hosted routes require
`VERP_HMAC_SECRET` (bounce) and a registered FBL source (complaint), neither configured.

Expected: the product's headline compliance behavior — a hard bounce or complaint suppresses the
address so it is never mailed again — must be exercisable and verified end to end somewhere. The
sibling code paths are well built and explicitly log the refusal, but "the code claims" the
suppression row, bounce bookkeeping and sales feedback ledger; only the bookkeeping observation
could be observed.

Why it is a defect: the compose stack
ships SNS_ALLOWED_TOPIC_ARNS empty and no VERP/FBL secrets, so the only local path to a
suppression row is unreachable. The brief's own rule — a flow is only dogfooded when a command
and its observed output prove it — cannot be satisfied for suppression/sales-ledger via any
documented local mechanism. This also means a self-hosted deployment that forgets
`VERP_HMAC_SECRET` silently records but never suppresses, and nothing in the stack surfaces that
as a misconfiguration (the domain/campaign dashboards show bounces with no effect).

Suggested fix: ship a dev fixture that exercises the authoritative paths — e.g. compose-provided
`VERP_HMAC_SECRET` + a documented `tools/` script that mints a v2 Return-Path for a real queue row
and injects the DSN, and a pre-registered local FBL source (or an admin-only internal endpoint
that drives the same handler with the SNS validator bypassed under an explicit dev flag). At
minimum, log a startup WARN when the MTA/worker run without VERP secret while bounce processing
is enabled, so "bounces don't suppress" is visible.

Suggested fix: for the `none` resolution arm, populate `observation_detail` from the DSN's
`Final-Recipient`/`Original-Rcpt-To` (sanitized) so the observation is searchable by recipient.

### P1 services/mail-server/crates/worker-processors/src/email/outbound_mta.rs:171 + outbound-mta/src/relay.rs:370 — a worker retry on the dedicated route can never resubmit: rebuilt message bytes break the relay idempotency fingerprint, failing the queue row while the relay still holds the message

Ran: live pipeline (RUN 6.2) — warming `dedicated_ips` fixture, SMTP send to a real-MX domain,
then observe `email_queue` and `outbound_relay_ledger` across worker retries:

```
warming dedicated_ips fixture → SMTP send → relay ledger row (transient source-IP bind failure)
→ worker resubmits on its retry ladder → attempt 3:
status=failed  error="…corrupt ledger row … idempotency conflict: send_unit reused with a
different delivery contract (stored fingerprint d660e5da…, incoming 33a4c7d6…)"
while outbound_relay_ledger = pending, attempt=2, next_attempt_at=+10m
```
Observed: the platform queue row is terminally `failed` at attempt 3 (worker `max_retries=3`)
while the relay's ledger keeps the same message queued on its own 12-attempt / ~24 h ladder. If a
later relay attempt succeeds (the transient condition clears), the message is delivered even
though the customer's message view says failed; conversely the relay will eventually emit a
delivery-expired DSN for a message the platform already failed.

Expected: the documented retry contract — "everything else … stays an UNCLASSIFIED transport
error: the processor retries with backoff, and the MTA ledger's idempotency makes the retry safe
(a stored acceptance is returned, never a second delivery)" — a worker retry of the same send unit
must either adopt the existing ledger row or store an identical message.

Why it is a defect: the relay fingerprints `Sha256(message bytes)` and refuses a differing
contract under the same `send_unit`. The worker rebuilds the message on every attempt:
`build_submission_message` → `build_raw_mime` → mail-builder 0.3.2, which stamps
`headers/date.rs: SystemTime::now()` and a `mime.rs` pseudo-unique boundary at serialization
time; when tracking is on, `prepare_email` also re-injects AES-GCM tokens with a fresh random IV.
So the bytes differ on every retry, the conflict is guaranteed, and the conflict is surfaced as
"corrupt ledger row" (misleading — the row is not corrupt). Any transient relay failure on the
dedicated route therefore becomes a false permanent failure within 3 attempts while the relay
continues to hold and possibly deliver the mail.

Suggested fix: (a) make the submitted bytes stable per send unit — freeze `Date` (set it from the
queue row / first build), the MIME boundary and tracking tokens, and persist the prepared MIME for
reuse on retries; or (b) compute/compare the fingerprint over the logical contract (tenant,
envelope, canonical recipients, subject/body hashes, source IP) rather than full bytes; and
(c) classify the fingerprint conflict as an explicit `AlreadyQueued`/adopt-existing outcome when
the contract is logically identical (and stop calling it "corrupt ledger row" in the surfaced
error).

### P3 services/mail-server/crates/outbound-mta/src/retry.rs:217 (ceiling) + relay.rs:895 — the per-row `outbound_relay_ledger.max_attempts` is inert; the ceiling always uses the process-wide config

Ran: inserted a ledger row with `max_attempts=1` and a transient failure
(`flow6-transient-1` variant). Observed: the row was retried past the first failure —
`attempt=2, next_attempt_at=+600s`; the daemon logs "outbound delivery deferred; retry
scheduled". `RetryPolicy::next_attempt_at` consults `self.config.retry.max_attempts`
(`OUTBOUND_MTA_MAX_ATTEMPTS`, default 12); the row's `max_attempts` column is written on submit
but never read for the ceiling decision.

Expected: a row's own `max_attempts` bounds its retry ladder (the column exists per row and the
claim/record SQL carries it).

Why it is a defect: the stored budget is silently ignored, so an operator or a future per-row
budget cannot cap retries; lowering `OUTBOUND_MTA_MAX_ATTEMPTS` after rows were enqueued also
does not change the rows already created with a different budget, making the effective ceiling
non-deterministic from the data alone. Impact is low while all writers copy the same config value.

Suggested fix: use `row.max_attempts` (falling back to the config value only when the column is
absent) in the ceiling decision, or drop the column in favour of the config and document that.
