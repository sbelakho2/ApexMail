# ApexMail Sub-Module Deep Audit — 2026-09-30

**Method.** The repository (~940K lines of Rust across 56 crates, plus infra, CI, SDKs, apps and docs) was decomposed into 15 sub-modules along domain boundaries. Each sub-module received an independent, strictly read-only deep review: entry points and hot paths read in full, workspace-wide targeted sweeps for defect patterns (`unwrap/expect/panic`, locks across `.await`, `format!`-built SQL, unbounded buffers, cast/rounding bugs, missing authz), and every reported finding verified against the code with `file:line` evidence. No code was modified; no builds, tests or services were run. Severity scale: **P0** = manufactured/false assurance, **P1** = exploitable security flaw, likely production bug, or data loss, **P2** = real robustness/correctness/debt risk, **P3** = improvement.

**Totals: 192 verified findings — 4 × P0, 34 × P1, 74 × P2, 80 × P3.**

## Executive summary

The codebase is far above industry norm in defensive engineering — visible everywhere are prior audit remediations, lease fencing, fail-closed defaults, parameterized SQL, escape-everything UI discipline, integer money, and adversarial test campaigns. The classic vulnerability classes (SQL injection, XSS via template engines, CSRF, path traversal, float money) are genuinely closed on the paths audited.

The residual risk is **not** classic sloppiness. It concentrates into four systemic patterns:

1. **Simulationware** — carefully hardened components that are not actually wired into the serving path, so their guarantees protect nothing while their documentation claims they are live: the HA crate's failover never promotes anything and nothing calls it (SM10); the attachment "sandbox" never detonates and its advertised namespaces/cgroups/seccomp do not exist (SM6); the AI pipeline and email agent with their sanitization layers are dead code while the live `/chat` path sanitizes nothing (SM9); `imap-proto-patched` contains the exact depth-cap fix imap-server needs but no crate compiles it (SM2); the root `compliance/` package and `edge-cases` service are dead drift (SM8, SM10).
2. **False-green assurance** — gates that pass without verifying the thing they claim: ~30% of Rust tests exercise toy reimplementations inside the test files, not production code (SM12); advisory-failed CI stages still bless a SHA with a hardcoded `passedStages` list, and the "hermetic" executor image cannot be built from the repo while silently skipping docker-dependent gates (SM14); two critical blackbox alert families can never fire and Loki has never received a single log (SM13); `AI_SANITIZE_AI_OUTPUT` and the WAF's DMARC/paranoia knobs are config theater (SM9, SM5, SM8).
3. **Silent loss/liveness gaps** — paths where data or money quietly disappears: mid-RCPT abort drops recipients with no DSN (SM1); a transient DB error permanently stalls a sales-sequence enrollment while reporting success (SM7); every statutory ledger posting is skipped on any fresh deployment because nothing provisions the legal entity/periods (SM7); account deletion locks the user out and never purges (SM3); a worker panic kills a processor while health stays green (SM10).
4. **Sibling drift** — equally-careful implementations of the same concern that diverged: SAML lacks the email assurance OIDC enforces (SM8); the GDPR retention job ignores legal holds the sweep honors (SM8); billing admin escapes the control-plane session policy (SM3); all five SDKs ship a webhook vocabulary the server no longer accepts (SM15); three "system tenant" definitions, duplicated harnesses, header copies, and stylesheets drift (SM3, SM11, SM12).

## Fix-first (all P0 + P1, condensed)

**P0 — manufactured tests (SM12):** rewrite or delete `stub_detection_tests.rs`, `property_based_tests.rs`, the concurrency suite's mirrored SQL, and empty `load_isolation.rs` — ~130 of ~427 tests verify toys, so money-path race fixes and rate limiting have no regression protection.

1. **WAF fast-path bypass (SM5-1):** gate vocabulary ⊅ analyzer vocabulary; `<x ontoggle=...>` and `1;TRUNCATE` pass untouched. Make the gate structural or run the tokenizer unconditionally.
2. **SAML JIT account takeover (SM8-2):** SAML ACS applies none of OIDC's email validation/domain checks before linking SSO identities to existing accounts by email.
3. **PHI decryption oracle (SM8-1):** `/compliance/encryption/decrypt-field` is router-mounted, tenant-member-gated, unaudited.
4. **Self-approvable data-access grants (SM8-3):** no admin check, no requester≠approver, no `status='pending'` guard, plaintext token.
5. **IMAP remote stack overflow (SM2-1):** unbounded MIME recursion in BODYSTRUCTURE; one APPEND+FETCH aborts the whole process. The depth cap already exists in the dead `imap-proto-patched` crate.
6. **IMAP CPU DoS + wrong-message FETCH (SM2-2/3):** quadratic `recent_count()`; MSN resolution against a stale view without emitting expunges.
7. **AI `/chat` stored XSS (SM9-1):** raw model output returned and persisted; the sanitizer exists only in dead code and the verifier only catches entity-encoded payloads.
8. **Badge stored-XSS sink (SM11-1):** unknown status strings (event types, suppression reasons) render unescaped on every console table.
9. **Outbound relay recipient loss (SM1-1):** mid-RCPT transport abort leaves un-attempted recipients with no verdict, no retry unit, no DSN.
10. **HA is fiction (SM10-2/3/4):** automatic failover has zero callers; `initiate_failover` promotes nothing but writes `state:"completed"`; STONITH fencing is not enforced on any data plane.
11. **Worker panic = silent outage (SM10-1):** supervision only handles `Err`; heartbeat/health stay green while a panicked processor delivers nothing.
12. **Ledger never posted (SM7-1):** no provisioning of legal entity/fiscal periods and no replay sweep — every invoice/revenue posting is skipped on a fresh deployment.
13. **Sequence dead-end (SM7-2):** transient failure after the `executing` claim permanently drops the send and stalls the enrollment as "Succeeded".
14. **Account deletion lockout (SM3-1):** `pending_deletion` tenants cannot authenticate (no cancellation possible) and nothing ever purges — a broken GDPR promise.
15. **Auth-server loaded footgun (SM4-1):** unrouted `login_post` bypasses MFA entirely; one router line from a live bypass (plus deterministic non-revocable session tokens, no lockout).
16. **SSRF DNS-rebinding (SM6-2):** URL detonator resolves for the guard, then re-resolves for the request; MX resolution applies no private-range filter at all (SM1-3).
17. **Sandbox fiction (SM6-1):** no detonation isolation exists; zip-bomb/nesting config is dead; nested archive content is never inspected.
18. **Observability dead legs (SM13-1/2/3):** `prober: smtp` doesn't exist in the pinned blackbox_exporter (permanent critical alert train, TLS-expiry monitoring inert); outbound-mta is unscraped; Loki 401s every push.
19. **0.0.0.0 datastore republication (SM13-4):** `.env.example`'s bare-port convention turns the dev override's port vars into all-interfaces bindings for Postgres/Redis/ClickHouse.
20. **CI hermeticity broken (SM14-1/2):** executor image unbuildable as committed (COPYs two nonexistent files); required WCAG gates depend on a gitignored `node_modules` no CI path provisions.
21. **SDK webhook vocabulary (SM15-1):** all five SDKs ship pre-2026-09-08 event names; Python/Java client gates hard-block every server-valid event.

## Cross-cutting improvement roadmap

1. **Adopt a "wired or deleted" rule.** Every dead-but-documented component (HA automatic failover, sandbox detonation, AiPipeline/EmailAnswerer, imap-proto-patched, edge-cases service, root compliance/, smtp-auth-proxy, FairQueueScheduler) either gets integrated with its latent flaws fixed or is removed. Dead hardened code is the repo's dominant liability pattern.
2. **End false-green assurance.** Rewrite the four self-referential test suites against production crates; derive CI `passedStages` from manifest statuses; make docker-absent and advisory-fail loud; build the executor image from the repo and pin by digest; verify alert rules have firing data sources (dead-man switches); make perf tests `black_box` + baseline-gated; add cargo-fuzz targets for the protocol parsers.
3. **Close the silent-loss paths.** Mid-RCPT recipient accounting, sequence-step lease/reaper, ledger auto-provisioning + sweeps, account-deletion cancellation + purge sweeper, panic-aware worker supervision, analytics cap-eviction → forced flush.
4. **Unify drifted siblings.** One SSO identity-trust bar (port OIDC email assurance to SAML); one legal-hold-aware deletion predicate; one platform-admin gate (session policy + slug-aware system tenancy + audit attribution); one webhook-event contract JSON consumed by server and all SDKs; one pagination helper; one CSP/header source; one test-harness crate.
5. **Bound everything keyed by attacker input.** DKIM key index, anonymous cost buckets, blocklist, explorer API-key rows, SSO staging rows, trust-portal inserts, LogAggregator maps — mirror the hard-cap + LRU discipline the repo already applies elsewhere.
6. **Root hygiene (minor).** Untracked local clutter (`dump.rdb` ×2, `test_output.txt`, `secrets/`, `.env`) — fine in git but should be cleaned from the working tree; tracked at root: two design PNGs and two working notes (`fixes.md`, `marketing_audit_v2.md`) belong in docs or out of the repo.

## SM1 — Mail Delivery Core (mta, outbound-mta, mail-proto, mail-common, mailstore-core, queue-provider, dns-resolver)

**Verdict:** This sub-module is unusually well-hardened — visibly the product of many prior audit passes (commented "F-xx/O-xx" fixes, adversarial test campaigns, lease fencing, SMTP-smuggling/CRLF defenses, bounded readers everywhere). The inbound/submission SMTP servers, util line-reader, queue-provider, dns-resolver, and mailstore storage layer are close to production-grade with no P0s found. The real defects cluster in the **outbound relay**: one genuine silent-recipient-loss path on a mid-RCPT abort, a lease-fencing gap that permits duplicate delivery, and an unfiltered MX-address SSRF surface. Everything else is P2/P3 robustness and drift.

**Findings:**

1. **[P1] Silent recipient loss when RCPT aborts mid-loop after another recipient accepted** — `outbound-mta/src/relay.rs:1077-1084, 1119-1122, 1162-1173` vs `relay.rs:746-779`. On a transport error during `RCPT TO` (timeout/reset) the loop sets `rcpt_aborted = true; break;` — recipients *after* the failure point are never attempted and land in no list. The guard `if rcpt_aborted && accepted.is_empty() { continue; }` only retreats when *nothing* was accepted; otherwise the code proceeds to DATA, and on the post-DATA 250 returns `results = accepted + rejected + deferred` (line 1164-1166) — the un-attempted recipients are absent. Back in `deliver()`, the unaccounted-recipient sweep (lines 753-779) only iterates domains in `unresolved`, and this domain was *settled*, so they get **no verdict, no deferred-retry unit (`deferred_retry`), and no DSN** while the unit is pinned `accepted`. Impact: silent per-recipient mail loss on any connection blip during RCPT of a multi-recipient send. Fix: when `rcpt_aborted` and proceeding to DATA, classify every `recipients` entry not present in accepted/rejected/deferred as `Deferred` so it joins the follow-up unit.

2. **[P2] Ledger transitions are fenced only on `state='delivering'`, not on attempt/lease owner — duplicate delivery possible** — `outbound-mta/src/ledger.rs:535-555, 557-619, 621-639` (`record_retry`/`record_accepted`/`record_permanent` all use `WHERE send_unit = $1 AND state = 'delivering'`) vs `claim_due` at `ledger.rs:506-533` which re-claims expired leases (`state = 'delivering' AND lease_until < $1`, `attempt = attempt + 1`). A single `attempt_target` pass can legitimately exceed the 15-minute default lease (per address: 30 s connect + 60 s EHLO/STARTTLS/MAIL + N×60 s RCPT + 600 s DATA — two slow addresses already exceed it), so a concurrent daemon sweep re-claims the row and a second live delivery runs. Both SMTP sessions deliver; the first `record_accepted` lands, the second silently no-ops (`rows_affected == 0` is not treated as an error), and a stale worker's `record_retry` can reset a successor's in-flight row and corrupt its attempt counter. Contrast `queue-provider/src/provider.rs:376-395`, which correctly fences on `lease_token`. Fix: add `AND attempt = $n` (or a lease token) to every terminal/retry UPDATE and treat 0 rows as a lost-lease event.

3. **[P2] MX address resolution applies no private/loopback-range filter — internal-network SSRF surface** — `outbound-mta/src/mx.rs:248-253`: loopback, RFC1918, and link-local (incl. `169.254.169.254`) addresses are explicitly usable — the test at `mx.rs:432` asserts `127.0.0.1` is "good". Recipient domains come from tenant/user-controlled input, so a tenant can publish `MX → host` resolving to internal IPs and drive the relay into opening SMTP sessions (with attacker-influenced EHLO/MAIL content) against internal Postgres/Redis/admin services. `mail-common/src/ssrf.rs:34-77` implements exactly the right predicate (including IPv4-mapped v6) but is not applied here. Fix: filter resolved MX addresses through `mail_common::ssrf::is_private_or_reserved_ip` (config-gated escape hatch for loopback test setups).

4. **[P2] DNS cache DKIM key-index grows without bound on attacker-controlled input** — `dns-resolver/src/cache.rs:199-203` (`track_dkim_key`) called from both `insert_with_ttl` (line 137) and `insert_negative` (line 156); entries leave moka via TTL expiry or capacity eviction but are removed from the `dkim_keys: RwLock<HashSet<String>>` only by explicit `invalidate`/`clear` (`cache.rs:206-210`). The tracked keys are `dkim:{selector}._domainkey.{domain}`, and selector/domain are attacker-controlled via the `DKIM-Signature: s=/d=` headers of inbound mail — an attacker sending mail with unique selector/domain pairs grows the process's memory without bound (moka stays capped; the index does not). Fix: cap the set size, or store the index inside a second bounded moka cache keyed the same way so it evicts in lockstep.

5. **[P3] `allow_soft_fail=false → Quarantine` DMARC arm is unreachable (dead operator knob)** — `mta/src/auth/email_authentication.rs:601-612` gates on `results.dmarc.result == DmarcVerdict::Fail` then matches `DmarcPolicy::None => Quarantine`, but `evaluate_dmarc` (`email_authentication.rs:884-891`) maps a `p=none` record with no aligned pass to `DmarcVerdict::None`, never `Fail`+`None`. Operators setting `allow_soft_fail=false` expecting quarantine of unaligned `p=none` mail get plain accept. Either emit `Fail` with the record's policy for p=none, or delete the knob.

6. **[P3] Peer-advertised `SIZE` is parsed but never enforced before DATA** — `outbound-mta/src/smtp.rs:456-459` parses `SIZE`, but `relay.rs:974-1005` consults only `capabilities.starttls`. A peer whose advertised SIZE is below `message.len()` still receives the full body (up to `max_message_bytes` = 50 MB default) only to answer 552 after end-of-DATA — wasted bandwidth and connect time. RFC 1870 expects the client to skip the target. Fix: in `attempt_target`, if `capabilities.size` is `Some(n)` and `n < message.len()`, record a transient failure and take the next MX.

7. **[P3] Encryption doc/implementation drift: "HKDF-SHA256" is actually unsalted SHA-256** — `mailstore-core/src/encryption.rs:5-9` documents "HKDF-SHA256 derivation with a per-version `info` string", but `derive_encryption_key` (`encryption.rs:185-192`) is one `SHA256("apexmail-mailstore-encryption" || version || master_key)`. Safe for a uniformly random ≥32-byte key (which `main.rs:218` enforces), but the comment misleads anyone tempted to feed a low-entropy passphrase. Fix the doc or use a real HKDF.

8. **[P3] Redis lockout counter: INCR and EXPIRE are not atomic** — `mta/src/auth/lockout.rs:80-90`: `INCR` then a separate `EXPIRE`; if the process dies or EXPIRE errors between the two, the counter persists forever without TTL and the (IP, account) pair trends toward a permanent lockout. Use `SET ... EX` on first increment (or a Lua/`INCR`+`EXPIRE NX` equivalent).

9. **[P3] HMAC dead-letter path: comment drift and unfenced UPDATE** — `queue-provider/src/provider.rs:278` says "Revert to pending so it can be inspected via dead letter" while the SQL at 280-291 sets `status = 'dead_letter'` directly, and that UPDATE (unlike `complete`/`fail`/`dead_letter`) has no `lease_token` fence. It is executed by the current claim owner so it's safe today, but it's inconsistent with the crate's own fencing discipline pinned by the test at `provider.rs:1163-1181`.

10. **[P3] `FairQueueScheduler::schedule` silently discards excess jobs** — `queue-provider/src/scheduler.rs:44-75`: the API consumes `Vec<Job>` and returns only the selected subset; jobs over the per-tenant cap or batch size are dropped with no way for the caller to release them back to pending (the doc at lines 18-21 says the caller must). Unwired/dead code today (documented), but a trap for the first production adopter.

11. **[P3] Pre-admission 421 writes have no timeout** — `mta/src/servers/inbound.rs:475-481` / `write_line_tcp` at `2238-2250` loops on `writable().await`/`try_write` indefinitely; a peer that connects, triggers the per-IP cap, and never reads can pin the refusal task (same shape in `submission.rs:267-272`). Small writes usually fit the socket buffer, so impact is limited, but a bounded `timeout()` around the refusal write would close it.

**Top 5 improvements:**
1. Fix the relay's mid-RCPT-abort recipient accounting (finding 1) — it is the only path in the module that can silently lose accepted-for-delivery mail.
2. Add attempt/lease-token fencing to `outbound_relay_ledger` terminal transitions and raise the lease above the worst-case delivery duration (finding 2).
3. Apply the existing `mail_common::ssrf` IP filter to resolved MX addresses in `DnsMxResolver` (finding 3).
4. Bound the dns-resolver `dkim_keys` index so it evicts with the cache (finding 4).
5. Decide and implement the DMARC `p=none` + `allow_soft_fail=false` semantics and enforce peer `SIZE` before DATA (findings 5-6) — both are cheap, spec-aligned wins for the outbound path.

## SM2 — Access Protocols, Tracking & Rendering (imap-server, imap-proto-patched, tracking-service, template-renderer, pdf-renderer)

**Verdict:** This sub-module is a tale of two codebases. tracking-service, template-renderer and pdf-renderer are unusually hardened — adversarial test suites, panic-shape guards (F37), XSS/open-redirect/CSP controls, sandbox budgets, embedded template validation, bounded pools everywhere; their remaining defects are a reachable panic in the click/pixel logging paths and a silent u16 truncation in the token codec. imap-server is the weak flank: a monolithic 9.4k-line main.rs that re-implements MIME structure parsing with **unbounded recursion** (remote stack-overflow crash via one APPEND + FETCH BODYSTRUCTURE), a **quadratic `\Recent` recount** that turns NOOP polling into a CPU furnace on unseen-heavy mailboxes, and a FETCH handler that resolves message-sequence numbers against a freshly re-listed view **without notifying the client of expunges** — silently returning the wrong messages. Ironically, the vendored `imap-proto-patched` crate contains exactly the depth-cap fix imap-server needs, but it is dead code: not a workspace member, with zero dependents.

**Findings:**

1. **[P1] Unbounded MIME recursion in BODYSTRUCTURE rendering — remote stack overflow (process abort)** — `services/mail-server/crates/imap-server/src/main.rs:2641-2644` and `:2670-2671`. `format_structure_region` recurses once per nesting level with no depth cap. A MIME blob of nested `multipart/mixed` parts costs ~40 bytes per level; the literal reader accepts 32 MiB literals (`MAX_LITERAL_SIZE`, main.rs:1102), so one authenticated APPEND of `Content-Type: multipart/mixed; boundary="a"` nested ~500k deep, followed by `FETCH 1 (BODYSTRUCTURE)` (or the `FULL` macro, which expands to `BodyStructure{extended:true}` at main.rs:2229), drives ~500k stack frames → stack-overflow SIGSEGV. `panic="unwind"` in the release profile (root Cargo.toml:240) does NOT help — stack guard violation aborts the process. Whole-server crash from one tenant. Fix: pass a `depth` parameter and bail at ~64 levels (the exact pattern already shipped, unused, in `imap-proto-patched/src/body_structure.rs:258` `MAX_BODYSTRUCTURE_DEPTH: usize = 64`); also cap `extract_body_part`'s descent, which burns O(depth × body) memcpy on the same input (main.rs:2440-2482).

2. **[P1] `recent_count()` is quadratic — CPU DoS via NOOP/SELECT polling** — `services/mail-server/crates/imap-server/src/main.rs:138-144`. `uid_map` is a sorted `Vec<u64>` (up to 100k entries); `contains` is a linear slice scan. On SELECT, every unseen message joins `recent_uids` (main.rs:2020-2024), so a mailbox with 100k unseen messages yields 100k × ~50k ≈ 5×10⁹ comparisons per call. `recent_count()` runs on SELECT (main.rs:2037), every changed-mailbox NOOP (main.rs:4953), EXPUNGE (4869), MOVE (3942) and APPEND (4783) — seconds of full-core CPU per poll, multiplied across the 500-connection cap. Fix: `uid_map.binary_search(u).is_ok()` (it is already sorted), or keep a `HashSet<u64>` mirror of the view.

3. **[P1] FETCH resolves sequence numbers against a re-listed view without emitting the view diff — client desync, wrong message returned** — `services/mail-server/crates/imap-server/src/main.rs:2719-2736, 2826-2827`. Unlike STORE/COPY/MOVE/EXPUNGE/SEARCH, which call `refresh_session_view` and emit the `view_diff` (untagged EXPUNGEs + EXISTS) BEFORE their own responses (main.rs:3335-3341, 3778-3781), `handle_fetch` re-lists silently: if another session expunged message #3, a client's `FETCH 5 FLAGS` resolves against the NEW map — returning what the client knows as message #6, numbered `* 5 FETCH`, with no EXPUNGE ever sent and `session.uid_map` left stale (so EXISTS still lies too). MSN-based FETCH silently addresses the wrong messages. Fix: resolve against `session.uid_map` (the view the client holds), or run `refresh_session_view` first and write its diff before any FETCH response.

4. **[P2] Remote panic in click/pixel handlers: byte-slice logging of multibyte tracking IDs** — `services/mail-server/crates/tracking-service/src/routes/click.rs:136-139` and `routes/pixel.rs:117-120`. `tracking_id` is an axum `Path<String>` (percent-decoded UTF-8). If byte 20 splits a multibyte char (e.g. 19 ASCII bytes + `é`), the slice panics: "byte index 20 is not a char boundary". This is the exact bug class the unsubscribe handlers explicitly fixed — `routes/unsubscribe.rs:52-56`: "after this check every later `&token[..n]` slice is on an ASCII string where byte indices are char boundaries" — but the F37 `is_valid_token_shape` guard was never applied to click/pixel. `warn!` is enabled at the default `tracking_service=info` filter (main.rs:240), so the field expression evaluates on every invalid token; `GET /c/aaaaaaaaaaaaaaaaaaaéxxxxx` (unauthenticated, length 10–4096, decode fails) kills the connection task per request (profile is `panic="unwind"`, so the process survives but the request 500s/resets, and pixel requests never get their GIF). Same latent pattern at `processor.rs:778` (`raw = &entry[..entry.len().min(100)]` — lower risk, internally-produced envelopes). Fix: hoist `is_valid_token_shape` (or a char-boundary-safe `floor_char_boundary`/`char_indices().take_while` prefix) into a shared helper used by click.rs:69, click.rs:137, pixel.rs:118, processor.rs:778.

5. **[P2] `imap-proto-patched` is dead vendored code — 2.5k lines of hardened parser nobody compiles** — `services/mail-server/Cargo.toml:225` (`imap-proto = { path = "crates/imap-proto-patched" }`). The crate is declared only in `[workspace.dependencies]`; it is absent from the `members` list (Cargo.toml lines 3-59) and no crate's `[dependencies]` references `imap-proto` (repo-wide grep for `imap_proto::` returns nothing outside the crate itself). Its patches — `MAX_BODYSTRUCTURE_DEPTH = 64` paren-depth cap (body_structure.rs:258-292), the NIL-INTERNALDATE `unwrap()` fix (rfc3501.rs:376-382), the multibyte `resp_text` slicing fix (rfc3501.rs:459-479) — are exactly the protections imap-server's hand-rolled MIME/response code lacks (findings 1, 6). Dead vendored security fixes are worse than none: they create false confidence. Fix: either wire imap-server's BODYSTRUCTURE/BODY[] path onto this parser (preferred — it kills finding 1 structurally) or delete the crate and the workspace entry.

6. **[P3] Lossy UTF-8 conversion corrupts binary header octets in FETCH responses** — `services/mail-server/crates/imap-server/src/main.rs:2283` (`filter_header_fields`), `:2339` (`raw_header_value`), `:2405` (`split_multipart`). RFC 3501 §4.3 literals carry raw octets; `BODY[HEADER.FIELDS (...)]` on a message with 8-bit (e.g. ISO-8859-1 or raw UTF-16) header bytes returns U+FFFD replacement characters instead of the original bytes — silent data corruption for non-UTF-8 mail (still common in the wild), and boundary matching in `split_multipart` can theoretically diverge on lossy-converted bytes. Fix: operate on `&[u8]` and match field names/boundaries as ASCII-insensitive byte comparisons.

7. **[P3] FETCH/UID argument plumbing drops literal tokens** — `services/mail-server/crates/imap-server/src/main.rs:3097` and `:1476`. `handle_fetch` doesn't receive `literals` at all, so its sequence token is resolved against an empty literal list; `handle_uid_command` "resolves" the entire sub-args string, which only works when the whole string is a single marker — any literal embedded mid-args (e.g. `UID SEARCH HEADER {7}\r\nSubject x`, re-resolved per-token later and thus working by accident) leaks the raw `\x01LITk\x01` marker into item parsing. Consequence: RFC-legal literal usages surface as confusing BADs. Fix: thread `literals` into `parse_fetch_args` and remove the whole-string `resolve_token` in `handle_uid_command` (resolve per-token inside each sub-handler, as SEARCH/COPY already do).

8. **[P3] Sequence-set and STORE-op syntax errors silently accepted** — `services/mail-server/crates/imap-server/src/main.rs:404-411` and `:3424-3429`. `FETCH 0 FLAGS` returns OK, and any garbage STORE operation word is silently treated as FLAGS-set instead of BAD. Low impact, but it masks client bugs and violates §6.4.5/§9. Fix: reject `0` in `parse_sequence_set`; require the op base to be exactly `FLAGS` (case-insensitive) after stripping `+`/`-`/`.SILENT`.

9. **[P3] Tracking token serializer silently truncates fields >64 KiB** — `services/mail-server/crates/tracking-service/src/codec.rs:587-604` (`serialize_tracking_data`) and `:454-458` (`serialize_unsub_payload_v2`). `encode` is public surface shared with worker-processors; an `original_url` (or recipient/message id) longer than 65 535 bytes truncates the length prefix, producing a structurally corrupt token that fails `decode` — a click link that dead-ends at the fallback with no error at mint time. Fix: return an error from `encode` when any field exceeds `u16::MAX` (the click route already enforces `max_redirect_url_len` at click time — enforce it at mint time too).

10. **[P3] LIST/LSUB does an O(mailboxes) subscription-set clone per row under a global lock** — `services/mail-server/crates/imap-server/src/main.rs:4378` calling `:207-210` / `:4463-4468`. `is_subscribed` → `subscribed_mailboxes` clones the account's whole `HashSet` while holding the process-global `SUBSCRIPTIONS` mutex — once per listed mailbox. A tenant with 10k mailboxes does 10k lock acquisitions and 10k clones per LIST, serialized across all connections sharing the table. Fix: snapshot the set once per LIST/LSUB call and test membership locally (`eq_ignore_ascii_case`).

**Top 5 improvements (ordered):**
1. **Cap MIME nesting depth in `format_structure_region`/`extract_body_part`** (finding 1) — this is the only finding that kills the whole process; the cap already exists in the dead vendored crate, port it (~10 lines).
2. **Fix FETCH view semantics** (finding 3): resolve MSNs against `session.uid_map` or emit the `refresh_session_view` diff before FETCH responses, matching STORE/COPY/MOVE — message mis-targeting is a correctness/integrity bug users will actually observe.
3. **De-quadraticize `recent_count`** (finding 2): binary search or a HashSet mirror; then re-check the other O(n×m) hot paths (`expunge_seqs_descending` is fine; `is_subscribed` is not).
4. **Share the F37 token-shape guard across tracking routes** (finding 4) — one helper, four call sites; also add the multibyte-prefix case to `routes/pixel/adversarial_tests.rs` and `routes/click/adversarial_tests.rs`, which currently miss it.
5. **Resolve the `imap-proto-patched` limbo** (finding 5): either make imap-server consume it for response/MIME parsing (eliminating finding 1's bug class at the root) or delete crate + workspace entry — and split imap-server's `main.rs` into modules (session, commands, mime, tls) so the next auditor doesn't have to read 9.4k lines to find these.

## SM3 — API Server (api-server)

**Verdict:** This is an unusually hardened crate — you can read at least three generations of internal security audits in the comments (F1–F65, "audit D", "P1-1", "SA2-009"), and the classic web-API vuln classes are genuinely closed: every object handler I sampled scopes SQL by `tenant_id` (domains.rs:470-478, webhooks.rs:445-455, messages.rs:2481+, billing invoices, SSR detail pages via `data::load_*`), SQL is parameterized everywhere (`format!` interpolates only static column lists / i64 limits — scim.rs:564-603, system_sender.rs:83-96, self_hosted_bounces.rs:568-580), impersonation requires system-tenant + wildcard + single-use signed token + fail-closed audit (impersonate.rs:54-166), the admin proxy does resolve-then-pin SSRF defense with redirect refusal (proxy.rs:194-303), CSRF is double-submit + HMAC + constant-time on both JSON and form surfaces (middleware/auth.rs:177-197, web.rs:580-591), login has PoW captcha + dual rate limits + anti-enumeration + ATO policy (auth.rs:2315-2443), and a compile-time test even guards that every admin route file calls the wildcard scope check (admin/mod.rs:141-159). Non-test `unwrap()/expect()` on reachable paths is essentially zero. What remains are drift and lifecycle gaps between equally careful subsystems, not classic holes: a self-service account deletion that is an immediate irreversible lockout with a fictional 30-day recovery, billing reads with no scope gate, `/v1/billing/admin/*` escaping the control-plane session hardening its sibling `/v1/admin/*` routes carry, an anonymous endpoint that churns a wildcard API-key row per request, and a handful of correctness/consistency defects (shadowed headers on refresh, unattributed money-minting audit row, offset masquerading as cursor, two diverging "system tenant" definitions).

**Findings:**

1. **[P1] Account deletion is a one-way lockout with a fictional 30-day recovery and no purge** — `src/routes/account.rs:164-226`. The handler sets `status = 'pending_deletion'` (line 171) and disables every user (line 186), then responds "Account deletion scheduled. You have 30 days to cancel this request." (lines 218-225). But: (a) the centralized tenant gate `tenant_status_permits_auth` admits only `"active"` (`src/middleware/auth.rs:1019-1021`) and the recovery allowlist covers only `"suspended"` (`auth.rs:1075`), so a `pending_deletion` tenant cannot authenticate to anything — including any cancellation route; (b) `rg 'pending_deletion'` across the whole `services/mail-server` workspace matches only this file — there is no cancellation endpoint and no sweeper/job that ever executes the deletion. Impact: the user is irreversibly locked out the moment they delete (cannot cancel, cannot even open a support session under the same tenant), and their data is retained indefinitely despite an erasure request — a GDPR-erasure promise the platform does not keep. Fix: add a narrow recovery allowlist + `POST /v1/account/deletion/cancel`, plus a retention job that actually purges/anonymizes after 30 days (reuse the existing admin GDPR machinery), or change the contract to immediate anonymization.

2. **[P2] Billing read endpoints require no scope — least-privilege credentials can read invoices** — `src/routes/billing.rs:3375` (`list_invoices`), `3403` (`get_invoice`), `3418` (`get_invoice_pdf_html`), `3433` (`get_invoice_xml`), `3329` (`get_subscription`), `2739` (`get_usage`), `3485` (`check_quota`). Every other read surface enforces its scope (`messages.rs:2463` `messages:read`, `webhooks.rs:371` `webhooks:read`, `analytics.rs:254` `analytics:read`), but these handlers go straight from `AuthUser` to `auth.tenant_id` queries — a `viewer`-role session (whose scopes are purely read-side lists, `auth.rs:770-782`) or an API key minted with a single narrow scope can read full invoice line items, subscription state, and spend. Impact: intra-tenant privilege confusion; finance data exposed to credentials that were deliberately scoped away from it. Fix: require a registered billing read scope on these handlers (a `billing:read` string already exists in the crate's own test fixtures, `analytics.rs:1558`).

3. **[P2] `/v1/billing/admin/*` escapes the control-plane session hardening applied to `/v1/admin/*`** — `src/app.rs:530-614` layers `require_cp_auth` (MFA'd CP session, idle + absolute timeouts, per-request recheck, `cp_access_log`) plus `require_system_tenant_middleware` only on the `/v1/admin` router; the financially destructive billing admin routes (wallet credits, plan override, forced subscription status, invoice creation — `billing.rs:84-99`) are mounted on the plain `authenticated` router and guarded solely by `has_admin_access` (`billing.rs:1363-1401`), a JWT tenant-id + scope string check. A stolen system-tenant session JWT — whose lifetime is a sliding window, since `refresh_token` (`auth.rs:4237-4382`) mints a fresh `iat` and the 7-day absolute check (`middleware/auth.rs:1294-1302`) keys off `iat` — can mint wallet credits and override plans without any of the CP ceremony the app.rs comment block (lines 599-610) calls CRITICAL. Impact: the money surface has materially weaker session policy than read-only CP analytics. Fix: nest the billing admin router under the `admin` stack (or layer `cp_auth` on it), keeping an explicit machine-credential carve-out if required.

4. **[P2] Explorer sandbox inserts a fresh wildcard-scope API key row on every anonymous request** — `src/routes/explorer.rs:159-208`. Each public `/explorer/exec` (rate-limited 8/min/IP) runs `sandbox()`, which unconditionally INSERTs a new `api_keys` row with `scopes ["*"]` (lines 190-199) and revokes the previous key (180-187). Nothing ever deletes superseded rows; the per-tenant key ceiling that `mint_api_key` enforces (`auth.rs:3857-3866`, `FOR UPDATE` + COUNT) is bypassed by this raw insert. At the public rate limit that is ~11.5K rows/day/IP of unbounded table growth driven by anonymous traffic, and the shared-key rotation means visitor B's provision revokes visitor A's in-flight key mid-dispatch (sporadic 401s under concurrency). Fix: cache the provisioned key per-process/Redis (provision once, reuse — the raw key never leaves the server), delete the superseded row on rotation, and cap the sandbox tenant's key count.

5. **[P2] The wallet-credit audit row is unattributed** — `src/routes/billing.rs:3874-3890`: `insert_audit_log(&state.db, Some(&tenant_id), None, "wallet.credit", ...)` passes `None` as the actor, while every sibling admin surface attributes the operator (`admin_apply_plan_override` writes `actor_id` from `admin_actor_id(&auth)` — defined at `billing.rs:1403-1405`, used at `3956/3996`; impersonation `impersonate.rs:246-256`; proxy `proxy.rs:59-71`). The single endpoint that mints balance leaves no record of which operator did it. Fix: pass `auth.user_id.as_deref()` in the third argument.

6. **[P3] `refresh_token` records `user_agent` from the wrong `HeaderMap`** — `src/routes/auth.rs:4364` builds `let mut headers = HeaderMap::new()` (shadowing the request `headers` parameter), then `auth.rs:4379-4381` reads `headers.get("user-agent")` from that response-only map — always `None`. Every refreshed session's accountability row (`record_issued_session`, line 4382) loses device attribution, degrading the session-inventory/ATO trail the login path populates. Fix: capture the request's user-agent into a local before the shadowing binding.

7. **[P3] Email-MFA code comparison is not constant-time** — `src/routes/auth.rs:2532`: `Some(code) if code == mfa_code` uses plain `String` equality for the 6-digit emailed code, while the crate's own standard is `apexmail_lib::timing_safe_compare` (CSRF at `middleware/auth.rs:192`, form CSRF at `web.rs:590-594`). Lockout + attempt caps make practical exploitation marginal, but it is drift from the crate's own bar on an authentication comparison. Fix: swap in `timing_safe_compare`.

8. **[P3] `cursor` is a raw offset on seven list endpoints, contradicting the keyset contract** — e.g. `src/routes/suppressions.rs:63` (`pub cursor: Option<i64>`) and `:226` (`params.cursor.unwrap_or(params.offset).clamp(0, 100_000)`); the same `cursor.unwrap_or(params.offset)` pattern in `webhooks.rs:373`, `domains.rs:448`, `templates.rs`, `support.rs`, `events.rs`, and `auth.rs` (list_api_keys). The crate documents an opaque keyset cursor (`src/routes/pagination.rs:1-13`, `helpers.rs:29-51`) and implements it correctly for messages (`messages.rs:2467-2530`, tuple-comparison keyset with validated cursor); these seven accept a client-supplied integer "cursor" that is really an OFFSET — deep pages do O(offset) scans and shift when rows are inserted, and a client following the documented contract gets offset semantics. Fix: migrate them to the shared keyset helper or rename the parameter `offset`.

9. **[P3] Two diverging definitions of "system tenant"** — `src/middleware/auth.rs:1414-1433` (`require_system_tenant`) is slug-aware: literal `"system"` or a DB lookup for `slug = 'system'` (`web.rs:2258-2269`), explicitly because hardcoding 403'd every human operator (comment at `auth.rs:1406-1413`). `src/routes/billing.rs:1363-1369` (`has_admin_access`) instead hardcodes the literal `"system"` plus `SYSTEM_TENANT_ID = "system_internal_tenant01"` (`system_sender.rs:17`). Today the hardcoded id is the seeded row, so billing accepts a subset of CP-accepted identities (safe direction), but any re-seed/rename of the system tenant silently locks every human operator out of billing admin — the exact failure class the CP gate was already fixed for. Fix: make billing call the shared `require_system_tenant` state-aware gate.

10. **[P3] Google SSO verifies ID tokens via the network `tokeninfo` endpoint** — `src/routes/sso.rs:724-751`: `verify_google_id_token` GETs `https://oauth2.googleapis.com/tokeninfo` per login rather than verifying the JWT locally against Google's JWKS. Audience/issuer/expiry are checked afterwards (753-775), so it is sound, but it couples every Google login's availability and latency to a third-party endpoint Google documents as not intended for production use, while the crate already ships local RS256 + multi-key rotation machinery (`middleware/auth.rs:1313-1341`). Fix: fetch/cache Google's JWKS and verify locally.

**Top 5 improvements:**

1. **Finish the account-deletion lifecycle** (finding 1) — it is the only finding that directly breaks a user-facing data-protection promise; wire cancellation + a retention sweeper into the existing GDPR tooling.
2. **Unify platform-admin authorization into one gate** (findings 3, 5, 9) — one `require_platform_admin` function that resolves system tenancy slug-aware, applies the CP session policy, and stamps the actor into every audit write; today there are three hand-rolled variants (`require_system_tenant`, `has_admin_access`, `sales_owner`) plus per-handler audit calls that drift.
3. **Enforce scope checks uniformly** (finding 2) and replace the string-match scope-guard test (`admin/mod.rs:133-159`, which passes if `require_scopes(&auth, &["*"])` appears anywhere in the file, even dead code) with a routing-inventory test that exercises each admin/billing route with a scoped-down credential.
4. **Split `src/routes/web.rs`** — 25,000 lines and 102 routes in one file (plus `web/data.rs` at 7.4K) is the crate's biggest maintainability risk; extract per-domain form/SSR modules (auth forms, contacts, campaigns, billing forms, CP forms) the way `routes/admin/` is already organized. Similarly, `ip_provider.rs` (5K) and `ses_provider.rs` (1.5K) are service-layer providers living inside the HTTP crate.
5. **Migrate the offset-mislabeled-as-cursor endpoints to the shared keyset helper** (finding 4's explorer key churn and finding 8) — one pagination contract crate-wide, and bound the explorer sandbox's key provisioning to a cached, cleaned-up single row.

## SM4 — Auth, DB & Platform Foundations (auth-server, apexmail-db, apexmail-lib, migrator, rate-limiter)

**Verdict:** This sub-module is in materially better shape than most of the workspace. The crypto primitives (OWASP Argon2id with param validation, HMAC-SHA256, AES-256-GCM at-rest with AAD binding, CSPRNG secret generation with rejection sampling, constant-time compares), the migrator (per-revision template DBs, ledger verification, fail-closed provisioning), and the Redis token-bucket limiter (atomic Lua, redis-side TIME, skewed-writer clamping, divided fallback budget) are all genuinely hardened and adversarially tested. The concentrated risk lives in auth-server's *retained-but-unrouted* login/register handlers — explicitly kept "for the day a route is deliberately re-exposed" — which implement an MFA-less login with no lockout and a deterministic, non-revocable session token: one router line away from being a live auth bypass. Secondary issues: webhook signing secrets stored and returned in plaintext, a Redis-outage fallback that collapses per-tenant isolation into one global bucket, a non-atomic registration write, and a bootstrap SCHEMA constant in apexmail-db that can never execute successfully against a fresh database.

**Findings:**

1. **[P1] Retained `login_post` bypasses MFA entirely — MFA-enabled users authenticate with password only** — `auth-server/src/main.rs:142-198` (SELECT at :157-160 doesn't even fetch `mfa_enabled`; cookie minted at :174-190 after only the argon2 check at :167-169). The handler is `#[allow(dead_code)]` and unrouted today, but the crate docs (:33-38) state it is "intentionally NOT wired into the router… kept for the day a route is deliberately re-exposed… with their security fixes applied." The claimed security fixes are present (constant-time MAC, expiry) but MFA is not among them: re-adding `.route("/login", post(login_post))` per that documented plan gives every `mfa_enabled=true` user a full session on password alone — a silent second-factor bypass. Fix: before any re-exposure, gate `login_post` on `mfa_enabled` (fetch the column, return an MFA-challenge response instead of a session cookie), or delete the handler; as-is it is a loaded footgun that contradicts its own doc comment.

2. **[P2] `login_post` has no lockout/throttle and leaks user existence through timing** — `auth-server/src/main.rs:164-172`: `_ => (String::new(), false)` — when the email is unknown, no argon2 verification runs at all, so responses for nonexistent users return in microseconds while real users pay a ~19 MiB Argon2id computation; an attacker measures the delta to enumerate registered emails, then password-sprays with zero rate limiting (no rate-limiter, no failed-attempt counter anywhere in the handler). Fix: verify against a fixed dummy hash on user-not-found, and route login attempts through the rate-limiter (this crate's own `RedisLimiter`/`KeyedRateLimiter`) keyed per-identifier and per-IP before the re-exposure that finding 1 anticipates.

3. **[P2] Session tokens are deterministic, non-revocable, and not HMAC-constructed** — `auth-server/src/main.rs:111-120` (`create_session_token`) and :76-109 (`verify_session_token`). Token = `email:ts:SHA256(email:ts:secret)`: (a) zero randomness — the same user logging in twice in the same second gets a byte-identical token, so nothing distinguishes sessions; (b) verification is purely stateless MAC check — there is no server-side session store, so logout, password change, and MFA-reset cannot invalidate a leaked token; it is valid for the full 24 h (:43) no matter what the user or admin does; (c) the construction is a homebrew `SHA256(msg||secret)` rather than HMAC (contrast `apexmail-lib/src/crypto.rs:37-55`, which does it right — and is never used here); (d) the email rides in cleartext in the cookie. Impact: stolen/leaked cookies are unkillable for 24 h; sessions are unfingerprintable. Fix: random ≥128-bit session id (OsRng) as the cookie value with a server-side (or Redis) session record carrying expiry/revocation, or a proper JWT with `jti` + denylist; at minimum switch the MAC to `create_hmac_signature` over a random nonce.

4. **[P2] Webhook signing secrets stored plaintext at rest and returned by every read** — `apexmail-db/src/repos/webhooks.rs:21-29` (INSERT binds `secret` raw), :40-47/:60-68/:87-107 (every SELECT returns `secret` into the `Webhook` struct, which has it as a plain `String` field in `apexmail-db/src/types.rs`); canonical schema `migrations/075_create_missing_tables.sql` declares `secret VARCHAR(255)`. These are the HMAC keys that authenticate outbound webhook payloads — a DB dump (or any code path that serializes `Webhook`) yields every tenant's webhook signing secret, enabling forged delivery callbacks. The codebase already has the fix in-module: `apexmail-lib/src/secret_at_rest.rs:279+` (`encrypt_at_rest` with AAD, production fail-closed) is used for `mfa_secret` but not here. Fix: encrypt via `secret_at_rest` with `aad = format!("webhook={id}")`, migrate on read (`migrate_at_rest`), and drop `secret` from list/find projections (return only a masked prefix).

5. **[P2] Redis-outage fallback collapses per-tenant limits into one global bucket** — `rate-limiter/src/redis_limiter.rs:340-361`: `check_n_for_tenant(Some(tenant), n)` builds the tenant-scoped Redis key at :346, but on any Redis error the error arm (:355-359) executes `self.fallback.check_n(n)` — a single un-keyed `GovernorLimiter` created at :198/:235. During a Redis outage every tenant on the pod shares one bucket of `burst/2` (default divisor, :62-65): one noisy tenant exhausts it and all other tenants' legitimate traffic is denied (fail-closed over-limiting), inverting the per-tenant isolation the API is built on. Fix: make the fallback a `KeyedRateLimiter` (already in this crate, with eviction tombstones) and scope `check_n` to `tenant_id` in the fallback path.

6. **[P2] apexmail-db's bootstrap `SCHEMA` cannot execute — `campaigns.template_id UUID REFERENCES templates(id)` where `templates.id` is VARCHAR(26)** — `apexmail-db/src/migrations.rs:331` (`template_id     UUID        REFERENCES templates(id) ON DELETE SET NULL`) vs :173 (`id          VARCHAR(26) PRIMARY KEY`) in the same `SCHEMA` constant. PostgreSQL rejects FKs between uuid and varchar (`…are of incompatible types`), so `run_migrations` (:540-546) — which wraps the whole constant in one transaction — fails at the campaigns CREATE TABLE on any fresh database. Grep shows no callers of `run_migrations` anywhere, and the module's own tests (:609-718) are string-`contains` assertions that pass despite the broken DDL, so the drift is invisible. The canonical chain (`migrations/075_create_missing_tables.sql:119-130`) has no such FK, so this is pure dead-code drift pretending to be "a single-file reference" (:4-5). Fix: delete `SCHEMA`/`run_migrations` and route any bootstrap need through `migrator::test_support` (the stated purpose of that module), or fix the FK to match canonical.

7. **[P2] Registration writes tenant and user as two autocommit statements with the first error swallowed** — `auth-server/src/main.rs:269-287`: `let _ = sqlx::query("INSERT INTO tenants …")` discards all failures (conflict *and* real DB errors), then the user INSERT runs on a separate connection/transaction. Any tenant-insert failure that isn't a conflict leaves the user INSERT to fail on the FK (user sees "Registration failed"), and any user-INSERT failure leaves an orphaned tenant row (free-plan count at :245-250 counts it forever, permanently consuming capacity against `FREE_TENANT_LIMIT`). The shared `Tx` helper exists precisely for this (`apexmail-db/src/transaction.rs:15-41`, `with_transaction` :52-65) but has zero callers in any repo. Fix: wrap both inserts in `Tx::begin`/commit so registration is atomic, and stop ignoring the tenant error.

8. **[P2] Public, unauthenticated status endpoints run uncached heavy DB probes plus a 3 s SMTP connect per request** — `auth-server/src/main.rs:436-531` (`probe_services`): six sequential queries per request, including `SELECT COUNT(*) FROM messages WHERE created_at > NOW() - INTERVAL '5 minutes'` (:468-470) and `… WHERE status = 'delivered' AND created_at > …` (:506-508) against the partitioned high-volume `messages` table (partitioned in `migrations/050_partition_high_volume_tables.sql:111`), plus a 3 s TCP connect (:319-324, :522). Both `/status` and `/status/api` are public through nginx (:565-570) with no caching, so a trivial loop of GETs multiplies into full-table-window COUNT scans on the primary and a slowloris-adjacent page latency; every browser refresh also blocks up to 3 s on the SMTP probe. Fix: run probes on a 30-60 s background task and serve the cached snapshot (the page already claims "probes run every 60 seconds" at :372 — make it true), and cap SMTP-probe concurrency.

9. **[P3] TOTP lockout state is per-process memory — ineffective across pods/restarts, and the map never shrinks** — `apexmail-lib/src/mfa.rs:51-55` (`attempts: parking_lot::Mutex<HashMap<String, (u32, Option<Instant>)>>`): with N replicas an attacker gets 5 guesses per window *per pod* (5·N effective), and a restart wipes all lockouts; entries are removed only on successful verify (:119-121), so failed-then-abandoned secrets accumulate. The api-server wraps this in a Redis-guarded path (`api-server/src/routes/auth.rs:1525-1526`, `verify_totp_code_guarded` at :1664), which mitigates it there — but the primitive sells itself as the rate-limiting verifier ("Prefer `TOTPVerifier::verify` in production code", :144) while being per-process only. Fix: move lockout accounting behind a trait (Redis impl) or document the single-process scope on the type.

10. **[P3] TOTP codes are replayable within their 90 s validity window** — `apexmail-lib/src/mfa.rs:151-178` (`verify_totp_code_inner` accepts offsets 0/±1 with no record of the last successfully used counter). RFC 6238 §5.2 explicitly requires rejecting reuse of the same time-step code; a code phished or logged once can be replayed for up to 90 s (and once per pod, given finding 9). Fix: track `last_used_counter` per secret (alongside the lockout state or in the api-server challenge record) and reject `counter <= last_used_counter`.

11. **[P3] `verify_password` hard-fails on weak Argon2 params — legacy hashes get a permanent lockout instead of a migration** — `apexmail-lib/src/crypto.rs:317-324`: `validate_argon2_params(&parsed)?` (:320) turns any stored hash with `m<19456` or `t<2` into `Err`, and `verify_password_for_login` propagates it at :334 (`valid: verify_password(password, hash)?`) — compare the bcrypt path (:339-358), which verifies and transparently upgrades to Argon2id. If any pre-OWASP argon2 hash exists in the DB, that user can never log in (and never be migrated); the same pattern in `verify_api_key_hash` (:140-146) bricks legacy API keys. Fix: on weak-but-valid params, still verify against the stored params and return `migrated_hash: Some(hash_password(...))` like the bcrypt branch.

12. **[P3] `User` rows always carry `password_hash` through every read path** — `apexmail-db/src/repos/users.rs:22-25, 39-45, 50-57, 67-70, 90-98, 115-133` — every SELECT (including `list_by_tenant`/`list_keyset`) projects `password_hash` into the `User` struct (`apexmail-db/src/types.rs`), which derives `Serialize`. Login needs the hash; user listings never do — every listing is one accidental `Json(user)` away from leaking the entire credential table. Fix: split the projection (a `UserPublic` without `password_hash`, and a `find_by_email_for_login` that includes it), or `#[serde(skip)]` the field.

13. **[P3] Sliding-window `retry_after` under-reports when the current window alone is over budget** — `rate-limiter/src/sliding_window.rs:100-108`: denial returns `window - elapsed`, but `weighted_count = prev·(1-p) + curr` (:61-69) stays ≥ `max_events` through the rest of the current window *and* (once `curr` rotates into `prev`) potentially the whole next window when `curr_count` alone exceeds the limit — so a compliant client honoring `retry_after` will re-request up to a full window early and be denied again. Fix: compute retry_after as the time until the weighted estimate actually drops below `max_events` (solve `prev·(1-p) + curr < max` for p; if unsolvable in-window, add one full window).

**Top 5 improvements:**

1. **Resolve the auth-server dead-handler question decisively.** Either delete `login_post`/`register_post` (the interactive auth lives in api-server per the crate docs), or complete them before any re-exposure: enforce MFA (finding 1), add lockout + rate limiting + timing-uniform failure (finding 2), and replace the deterministic token with random, server-revocable sessions (finding 3). Today they are one router line from a live bypass.
2. **Encrypt webhook signing secrets with the already-built `secret_at_rest` module and strip `secret` from read projections** (finding 4) — smallest change, largest credential-exposure reduction.
3. **Make the RedisLimiter fallback tenant-scoped** using this crate's own `KeyedRateLimiter` (finding 5) so a Redis outage no longer converts per-tenant isolation into global starvation.
4. **Enforce transaction boundaries for multi-table writes** — wrap registration (tenant+user) in the existing, currently-unused `Tx`/`with_transaction` helper (finding 7) and stop discarding the tenant-insert error.
5. **Serve the status page from a cached background probe snapshot** (finding 8) — it removes a public DB-load/latency amplifier and makes the page's own "probes run every 60 seconds" claim true.

Additional note for the record: no SQL injection found (the only `format!`-built SQL interpolates a compile-time column constant, `contacts.rs:19-20`; all values are bound), no lock-across-`await` (the `tokio::Mutex` in `redis_limiter.rs:469` guards no await), no `Local`/timezone misuse, and no weak RNG on secret paths (`generate_id`'s nanoid PRNG is documented non-secret; `generate_api_key`/`generate_webhook_secret`/`generate_verification_token` all use OsRng with rejection sampling, `apexmail-lib/src/id.rs:29-52, 63-116`).

## SM5 — Edge/Network Security Engines (ddos-protection, fingerprint, waf-engine, ids-engine, isolation)

**Verdict:** This sub-module is far more hardened than the average "security engine" crate — prior audit rounds (F2/F3/F9/F10/G/I, E-105/107, #292/293) visibly fixed the classic issues: no `unwrap/expect/panic!` in non-test code, all regexes/Aho-Corasick automatons compiled once (linear-time `regex` crate — no ReDoS possible), SQL is parameterized with validated/quoted identifiers, IP identity is canonicalized (v4-mapped + IPv6 /64 truncation), XFF is trusted-proxy/rightmost-entry only, PoW challenges use a server-side issuance registry with HMAC, replay cache and clamped difficulty, tracking tables have hard capacity caps, and Postgres RLS is created with `FORCE ROW LEVEL SECURITY`. What remains is a set of real detection/memory/correctness defects concentrated in three places: (1) the WAF's fast-path gate is a keyword *denylist-ish inclusion signal* whose vocabulary is NOT a superset of the analyzers it gates — concrete XSS/SQLi payloads slip past untouched; (2) the DDoS crate's per-IP adaptive limiter is a single *global* threshold fed by *all* clients' rates, so one attacker both poisons the baseline and tightens the limit for every legitimate user, while the anonymous cost-bucket map has an eviction rule that never fires for partially-drained buckets (unbounded memory under IPv6 rotation); (3) several `Instant::now() - Duration` sites panic on low-uptime hosts — one of them sits directly on the request path. The isolation crate's regex-based SQL guard has two parse-desync bypasses, and the IDS SMTP analyzer Drops on any NUL byte in DATA, refusing legitimate binary mail in inline mode.

**Findings:**

1. **[P1] WAF fast-path gate vocabulary is not a superset of the analyzers it gates — direct XSS/SQLi bypass** — `waf-engine/src/fast_path.rs:90-153` vs `waf-engine/src/xss_analyzer.rs:106-221`, gated at `waf-engine/src/engine.rs:235-246, 327-331, 448-459`. The engine only runs `analyze_xss`/`analyze_sqli` when `fast_path_check` matches (`if self.config.enable_xss && path_fast_check.has_xss_patterns`). The gate list contains ~24 event-handler prefixes and ~18 tags/sinks, but the analyzer recognizes 100+ handlers (`ontoggle`, `onfocusin`, `onwheel`, `onscroll`, `oncopy`, `onmessage`, … at xss_analyzer.rs:106-221) and tags (`<details`, `<video`, `<audio`, `<template`, `<math`, `<base`, … at xss_analyzer.rs:281-301). Payload `<x ontoggle=fetch('//evil')>` contains **no** gate token (no `onerror/onload/...`, no listed tag, `fetch(` is not a gate sink) → `has_xss_patterns=false` → the analyzer that *would* fire rule 941200 never runs → request allowed. Same class on the SQLi side: `1;TRUNCATE TABLE users` — `truncate` is in `detect_comment_evasion`'s dangerous sequences (sql_analyzer.rs:703-713) but not in the gate list nor `match_keyword`, so the tokenizer never runs. The tests only exercise payloads whose tokens are in both lists. Impact: reliable, trivially constructible WAF bypass for the exact attacks the analyzers were built to catch. Fix: make the gate structural instead of lexical — gate XSS on `on[a-z]+\s*=` / `<[a-z]` detection (the analyzer already does complete-word matching), gate SQLi on the tokenizer itself (it is cheap), or assert gate-superset with a property test over the analyzer vocabularies.

2. **[P2] "Per-IP" adaptive rate limiter is one global threshold fed by all clients — single-IP attack 429s everyone** — `ddos-protection/src/lib.rs:210-222` (one `AdaptiveRateLimiter` for the whole process), `lib.rs:368-385` (`adaptive.update(...)` with *this session's* rate, then `if rate_rps > adaptive.current_threshold()` enforced **per request for every IP**), `adaptive.rs:205-233` (z-score over the pooled observations tightens the shared threshold to `0.5 × mean`). One IP blasting for a few seconds declares "attack", sets the global threshold to half the pooled mean, and every legitimate client exceeding the tightened limit gets `RateLimit` until cooldown (120 s default) plus recovery. Conversely, an attacker contributing a large share of observations steers the EMA threshold upward for their own fleet. The config knobs are literally named `per_ip_*` (`config.rs:27-40`) — the implementation is global. Impact: cheap cross-tenant denial of service and attacker-controllable limit tuning. Fix: shard the limiter per canonical IP key (bounded LRU of limiters, like the session table) or compute the per-IP z-score against a *global* baseline but keep the threshold per-IP.

3. **[P2] Anonymous cost-budget map grows without bound — eviction rule never fires for partially-drained buckets** — `ddos-protection/src/cost_based.rs:147-157` (a `TenantBudget` entry is created per `anon:{ip}` key, `lib.rs:877-883`), `cost_based.rs:273-285`: `cleanup()` evicts only `is_at_capacity && is_stale` — an entry with `remaining < capacity` is **never** evicted ("Keep entries that have recent activity or are not at full capacity"). The reputation table (250 k cap) and session table (100 k cap) are hard-capped; this map has no cap at all. An attacker rotating IPv6 /64s (each /64 is one canonical key, `lib.rs:908-920`) or a modest botnet mints one permanent `String + RwLock<TenantBudget>` entry per address after a single request. 1 M distinct keys ≈ 100+ MB of uncontrollable growth. Fix: add a `max_tracked_budgets` cap with LRU-by-`last_refill` eviction (mirror `SessionTracker::enforce_capacity`), and evict stale entries regardless of remaining budget.

4. **[P2] `Instant::now() - Duration` panics on low-uptime hosts — one site is on the request path** — `ddos-protection/src/adaptive.rs:146` (`let cutoff = Instant::now() - self.config.baseline_window;`, default 300 s) is executed from `DdosProtector::evaluate` → `adaptive.update` on **every request**; `Instant` subtraction panics when the result precedes the monotonic epoch, i.e. when host uptime < the window. A freshly booted/reprovisioned host or VM panics every DDoS-evaluated request for the first 5 minutes. Same pattern in background loops that silently die on panic (tokio aborts the task, cleanup stops): `ddos-protection/src/coordinator.rs:688,769` (`- event_retention`, default **3600 s**), `ids-engine/src/engine.rs:389` (`- 60s`), `ddos-protection/src/smtp_protection.rs:604` (`- 120s`). `fingerprint/src/database.rs:418` already does it correctly (`checked_sub(...).unwrap_or(now)`). Fix: replace all five with `checked_sub` + fallback to `Instant::now()`/epoch, and add `#[track_caller]` panic telemetry to spawned loops.

5. **[P2] Isolation SQL guard bypass: `FROM"emails"` (no whitespace) and dollar-quote desync** — `isolation/src/data_isolation.rs:34-46`: `TABLE_REF_RE` requires `\s+` between the clause keyword and the table (`\b(?:from|join|update(?:\s+only)?|into)\s+`), but PostgreSQL accepts `SELECT * FROM"emails" WHERE ...` (the quote terminates the keyword). The regex never captures the table → `touches_tenanted_table=false` → the workspace-predicate requirement at `data_isolation.rs:426-440` is skipped entirely and `validate_query_access` returns true for an unscoped tenanted query. Second vector: `strip_sql_comments` (`data_isolation.rs:91-148`) tracks single-quote strings but not dollar-quoted strings (`$$...'...$$`), so a literal like `$q$'$q$` flips the stripper into string-mode and swallows the subsequent real `FROM emails` — Postgres parses it as a literal followed by a live clause. Both bypasses defeat the textual tenant guard; RLS (when actually configured via `setup_rls`) is the only remaining backstop. Fix: allow zero-whitespace before quoted identifiers in `TABLE_REF_RE` (`\s*` + a `"` branch), and make the stripper dollar-quote aware — or better, parse with a real SQL tokenizer instead of regexes.

6. **[P2] IDS SMTP NUL-byte rule Drops on DATA payloads → legitimate binary mail refused** — `ids-engine/src/protocol_analyzer.rs:104-113` (`payload.contains(&0u8)` → anomaly 3000004, `action: SignatureAction::Drop`, severity High), wired to the full raw DATA payload at `mta/src/servers/content_security.rs:937` (`runtime.engine.inspect(ip, port, "smtp", raw)`), where a Drop verdict refuses the message when `MTA_IDS_REFUSE=true` (`content_security.rs:1004`). Any inbound message carrying a non-base64 binary attachment (8BITMIME bodies, PDFs, images, zip archives all contain `0x00`) is classified as "possible evasion" and refused. This is a false-positive mail-loss path on the primary inbound flow. Fix: restrict 3000004 to the *command* stream (before DATA) or require multiple NULs / a NUL inside an SMTP verb, and exempt the DATA phase.

7. **[P2] WAF rule 942700 blocks on the bare English word "load" (blocking score)** — `waf-engine/src/sql_analyzer.rs:443` maps `"load" | "load_file"` to `Keyword(Load)`; `detect_dangerous_functions` (sql_analyzer.rs:913-929) fires score **5** on any `Keyword(Load|Outfile|Dumpfile|Information)`; default `blocking_threshold: 5` (`waf-engine/src/config.rs:56`). The fast-path gate opens on any apostrophe/`#`/`--` (fast_path.rs:55-68), so a perfectly ordinary body like `I can't load the file #42` passes the gate, tokenizes "load" as the SQL keyword, and gets a 403. Same shape for "outfile"-adjacent prose. Impact: over-blocking legitimate API/ticket bodies — the failure mode operators respond to by raising thresholds or disabling the rule, degrading all SQLi protection. Fix: require the keyword in call/qualified form (`load_file(`, `LOAD DATA`, `INTO OUTFILE`) as the comment-detection path already does, or lower 942700 to a monitoring score unless paired with a second signal.

8. **[P2] `/isolation/migrate/:org_id` passes an org ID where a workspace ID is required — migration silently no-ops and reports success** — `isolation/src/routes.rs:939-946` calls `migrate_isolation_level(&org_id, &current, &target)`, but the callee signature is `migrate_isolation_level(&self, workspace_id: &str, ...)` (`isolation/src/data_isolation.rs:582-587`). `migrate_to_schema` then creates an orphan `ws_{org_id}` schema with empty cloned tables (`WHERE workspace_id = $1` matches no rows), the `UPDATE iso_workspaces ... WHERE id=$2` and `iso_isolation_configs ... WHERE workspace_id=$2` touch zero rows, and the endpoint still returns `{"status":"migrated"}`. Operators believe tenants moved to dedicated schemas when nothing moved; orphan schemas accumulate. Fix: resolve the org's workspaces and migrate each (in one transaction per workspace), or make the route workspace-scoped like its siblings; return 404/409 when zero workspaces matched instead of "migrated".

9. **[P2] Tenant-predicate check is satisfied by `workspace_id = $N` anywhere in the query — wrong-table scoping** — `isolation/src/data_isolation.rs:50-59` (`TENANT_PREDICATE_RE` matches the predicate textually) and `426-440`: a query joining two tenanted tables passes validation when *any one* of them carries the predicate, e.g. `SELECT * FROM contacts c JOIN emails e ON e.contact_id = c.id WHERE c.workspace_id = $1` is accepted while `emails` is unscoped — if the join key doesn't itself encode tenancy, cross-workspace `emails` rows leak. Fix: require the predicate on every extracted tenanted alias (per-table check), not once globally.

10. **[P3] Blocklist `DashMap` has no capacity cap** — `ddos-protection/src/lib.rs:116, 585-591` (`blocklist.insert` unbounded), removal only on expiry in `run_cleanup_once` (lib.rs:785-797). Reputation/sessions/cost tables all got hard caps (fix G / F9) but the blocklist did not: a distributed attacker driving IPs below `block_threshold` (two ML anomalies × 20 points each, lib.rs:442-443) mints one 1-hour entry per IP with no bound. Fix: cap with LRU-by-expiry eviction, same pattern as `alert_counts` (`ids-engine/src/engine.rs:409-442`).

11. **[P3] IDS Drop-specificity guard counts pattern *occurrences*, not distinct patterns** — `ids-engine/src/signature.rs:175-178` (`e.0 += 1` on every automaton hit) vs the documented intent at `signature.rs:204-209` ("≥2 **distinct** matched tokens"). Two occurrences of the same 4-byte token `cmd=` satisfy the guard and fire a content-only Drop signature (2000072) — `?a=cmd=1&b=cmd=2` drops. Fix: track a per-signature `HashSet<pattern_idx>` and count its size.

12. **[P3] SID 2000051 (HTTP/2 Rapid Reset) can never match real traffic** — `ids-engine/src/signature.rs:576-589`: the content pattern is the ASCII string `RST_STREAM`, but HTTP/2 is binary-framed — the frame type is the byte `0x03` and the string never appears on the wire (HPACK never emits it). The signature is dead weight that reads as CVE-2023-44487 coverage in `signature_count()`. Fix: parse the SETTINGS/RST_STREAM frame header bytes (the TLS/record parsing already exists in `tls_handshake_below_tls12`) or remove the signature rather than claim coverage.

13. **[P3] Inert config + contradictory reputation decay for trusted IPs** — `ddos-protection/src/config.rs:49-50` defines `initial_reputation`, but `ReputationScore::default` hardcodes 50 (`reputation.rs:45-60`) — the knob does nothing (same "inert config" class as the fixed audit F2c). Worse, `ReputationScore::decay_toward_neutral` explicitly exempts trusted/flagged IPs (`reputation.rs:120-131`), but the cleanup loop's inline decay (`lib.rs:814-820`) has no such check — an admin-set trusted entry (score 90) decays to 50 within ~40 minutes of cleanup ticks. Fix: use `entry.decay_toward_neutral(1)` in the retain closure and honor `initial_reputation` in `or_insert_with`.

14. **[P3] WAF `paranoia_level: 0` silently disarms every rule** — `waf-engine/src/engine.rs:563-566`: with `paranoia_level=0` (no lower-bound validation in `WafConfig`, config.rs:11,54) the retain filter drops *all* matches (every rule is level ≥ 1) while the engine reports healthy. Fix: validate `paranoia_level ∈ 1..=4` at construction and reject the config.

15. **[P3] Tenant-claim model fails open on a missing header and cannot detect forgery** — `isolation/src/routes.rs:170-196`: `verify_org_claim` returns `Ok` when `x-org-id` is absent ("internal service-to-service traffic"), and when present only checks claim==path — a client whose `x-org-id` is forwarded unmodified by the edge can claim the victim org and pass trivially. All tenant separation in this service rests on the bearer secret plus an *assumed* edge behavior (strip/overwrite). Fix: require the claim header in production mode (config flag), and log-and-alert on claim/path mismatch instead of debug-logging its absence.

16. **[P3] SSRF internal-range list misses uncompressed IPv6 loopback** — `waf-engine/src/detection.rs:543-576`: patterns cover `://[::1]`, `://[fe80:`, `://[fc00:`, `://[fd`, `://0:`, but not `http://[0:0:0:0:0:0:0:1]/` or `://[::ffff:10.` variants in URL position — an attacker rotates the textual form and skips rule 934200. Fix: parse the host and compare against `Ipv6Addr::is_loopback/is_uniquelocal/is_link_local` (the codebase already canonicalizes IPs elsewhere) instead of string matching.

**Top 5 improvements:**

1. **Make the WAF fast path provably conservative** — derive the gate from the analyzers' own matchers (or run the cheap SQL tokenizer unconditionally) and add a property test asserting every analyzer-recognized payload opens the gate; today the gate is the single most exploitable component (Finding 1).
2. **Shard the adaptive limiter per canonical client key and cap the anonymous cost-bucket map** — removes both the cross-tenant 429 amplification and the last unbounded per-IP-keyed table (Findings 2, 3, 10).
3. **Replace bare `Instant::now() - Duration` with `checked_sub` everywhere** (five production sites, one on the request path) and add panic telemetry to spawned maintenance loops (Finding 4).
4. **Swap the isolation crate's regex SQL guard for a real tokenizer** (whitespace-free `FROM"emails"`, dollar-quote desync, wrong-table predicate scoping all disappear), and fix the `/isolation/migrate` org-vs-workspace parameter bug before any operator relies on it (Findings 5, 8, 9).
5. **Tune the IDS/WAF false-positive Drops that burn operator trust**: NUL-byte Drop on DATA payloads, bare-"load" 942700, occurrence-counting specificity guard, and the dead Rapid Reset signature — then wire the paranoia-level and initial-reputation config validation so silent disarm/inert knobs cannot recur (Findings 6, 7, 11, 12, 13, 14).

## SM6 — Content Security Engines (spam-filter, sandbox, ato-protection, dlp-engine, threat-intel, email-grader, inbox-placement, pattern-matcher)

**Verdict:** These eight crates are well above the norm for this class of code: fail-closed defaults are pervasive (ClamAV outage → Reject, oversized/unreadable attachments → risk floor, batch `Err` counts as rejected), decompression is output-bounded, caches and maps are LRU/purge-bounded, lock discipline is careful (no locks across await anywhere I checked, DashMap guard-drop documented before removal), score math is clamped and NaN-hardened (haversine clamp, log-sum-exp, weight renormalization), and prior audit rounds left visible fixes plus regression tests. The serious problems are architectural rather than sloppy: the "sandbox" is a static byte-scanner whose docs, crate description, and config advertise Linux namespaces/cgroups/seccomp detonation that does not exist anywhere in the code (and its zip-bomb/nesting config is dead); the URL-detonation SSRF guard has a classic resolve-check-then-connect-again DNS-rebinding hole; DLP chunked scanning creates a deterministic evasion seam exactly where a PII token can be placed; the PDF stream walk is quadratic on crafted input; and threat-intel silently drops feed entries (fail-open) when the blocklist saturates.

**Findings:**

1. **[P1] Sandbox advertises OS-level detonation isolation that does not exist; archive-bomb config is dead** — `sandbox/src/lib.rs:14-20` ("On Linux, this module can additionally leverage: Namespaces … cgroups v2 … seccomp-BPF … behind the `linux-sandbox` feature flag") and `sandbox/Cargo.toml` (`[features] events = ["mail-common"]` — there is no `linux-sandbox` feature; crate description claims "detonation sandbox using Linux namespaces, cgroups v2, and seccomp-bpf"). There is no `Command::new`/process execution anywhere in the crate (grep verified); attachments are never unpacked, and `SandboxConfig::max_nesting_depth`, `max_total_extracted_size`, `max_archive_entries`, `blocked_mime_types`, `analyze_macros`, `analyze_embedded_urls` (`sandbox/src/config.rs:14-29`, 37-41) are read nowhere outside config.rs (grep verified — including the fields literally commented "zip bomb protection"). Nested-archive detection relies on raw byte-string heuristics (`has_zip_vba_project`, `file_inspector.rs:585-610`), which see entry *names* but never decompressed entry *content*; a macro doc nested one archive deep is scored on the outer container's bytes only. Impact: operators reading the docs believe malicious attachments are detonated under CPU/memory/network limits; in reality the engine's only resource limits are a 25 MB size pre-check and a dynamic-analyzer wall-clock timeout. Fix: either implement bounded extraction (recursing `max_nesting_depth`, cap `max_archive_entries`, budget `max_total_extracted_size`, re-inspecting each entry with `inspect_file`) or delete the isolation claims, the dead config fields, and the crate description; at minimum stamp every verdict with "static analysis only".

2. **[P1] URL-detonation SSRF guard is bypassable via DNS rebinding (TOCTOU between guard resolution and request)** — `spam-filter/src/url_analyzer.rs:457-509`: `url_blocked_by_ssrf_guard` resolves the host via `to_socket_addrs` on the blocking pool and validates every address against `ip_is_private_or_reserved`; then line 544 `let resp = match client.head(&current).send().await` makes `reqwest` resolve the same hostname *again, independently*. An attacker controlling DNS for a link in a spam email returns a public IP for the guard lookup and `169.254.169.254`/`10.0.0.5` for the second lookup — the detonator then fetches cloud metadata or internal services, with the response influencing scoring findings. The same rebinding applies to every redirect hop. Fix: resolve once, then connect to the validated socket address with the Host header/SNI pinned to the original name (custom `reqwest` resolver returning the already-validated addrs), or reject hostnames whose TTL/answers differ between the two resolutions.

3. **[P2] DLP chunked scanning: a PII token straddling a chunk seam is invisible by construction** — `dlp-engine/src/engine.rs:122-137`: oversized bodies are split into `max_scan_size` pieces and `parts.join("\n")` — the comment states this deliberately ("A newline separator keeps PII/policy patterns from matching across a chunk seam"). A sender who pads an outbound body (quoted reply, filler) so a `4111 1111 1111 1111` or `123-45-6789` spans a multiple of `max_scan_size` (1 MiB default) gets a card/SSN that matches in neither chunk — deterministic, repeatable DLP bypass. The head+tail fallback join at `engine.rs:110-121` has the same seam (plus a documented unscanned middle). Fix: overlap consecutive chunks by ≥ the longest detectable token (64 bytes suffices for card+separators) before joining, or run the regexes per-chunk with an explicit carry-over window.

4. **[P2] Quadratic scan in PDF stream discovery — DoS via crafted attachment** — `dlp-engine/src/attachment.rs:477-523`: `find_pdf_streams` iterates *every* byte-occurrence of `"stream"` (including the one inside `endstream`), and for each occurrence runs `data[..stream_kw].windows(2).rposition(|w| w == b"<<")` (lines 495-499) — a full backwards scan of the entire prefix when no `<<` exists nearby. The guard `if streams.len() >= MAX_PDF_STREAMS_EXAMINED` (line 484) only counts FLATE streams actually *collected* (`streams.push` at 515 requires `is_flate`), so a file of repeated non-Flate `stream…endstream` pairs (~16 bytes each) never trips it: ~n/13 iterations × O(position) backwards scan ≈ 10¹²+ byte-pair comparisons on a 25 MB attachment — a multi-minute/`cpu`-pegging stall on the DLP scan path. Fix: bound total keyword iterations (not collected streams), and limit the backwards dictionary search to a small window (e.g. 1 KiB) before giving up.

5. **[P2] Threat-intel blocklist saturation silently drops feed entries (fail-open)** — `threat-intel/src/engine.rs:193-199`: `let _ = ips.add_cidr(&cidr, entry); ips.add_ip_str(&cidr, entry);` — `add_cidr` returns `Err(BlocklistFull)` and `add_ip` returns `false` when the cap is hit (`ip_blocklist.rs:151-176`), and both results are discarded with no log, no `record_refresh_failure`, no metric. Once `max_ip_entries` is reached, every subsequent refresh reports success while absorbing zero new IoCs — newly listed attacker infrastructure scores `Clean` indefinitely. Fix: count rejected entries per refresh; log + surface a degraded state (or refuse the refresh like the empty-payload case at `engine.rs:144-147`) when a material fraction is dropped.

6. **[P2] `analyze_for_tenant` skips the Bayesian cold-start guard that `analyze` enforces** — `spam-filter/src/engine.rs:539-543`: `let global_prob = if self.config.enable_bayesian { self.bayesian.classify(body) } else { 0.5 };` — no `total_samples() < min_training_samples` check, whereas `analyze()` at `engine.rs:209-221` forces 0.5 "Neutral — don't let an under-trained model influence scoring" below 200 samples (default). Through the 60/40 blend (line 557), a 2-sample model's raw probability directly moves tenant verdicts — exactly the failure the guard exists to prevent, and the two entry points are documented as sharing a scoring path. Fix: apply the identical guard to `global_prob` (and hence the blend) in `analyze_for_tenant`.

7. **[P3] `PatternMatcher::find_first` returns `None` for every input once the automaton is degraded** — `pattern-matcher/src/matcher.rs:271-284`: `self.automaton.as_ref()?.find(...)` — the `?` exits early when the Aho-Corasick build failed; `find_all`/`is_match`/`count_matches` (lines 213-266) all route through the literal fallback in that mode, but `find_first` has no fallback arm, so it silently reports "no match" for all text exactly when the pattern set is oversized. Any detection consumer calling `find_first` loses all detection in degraded mode (the fallback tests at matcher.rs:468-492 cover every method except this one). Fix: `find_all_fallback(&text_lower).first()` mapped like the others.

8. **[P3] Spaced-card overlap dedup hardcodes 16-byte card matches** — `dlp-engine/src/pii.rs:431-432`: `let taken: Vec<(usize, usize)> = matches.iter().map(|m| (m.offset, m.offset + 16)).collect();` — already-reported card matches are 13–19 bytes (`"4111 1111 1111 1111"` is 19, Amex is 15). For a 19-byte match the stored end under-extends by 3 bytes (adjacent spaced-digit run can double-report the same card → double 8.0 risk contribution toward `block_threshold`), and for 15-byte matches it over-extends (can suppress a genuinely distinct adjacent number). Fix: record `(m.offset, m.offset + matched_len)` from the regex match, not `+16`.

9. **[P3] 7-Zip "encrypted" detection repeats the whole-file byte-scan false-positive the ZIP path explicitly fixed** — `sandbox/src/file_inspector.rs:955-966`: `is_7z_encrypted` scans for the AES codec marker `[0x06, 0xF1, 0x07, 0x01]` anywhere via `data.windows(4).any(...)` — while `zip_central_directory_encrypted` (lines 690-704) was rewritten precisely because "checking … the raw 0x99 0x01 byte pair anywhere in the file" produced false encrypted verdicts. Four random bytes occur ~n/2³² times; compressed non-encrypted 7z payloads containing them are flagged `ARCHIVE_ENCRYPTED` at risk 7.0 → quarantine by default. Fix: parse the 7z header's coded-stream/property info, or scan only bytes inside declared header structures.

10. **[P3] ClamAV analyzer has no non-Unix arm; dynamic path copies every attachment** — `sandbox/src/dynamic_analyzers.rs:555`: the analyze body's only tail expression is the `#[cfg(unix)]` block with no `cfg(not(unix))` counterpart — on a non-Unix target the function body ends after the size check with no tail expression (compile failure, not silent fail-open — confirm before any Windows port). Also `sandbox/src/engine.rs:416` clones the full attachment (`data.to_vec()`) for every dynamic analysis; at the 25 MB cap with an 8-slot pool that is ~200 MB of transient copies under one burst. Minor, but cheap to avoid (Arc the buffer).

**Top 5 improvements:**

1. Make the sandbox real or honest: implement one bounded unzip pass that recurses to `max_nesting_depth`, caps entries and total extracted bytes, and re-runs `inspect_file` per entry — this single change converts four dead config fields and the biggest detection gap (nested/compressed payload content) into enforcement; until then, strip the namespaces/cgroups/seccomp claims from lib.rs and the Cargo description.

4. Replace unbounded whole-file/prefix heuristics with bounded parsers: cap PDF keyword iterations independent of collected Flate streams, window the `<<` backwards search, and parse 7z headers instead of scanning for codec bytes.

## SM7 — Commerce & Billing (billing-service, billing-common, billing-entitlements, accounting-core, sales-autopilot)

**Verdict:** This is an unusually well-hardened commerce stack. Money is integer cents end-to-end (i128 intermediates, half-up rounding helpers, a source-scan gate banning f64 from money paths in `money_invariants.rs`); every external operation (Stripe calls, wallet debits, credit notes, journal postings) carries an idempotency key or unique source document; invoice claiming uses advisory locks + savepoints + schema backstops; the quota gate is an atomic Redis Lua with a durable usage-operation ledger; the EU legal gate and consent model fail closed everywhere; lead scoring is NaN/inf-hardened with clamped probabilities. No P0 float-money, SQL-injection, or double-charge-on-retry defect was found on the primary paths. The residual risk is concentrated in *completeness and liveness*, not arithmetic: (1) statutory ledger postings are best-effort with no replay sweep and are guaranteed to be skipped until an operator manually provisions a legal entity and open fiscal periods — nothing in migrations or code does it; (2) the sequence step state machine has a genuine dead-end where any transient failure after the `executing` claim silently drops a customer touch and stalls the enrollment forever; (3) a narrow Stripe re-collection path can double-record revenue; (4) bank statement lines are force-classified into two accounts regardless of what the payment was.

**Findings:**

1. **[P1] Statutory ledger entries are silently skipped forever when the ledger isn't provisioned — and nothing provisions it** — `billing-service/src/accounting_postings.rs:24-32`, `accounting-core/src/chart.rs:294-299`, `accounting-core/src/periods.rs:104-107`, `accounting-core/src/sweeps.rs:1-19`. `log_post_failure` documents the policy: *"accounting posting failed — billing state is committed; replay the source event once the ledger is configured (posting is idempotent)"*. But there is no replay for the billing sources: the only callers of `post_invoice_issued`/`post_payment_allocation`/`post_credit_note` are the live write hooks (`overage.rs:1968,2027`, `credit_notes.rs:480`, `stripe_webhooks.rs:2418,2444,2480`), and `sweeps.rs` explicitly sweeps only payroll/expenses/bank ("three of them had no production writer"). Meanwhile `default_legal_entity` is a bare `SELECT ... WHERE is_default` returning `NoDefaultLegalEntity` when empty (migration 220 seeds no entity), and `find_open_period_for_date` returns `NoOpenPeriod` unless an open period covers `document_date` — `ensure_period` has zero production callers (only a test route setup in `api-server/src/routes/bank_statements.rs:207`). Impact: on any deployment where an operator hasn't hand-provisioned entities/periods (i.e. every fresh one), **every** invoice revenue entry, AR settlement, and credit-note reversal is skipped with only an ERROR log; a backdated invoice after month-close fails `NoOpenPeriod` the same way. The double-entry core itself is correct — it just never receives the rows. Fix: auto-provision the default entity/chart and the covering fiscal period inside the posting adapters (or a bootstrap job), and add invoice/allocation/credit-note sweeps mirroring the payroll sweep, plus an alertable `accounting_postings_skipped_total` metric.

2. **[P1] Sequence step state machine dead-end: any failure after the `executing` claim permanently drops the send and stalls the enrollment** — `sales-autopilot/src/sequence_worker.rs:2372-2389`, `2423-2438`, `2464-2481`. The claim is `UPDATE sales_step_executions SET state = 'executing' ... WHERE id = $1 AND state IN ('scheduled','queued')` (2372-2381). Between it and the terminal write (2464-2473) sit the entire dispatcher enqueue (2423-2438) and DB updates. If any of those fails, `handle` returns `ActionOutcome::Retry` (1843-1852) — but on replay `ctx.state == 'executing'` passes the terminal-state gate (1887 only checks sent/skipped/cancelled), the claim matches zero rows, and the handler returns `ActionOutcome::Succeeded` at 2383-2389 ("claimed by another worker — skipping") **without sending and without advancing**. `advance_enrollment` runs only `if state == "sent"` (2479-2481), and no code anywhere transitions a step out of `'executing'` (grep confirms the only writers are 1191/2373/2465 in this file). A transient DB blip — not even a crash — permanently cancels the touch, reports success, and leaves the enrollment frozen mid-sequence. Fix: make the claim lease-based (`executing` + `claimed_at`, reaper re-queues steps past the lease), or return `Retry`/dead-letter instead of `Succeeded` when the claim misses a non-terminal state.

3. **[P2] Stripe usage re-collection with a changed remainder can double-charge and double-record revenue** — `billing-service/src/overage.rs:2191-2197`, `1684-1715`; `billing-service/src/stripe_webhooks.rs:2453-2483`. The Stripe idempotency seed embeds the live amount: `"usageinv_{}_{}_{}c_{}" ... amount_cents` (2191-2197). If attempt 1 creates+finalizes Stripe invoice A and stores the mapping, then an allocation lands (manual payment, wallet credit) before a collection retry, the recomputed smaller `remaining_cents` produces a **new** key → a second Stripe invoice B for the delta. The local mapping update then refuses (`WHERE ... stripe_invoice_id IS NULL OR = $2`, 1685-1694) and only warns (1700-1706). When B's `invoice.paid` arrives, `marked` is empty (no local row carries B's id), so `insert_paid_invoice_from_stripe` (2461) inserts a **second** paid invoice and `post_invoice_issued` posts a second AR/revenue entry (2469-2481) — one obligation, two invoices, two ledger entries, customer charged A+B. Fix: freeze the collection amount on the outbox payload at first attempt and always reuse it; in `insert_paid_invoice_from_stripe`, refuse (or link for review) when the tenant already has a bound Stripe invoice for the same local obligation.

4. **[P2] An accounting-hook SQL failure inside a billing transaction aborts the billing write itself, contradicting the documented best-effort policy** — `billing-service/src/credit_notes.rs:480-482` + `billing-service/src/accounting_postings.rs:77-86`. `post_credit_note_in(&mut tx, ...)` runs inside `create_credit_note`'s transaction. A non-SQL failure (`NoOpenPeriod`, `NoDefaultLegalEntity`) is swallowed per policy — the credit note commits, the ledger entry is lost (finding 1). But a **SQL-level** failure inside the adapter (FK violation on an account, CHECK violation) poisons the Postgres transaction; the subsequent `tx.commit()` at 482 returns a generic `Db` error and rolls back the wallet mint and credit note entirely, with nothing in the error pointing at the ledger. Two contradictory failure modes from one call site. Fix: wrap the in-tx hook in a SAVEPOINT and map SQL failures to the same logged-skip path as typed errors (or make posting failures fail the billing write loudly and deliberately everywhere).

5. **[P2] PAYG months that miss the 40-day window are unbilled and leave no review marker** — `billing-service/src/overage.rs:1548-1562`, `1130-1138`. The PAYG sweep only ever considers the last two completed months (`recent_completed_calendar_months`, bounded by the 40-day metering TTL). When a PAYG tenant lacks a billing address, the whole claim transaction — including the `billing_periods` row — is rolled back (1130-1138), so unlike the subscription half (which surfaces `aged_needs_review`, 693-710), a PAYG month that stayed address-less past the window simply ceases to exist: usage ages out with the metering events and the revenue is silently forgone with no `needs_review` state and no counter. Fix: commit the period claim with `needs_review` on the address gate (mirroring the subscription half) instead of rolling back.

6. **[P2] Every bank statement payment posts to "operating expense" and every receipt credits Accounts Receivable** — `accounting-core/src/adapters.rs:1090-1100`. `post_bank_statement_line_in` hardcodes: receipt → `Dr bank / Cr AR`, payment → `Dr expense / Cr bank`. A payroll transfer, a tax payment, or an owner capital injection ingested from the statement is posted to the wrong account (and capital credited to AR misstates receivables). Entries stay balanced, so close-time `debit==credit` checks pass — the books are wrong in classification, not in sum. Fix: classify lines by counterparty/reference into suspense when unmatched, and route known counterparties (payroll payable, tax payable) to their accounts; leave unmatched lines in `ROLE_SUSPENSE` for human review.

7. **[P3] `stripe_decimal_to_cents` unchecked multiply on external input** — `billing-service/src/stripe_webhooks.rs:2631-2639`. `Some(whole * 100 + frac_parsed)` — `whole.parse::<i64>()` accepts up to i64::MAX, so `whole * 100` overflows and wraps in release for a (signature-verified, so unlikely) payload ≥ ~9.2e16 major units. Same class: `derive_invoice_totals`'s unchecked `sub + vat` at 608-611. Use `checked_mul`/`checked_add` → `None`, as `bank_ingest::parse_amount_cents` already does correctly (`accounting-core/src/bank_ingest.rs:228-233`).

8. **[P3] `vat_amount_half_up` rounds asymmetrically for negative bases** — `billing-common/src/vat_rates.rs:143-149`. `(amount_cents * rate_tenths + 500) / 1000` on a negative amount rounds toward +∞ (magnitude down), diverging from the half-up-on-magnitude behaviour of positive amounts. All current callers pass non-negative bases (`split_vat_proportional` clamps at 0), so this is latent — but it is the platform's single VAT helper, and credit-side VAT bases are one refactor away. Fix: branch on sign and round half-away-from-zero.

9. **[P3] Invoice line text hardcodes the € symbol for non-EUR snapshot currencies** — `billing-service/src/overage.rs:2577-2585` via `billing-common/src/proration.rs:27-34`. The unit test itself pins `"€0.40 USD"` (2563) — a legal invoice document quoting a euro symbol next to a USD amount. Fix: make the symbol currency-aware (or omit it) in `format_rate_per_thousand_emails`.

10. **[P3] `i64::MIN` bank amount wraps through `unsigned_abs() as i64`** — `accounting-core/src/adapters.rs:1089`. For `amount_cents == i64::MIN` the magnitude wraps back negative; `validate_lines` then rejects it loudly, so no corruption occurs — but the failure mode is accidental, not designed. Use `checked_abs()`.

11. **[P3] Recipient email addresses logged at warn level on the send-refusal paths** — `sales-autopilot/src/dispatcher.rs:1623-1627`, `1694-1698` (`recipient = %recipient_email`). B2B PII in operational logs; the enrichment providers log only domains (`enrichment/providers/http.rs:226`). Consider hashing or truncating recipient addresses in logs, or gating on a debug flag.

**Top 5 improvements (ordered):**

1. **Close the ledger-completeness gap (Finding 1):** auto-provision default legal entity + chart + covering open fiscal period in the posting path, and add `invoices` / `invoice_payment_allocations` / `credit_notes` sweeps next to the existing payroll/expense/bank sweeps, with an alertable skip metric. This is the difference between "double-entry core exists" and "the books are actually kept".
2. **Fix the `executing` dead-end (Finding 2):** lease + reaper (or single-transition claim) for `sales_step_executions`, and never return `Succeeded` on a claim miss unless the row is terminal. This is a silent customer-touch loss triggered by an ordinary DB hiccup.
3. **Freeze Stripe collection parameters on the outbox (Finding 3)** so retries always reuse the same idempotency key, and make `insert_paid_invoice_from_stripe` refuse to mint a second local invoice for an already-bound obligation.
4. **SAVEPOINT the in-tx accounting hooks (Finding 4)** so ledger failures are one deliberate, logged policy instead of two contradictory ones.
5. **PAYG parity + bank-line classification (Findings 5-6):** persist `needs_review` PAYG periods instead of rolling back, and classify or suspense bank statement lines rather than forcing every payment into operating expense.

## SM8 — Enterprise & Compliance (enterprise, compliance)

**Verdict:** Both crates have clearly been through prior security audits and most classic enterprise/compliance vulns are already fixed — SAML verification enforces whole-document signature binding, atomic InResponseTo consumption, per-tenant replay guards and fail-closed expiry; OIDC uses PKCE + atomic GETDEL state + RS256-only JWKS validation + email-domain assurance; outbound federation is SSRF-guarded with DNS pinning; the audit log is a per-tenant hash chain with HMAC signatures, cross-process advisory locks and legal-hold-aware archival; GDPR erasure produces per-store certificates with statutory-retention disclosure via a monotonic legal archive. What remains is concentrated in three areas: (1) role granularity — the enterprise API's only authorization is `admin: bool` or tenant membership, which turns several security-control endpoints (a PHI decryption oracle, self-approvable data-access grants, BAA signing) into any-member operations; (2) asymmetry between hardened paths — the SAML flow lacks the email assurance the OIDC flow has, and the GDPR-side retention job lacks the legal-hold filter the sweep has; (3) an audit-trail gap — the enterprise service itself never writes audit entries, and the compliance ingest endpoint has an argument bug that mislabels every entry. The root-level `compliance/` directory is a dead, drifted standalone package.

**Findings:**

1. **[P1] PHI decryption oracle: `/compliance/encryption/decrypt-field` needs no admin and writes no audit entry** — `services/mail-server/crates/enterprise/src/routes.rs:2401-2444`. The comment says "for testing/migration tooling", but the route ships on the production router (routes.rs:752) gated only by `verify_tenant_access` — i.e. *any* tenant member, viewer role included, not `require_admin` (compare `template_approve`, routes.rs:3276-3286, which does check). The tenant-AAD binding limits cross-tenant oracle use but nothing stops a low-privilege insider from bulk-decrypting every ciphertext of their own tenant (PHI fields, per `field_encryption::PHI_FIELDS`), and the operation is completely unaudited. **Fix:** `require_admin(&auth)` + a mandatory `compliance.log_audit` entry per call (actor, field_name, tenant), or move to a non-routable tooling binary.

2. **[P1] SAML path skips the OIDC email-domain/verification assurance → JIT account-linking hijack** — `services/mail-server/crates/enterprise/src/routes.rs:1844` + `sso.rs:1439-1448`. `let email = attribute("email").unwrap_or_else(|| validated.name_id.clone());` The OIDC flow requires a syntactically valid email, `email_verified` when present, and `email_belongs_to_sso_domain` (sso.rs:1251-1273, 599-622). The SAML ACS applies *none* of these: the asserted email (or raw NameID) goes straight into `resolve_or_provision_sso_user`, whose first-link fallback runs `SELECT ... FROM users WHERE tenant_id = $1 AND LOWER(email) = LOWER($2)` (sso.rs:1439-1448) and binds the SSO identity to that account, inheriting its role — `admin`/`owner` then yields canonical scopes `["*"]` (sso.rs:506-509). A SAML IdP (or anyone controlling an account on a mis-scoped IdP) asserting `victim@anydomain.com` takes over any same-tenant local account that never opted into SSO. The NameID fallback also provisions `users` rows whose `email` is an opaque string, not an address. **Fix:** in `sso_saml_acs_inner`, run `valid_oidc_email(email)` + `email_belongs_to_sso_domain(&email, &config)` and refuse on failure; treat opaque NameIDs as `external_user_id` only.

3. **[P1] Data-access approval has no separation of duties, no state guard, plaintext grant token** — `services/mail-server/crates/enterprise/src/routes.rs:2196-2232` + `compliance.rs` (`approve_data_access`). The route checks only tenant ownership (`guard_resource_tenant`); it does not require admin, does not check `approved_by != requester_id`, and the SQL has no `AND status = 'pending'` — a tenant member can file a request (`compliance_data_access`, routes.rs:2172) and then *self-approve* it, minting themselves a time-boxed access token; a completed/expired request can be re-approved to refresh the token. The raw `access_token` is also stored verbatim, unlike SSO bearer tokens which persist only a SHA-256 digest (sso.rs:1349-1353). **Fix:** require admin or approver≠requester, add `AND status='pending'` to the WHERE, store only a digest and return the raw token once.

4. **[P2] GDPR-side `enforce_retention` purges without the legal-hold filter the sweep enforces on the same table** — `services/mail-server/crates/compliance/src/gdpr_automation.rs:2032-2061`. `RetentionSweeper::run_sweep` purges `gdpr_exports` and `dsr_verification_outbox` through `purge_with_hold_filter` honoring `tenants.legal_hold` (retention_sweep.rs:294-310, 726-756), and `AuditLogger::archive` excludes held tenants as "evidence spoliation" (audit_logger.rs:849-876). But `GdprAutomation::enforce_retention` deletes `gdpr_exports` and withdrawn `consent_records` with no hold exclusion — and both jobs run as crons (`compliance/src/bin/server.rs:321` and `:351`). A held tenant's SAR exports (evidence of what was disclosed) and consent history can be destroyed by the GDPR job, defeating the hold. The DSR erasure path likewise never consults `tenants.legal_hold` (gdpr_automation.rs:900-934 → `erase_store`), while the sweep treats the flag as an absolute skip. **Fix:** route all deletions through one hold-aware predicate; at minimum apply the `tenant_id <> ALL(held)` filter in `enforce_retention` and make `process_erasure_request` consult the hold (defer to `pending_manual_review` like rectification).

5. **[P2] `POST /audit` passes tenant_id as `resource_id` and trusts body-supplied actor ids** — `services/mail-server/crates/compliance/src/routes.rs:572-583`. `AuditLogger::log`'s signature is `(action, resource, resource_id: Option<&str>, details, ...)` (audit_logger.rs:168-177) — so every ingested entry records `resource_id == tenant_id`, and the body's actual `resource_id` is never even parsed (lines 513-535 parse only action/resource/tenant_id). Downstream queries like the SAR export's `resource_id = $1` match (gdpr_automation.rs:802-805) silently rely on this coincidence. Additionally, `ctx.user_id` is taken verbatim from the request body (routes.rs:557-560), while the same file's own policy — `extract_caller_id`, routes.rs:222-238 — states client-supplied ids must be stored as `claimed_user_id:`-prefixed and "never mistaken for an authoritative actor"; that treatment is applied on the secrets endpoints but not on the audit ingest. The tamper-evident trail can therefore carry forged actor attributions. **Fix:** parse and bind the body's `resource_id`; wrap body user ids with the `claimed_user_id:` prefix.

6. **[P2] Canonical console session hardcodes 8h, ignoring `session_duration_hours`** — `services/mail-server/crates/enterprise/src/sso.rs:1558-1559`. The comment contradicts the code: `issue_sso_session` sizes the enterprise row from `config.session_duration_hours` (sso.rs:1341-1347), but `mint_canonical_session` always emits an 8h `am_session` JWT/cookie. A tenant configuring 1h SSO sessions still gets 8h console cookies (privilege window 8× policy); a 24h configuration is silently cut to 8h. **Fix:** thread `session_hours` into `mint_canonical_session` and derive `expiry_secs` from it.

7. **[P2] The enterprise service never audits its own sensitive actions** — `services/mail-server/crates/enterprise/src/compliance.rs:290-307`, `routes.rs:733`. The only writer to `ent_compliance_audit_logs` is the client-driven `POST /compliance/audit` endpoint; no server-side code path calls `log_audit`. Unaudited: SSO reconfiguration (`sso_configure`, sso.rs:689-721 — admin-only, but only a tracing `info!`), SSO session issuance (sso.rs:1378-1385), BAA/DPA signing (routes.rs:2051, 3681), zero-retention enablement (routes.rs:2072 — directly changes purge behavior), sub-account API-key minting (routes.rs:2954), contract signing/counter-signature (routes.rs:1353-1399), `decrypt_field` (finding 1). For tenants marketed HIPAA/SOC2 controls, the audit trail exists only if upstream clients remember to post entries. **Fix:** emit `log_audit` calls inside these handlers (server-derived actor/ip, as `compliance_log_audit` already demonstrates at routes.rs:2094-2139).

8. **[P2] Enterprise RBAC is binary admin/tenant; JWT scopes are ignored** — `services/mail-server/crates/enterprise/src/routes.rs:104-131, 205-211`. `JwtClaims` decodes only `sub`, `tenant_id`, `admin: bool` — the canonical JWT's `scopes` vector (minted per role in sso.rs:506-547) is never read. Authorization for every non-admin-gated endpoint reduces to "any member of the tenant": enable compliance frameworks (routes.rs:2020), sign the BAA (2051), toggle zero-retention (2072), rewrite whitelabel config including `custom_css` (3358), create/delete log-stream destinations (2448+), allocate dedicated IPs (2671). Only four actions (`sso_configure`, `template_approve`, `sso_cleanup_sessions`, contract counter-sign) demand admin. A viewer-role console session carries the same enterprise-API authority as an owner except for those four. **Fix:** decode `scopes` in `auth_middleware` and require per-route scope strings (e.g. `compliance:write`, `security:write`) for control-plane mutations.

9. **[P3] Root-level `compliance/` is a dead, drifted duplicate** — `/Users/sabelakhoua/IdeaProjects/ApexMail/compliance/`. It is a standalone package `apexmail-canonical-config` with its own `Cargo.lock`, not a member of any workspace (no root `Cargo.toml`; `services/mail-server/Cargo.toml` members list only `crates/compliance`), and nothing in the repo depends on it. `src/lib.rs` declares only `pub mod legal_entity;` — `customer_evidence.rs`, `final_checklist.rs`, `metrics_activation.rs` are undeclared dead files — and `legal_entity.rs` has drifted from the live copy at `services/mail-server/crates/compliance/src/legal_entity.rs` (38 vs 25 `pub const`s; root has `GENERAL_EMAIL`, crate has `CONTACT_EMAIL`, root `PHONE: "+372 (TBD)"`). **Fix:** delete it, or reduce it to a doc pointer at the crate copy.

10. **[P3] Data residency is configuration theater** — `services/mail-server/crates/enterprise/src/config.rs:262-264, 485-494`. `data_residency` / `data_residency_regions` are parsed from `DATA_RESIDENCY` / `DATA_RESIDENCY_REGIONS` and then never read by any code path in either crate (verified by grep — zero non-config references). No routing, pinning or replication constraint exists, while `compliance/src/claims_registry.rs:128` advertises `docs/compliance/data-residency.md` as public evidence. **Fix:** either wire the setting into request routing/storage selection or remove it and the claim before it's cited in a DPA.

11. **[P3] Unauthenticated SSO login initiators write unbounded staging rows; domain lookup is case-sensitive** — `services/mail-server/crates/enterprise/src/routes.rs:139-156`, `sso.rs:747-749, 794-804`. `/sso/login/:*` is exempt from `auth_middleware` (fine — protocol requirement) but each call INSERTs a row into `ent_saml_authn_requests` / `sso_oidc_state` with no rate limit; rows live 10 minutes and the sweep runs hourly (`bin/server.rs:123-137`), leaving ~6 unbounded windows of DB-row bloat per spam run. Separately, `get_config_by_domain` uses exact `WHERE domain = $1 AND enabled = true` while email checks lowercase (`email_belongs_to_sso_domain`, sso.rs:599-604) — a configuration saved as `Example.com` is unreachable via `example.com` RelayState and silently breaks the flow. **Fix:** per-IP rate limit on the initiators; `WHERE LOWER(domain) = LOWER($1)`.

12. **[P3] Anonymous trust-portal access requests have no rate limit** — `services/mail-server/crates/compliance/src/admin_routes.rs:127` + `trust_portal.rs` (`submit_access_request`). `POST /trust/access-request` is intentionally public, but the only validation is `input.requester_email.contains('@')` before an unconditional INSERT into `trust_portal_access_requests` — an unauthenticated row-spam vector into the compliance database (the DSR endpoints, by contrast, have a full two-level rate limiter, routes.rs:1033-1076). **Fix:** reuse the DSAR limiter pattern (per-IP + global cap) and validate email shape/length.

**Top 5 improvements:**
1. Close the self-service control plane: `require_admin` + audit on `decrypt_field`; separation-of-duties, pending-state guard and digest-at-rest on `approve_data_access` (findings 1, 3).
2. Port the OIDC email assurance (`valid_oidc_email`, `email_verified`, `email_belongs_to_sso_domain`) into the SAML ACS path so both federations share one identity-trust bar (finding 2).
3. Centralize deletion authority behind one legal-hold-aware predicate used by the sweeper, `GdprAutomation::enforce_retention`, and DSR erasure — today the same `gdpr_exports` table is purged under three different rules (finding 4).
4. Make the enterprise service emit its own audit entries for security-relevant mutations (SSO config, session issuance, BAA/DPA, key minting, zero-retention, decryption), and fix the `audit_create` `resource_id` argument bug + claimed-actor prefixing (findings 5, 7).
5. Decode and enforce JWT `scopes` in the enterprise `auth_middleware` (fine-grained RBAC instead of admin/tenant boolean), and delete the dead root `compliance/` package (findings 8, 9).

## SM9 — AI Services (ai-service, ai-embeddings)

**Verdict:** Both crates are far above average for LLM-served Rust: provider calls carry builder-level AND per-request timeouts with a fallback floor, the API key is redacted in Debug and never logged, provider error bodies are truncated before echoing, service auth is per-workload + timing-safe + fail-closed in production, `/chat` enforces header-vs-body tenant equality, tools are RBAC'd and tenant-isolated with the caller identity taken from a `TrustedToolCaller` (never the model), retrieval uses bound `plainto_tsquery`, and no `unwrap()`-on-model-output panic vector exists on live paths (the 13 in verifier.rs are all `Lazy` static-regex constructors or post-match `cap.get(0)`). The real problems are (1) the one live generative path (`/chat`) returns and persists the raw model answer with **no HTML sanitization at all** — the entire XSS-stripping layer exists only in dead code, and the verifier only catches entity-encoded XSS; (2) two of the most security-critical components — the 1,335-line tool-loop pipeline and the 1,634-line email answering agent — are **never wired into any binary**, so their carefully-built defenses protect nothing while their latent flaws (unsanitized streamed tokens, raw attacker `from`/`subject` embedded into stored drafts, a canned success on generation failure) ship silently; and (3) the embedding pipeline trusts sidecar response cardinality and lets NaN vectors through `l2_normalize`. No fabricated-AI-output problem on live paths — disabled runtimes fail closed with honest escalations (chat.rs:306-321), and `predict` refuses rather than fabricates.

**Findings:**

1. **[P1] Live `/chat` path returns and stores raw model output with no output sanitization** — `chat.rs:440-448`, `chat.rs:465-484`, `chat.rs:521-535`; `verifier.rs:450-456`. After `verify_grounded` passes, `build_response(req, answer, ...)` returns `answer` verbatim and `persist_audit` writes it to `ai_chat_messages`. The pipeline's sanitizer (`sanitize_llm_output`, pipeline.rs:533) is only invoked in dead code, and the verifier's only XSS check is `HTML_XSS_RE` matching **entity-encoded** payloads (`&#x?...;? (script|iframe|...|javascript)`) — a raw `<script>alert(1)</script>` or `<img src=x onerror=...>` in the answer matches none of the verifier's rejection rules and is returned to the control plane and persisted, later re-served by `/admin/chat/history` (routes.rs:681-710). The crate's own doc comments claim "Sanitizer: strip XSS/injection from the model output" is a pipeline stage — on the live path it does not exist. A prompt-injection that survives the input defenses (blocklist-based, defense.rs) and yields HTML output becomes stored XSS in whatever surface renders the answer. Fix: run `defense::sanitize_llm_output` — better, the ammonia allowlist from content.rs:156-226 — on every answer in `build_response`, before both the response and the audit write, and add raw-tag patterns to the verifier's rejection set.

2. **[P2] Output sanitizer is detect-then-strip: the stripper runs only when a *different* detector regex fired** — `defense.rs:706-736` (`if modified { output = strip_dangerous_html_tags(raw); }`). `XSS_PATTERN_RE`/`CSS_INJECTION_RE`/`HTML_ENTITY_XSS_RE` decide whether stripping happens, but `strip_dangerous_html_tags` has its own, different pattern set (`<style>`, `<base>`, `<form>`, `<input>` are stripped but not detected). Any vector the detectors miss (e.g. `@import 'http://…'` without `url()`, which `CSS_INJECTION_RE` doesn't match) passes through completely untouched — the stripping layer adds zero protection exactly when detection fails, i.e. against novel payloads. Fix: make stripping unconditional (it's a regex-substitution pipeline; running it on clean text is a no-op) or replace the whole thing with the ammonia allowlist already vendored in this crate (content.rs:165-225) — an allowlist cannot be bypassed by pattern novelty.

3. **[P2] `sanitize_ai_output` is a dead config knob** — `config.rs:41-42`, `config.rs:147-150`. Parsed from `AI_SANITIZE_AI_OUTPUT`, validated, defaulted `true`, and consumed by **nothing** (grep over both crates: zero readers outside config.rs). Operators setting it `false` believing they control sanitization are configuring a no-op; operators leaving it `true` believe output is ammonia-sanitized ("Whether to sanitize AI-generated HTML output with ammonia") when no live path sanitizes at all. This is exactly the "feature-gated path that silently no-ops" class. Fix: wire it to the ammonia pass in finding 1, or delete the field.

4. **[P2] `embed_batch` never validates sidecar response cardinality or index completeness** — `embeddings.rs:112-147`. After `response.json()`, vectors are collected by `e.index`, sorted, dimension-checked per vector — but `vectors.len() == texts.len()` is never checked, nor that indices are exactly `0..n`. A sidecar that returns 255 embeddings for 256 inputs, duplicates an index, or drops one produces a silently misaligned batch: `/embed` (routes.rs:163-171) answers 200 with `count: 255`, and any caller zipping `texts` with `embeddings` (or storing chunk i's text with chunk i's vector in the vector store) corrupts tenant data with no error anywhere. `embed()` (embeddings.rs:76-79) similarly takes `results.into_iter().next()` regardless of what was requested. Fix: after the dimension loop, `if vectors.len() != texts.len() { return Err(InferenceError(...)) }` and reject non-contiguous indices.

5. **[P2] `l2_normalize` passes NaN/±Inf vectors through unnormalized** — `embeddings.rs:155-163`. `if norm > f32::EPSILON { … }` is false when `norm` is NaN (all comparisons with NaN are false), so a vector containing NaN components is returned **with its NaNs intact**; +Inf components give inf/inf = NaN after division. The vector store re-guards at ingest (`has_non_zero_norm` requires `norm.is_finite()`, vector_store.rs:52-55), but the HTTP `/embed` endpoint returns these vectors directly to callers (routes.rs:163-171), whose own cosine/ranking math then propagates NaN — and NaN scores make heap comparisons in `VectorStore::search`-style top-K silently unordered. A misbehaving/hostile sidecar response poisons downstream rankings instead of erroring. Fix: reject non-finite components (or non-finite norm) with `InferenceError` inside `embed_batch`, next to the dimension check.

6. **[P2] ai-embeddings tenant isolation is caller-asserted behind one shared token** — `routes.rs:179-199` (`/vectors`) and `routes.rs:201-222` (`/search`); `auth.rs:31-41`. `tenant_id` arrives in the request body from any holder of the single `AI_EMBEDDINGS_AUTH_TOKEN`; there is no per-caller identity and no binding of tenant to credential, so any compromised internal caller can write vectors under — or read another tenant's stored chunk text via — any `tenant_id` it names. The repo's own standard (ai-service routes.rs:580-618 "P1-SECURITY: … a holder of the universal internal token must not be able to … act as that tenant") is not met here; currently no in-repo caller exists (api-server loads the token but never calls the service), which makes this a design-time fix before first integration. Fix: adopt the ai-service pattern — require a validated `x-apexmail-tenant-id` header set by the gateway after its own authorization, and (like ai-service) make its absence a 401 rather than trusting the body.

7. **[P2] The two most security-sensitive components are dead code with latent flaws** — `routes.rs:742-763` (router list), `bin/server.rs` (no other wiring). `AiPipeline` (pipeline.rs, incl. the tool-execution loop) and `EmailAnswerer` (email_agent.rs poll loop) are referenced only by their own tests. Latent defects that will bite the day someone wires them: (a) pipeline.rs:414-427 — in the streaming path a generation **error** is swallowed and the partial accumulated text `c` proceeds as the response (`Err(_) => c`), skipping the retry ladder the non-streaming path has, so a truncated answer can pass verification and ship as success; (b) pipeline.rs:419-422 — streamed tokens are `tx.try_send`'d to the client **unsanitized**; sanitization happens only on the reassembled final string (pipeline.rs:533), so any stream-consuming consumer sees raw model output; (c) email_agent.rs:1117-1140 — `format_reply` embeds the *unsanitized* `from` and `subject` into the stored draft (`"On {}, {} wrote:"`, `"> Subject: {}"`) while only the AI response goes through `sanitize_email_body` — attacker-controlled header text re-enters the stored body that the approval control plane later releases; (d) email_agent.rs:1166-1181 — `generate_email_reply` converts LLM failure into a 200-shaped canned `response` string, so a caller cannot distinguish failure from a real (fake) answer except via `tokens_used: None`. Fix: either delete both modules or wire them and fix a-d; keeping 3,000 lines of unwired "hardened" agent code is a standing trap (and its guarantees mislead review, as they did the crate docs).

8. **[P3] Chunker offsets do not reference the source document** — `chunker.rs:162-171` with `chunker.rs:103-107`. `recursive_split` merges parts *with* their separators (`format!("{}{}{}", current, sep, part)`), but `merge_with_overlap` advances `offset += chunk.len()` counting only chunk bytes; `end_offset = start_offset + text.len()` further includes prepended overlap bytes. Published `start_offset`/`end_offset` therefore drift from true document positions (separators uncounted, overlap counted) — any downstream highlight/quoting feature built on them points at the wrong text. Tests only assert monotonicity (chunker.rs:249-264), not correctness. Fix: compute offsets from the split structure (track separator lengths) and document overlap semantics.

9. **[P3] Character-fallback split treats the byte cap as a char count** — `chunker.rs:79-85`. With no separators left, `text.chars().collect::<Vec<_>>().chunks(max_size)` chunks by **chars**, so for CJK/emoji each "chunk" can be 3-4× `max_size` **bytes**; `merge_with_overlap` then byte-truncates it (chunker.rs:158-160), silently discarding up to three-quarters of that chunk's tail with no truncation marker. Non-ASCII-heavy documents lose content and generate more chunks than configured. Fix: chunk by accumulated `char.len_utf8()` against the byte budget.

10. **[P3] Provider API key may transit plaintext HTTP** — `config.rs:177-181` explicitly allows `http://` endpoints; `inference.rs:358-359` attaches `bearer_auth(api_key)`. Justified for the default local sidecar (`http://127.0.0.1:8081/v1`), but nothing prevents a non-local `http://` endpoint in production, unlike ai-embeddings which warns loudly when sidecar TLS is disabled (embeddings.rs:52-56). Fix: log a warning (or refuse, outside loopback) when a non-loopback `http://` model endpoint is configured with a non-empty `AI_MODEL_API_KEY`.

11. **[P3] NDJSON export/import double-buffers the full store in memory; eviction is O(N log N) per insert** — `vector_store.rs:254-264` (export writes every line to `writer` AND accumulates `data_bytes`), `vector_store.rs:295-320` (import collects all lines before parsing), `vector_store.rs:393-407` (`evict_lru` collects and sorts **all** entries on *every* `add` past the threshold). At `max_vectors` in the 100k range a snapshot restore/export briefly holds ~2-3× the store's serialized size, and sustained ingestion past the eviction threshold pays a full sort per insert (amortized eviction of one victim per insert). Fix: stream the export through an `Hmac` core (`Mac::update` in chunks) instead of a shadow buffer, parse import line-by-line after HMAC finalization, and batch evictions (evict 10% once per threshold crossing rather than per insert).

**Top 5 improvements:**
1. Sanitize every model answer on the live path before return *and* audit persistence (ammonia allowlist, unconditional) — closes findings 1, 2, 3 at once.
2. Decide the fate of `pipeline.rs` and `email_agent.rs`: wire them (after fixing the four latent flaws in finding 7) or delete them; unwired "hardened" agent code is the biggest liability in the crate.
3. Harden the embedding contract against a misbehaving sidecar: cardinality/index validation and finite-component rejection in `embed_batch`.
4. Move ai-embeddings to gateway-asserted tenant identity (header required, body value cross-checked) before the first internal caller integrates.
5. Fix chunker offset bookkeeping and the byte/char cap mismatch so downstream consumers can trust `start_offset`/`end_offset` and non-ASCII documents stop losing chunk tails.

## SM10 — Platform Services & Workers (analytics, observability-service, ha, devex-service, worker-processors, edge-cases)

**Verdict:** This is the most defensively-engineered sub-module I have audited in this workspace — worker-processors uses lease-token-fenced claims (`claim_token`/`metadata.lease_token` predicates on every completion write), SKIP LOCKED everywhere, SSRF-pinned webhook delivery, allowlisted dynamic SQL, and per-workload auth in devex; non-test `unwrap/expect/panic` count is near zero and every one is a documented invariant. The real risk is concentrated in two places: (1) the **ha crate is a metadata simulation of high availability** — automatic failover has zero production callers, `initiate_failover` never promotes a standby or repoints clients, and STONITH fencing is only enforced on the HA service's own HTTP routes, not the data plane; and (2) **supervision is blind to panics** — a single panic in a processor loop permanently kills that processor while the heartbeat, `/health`, and `/metrics` all stay green. Secondary issues: analytics buffer-cap evictions corrupt counts in both directions, a nightly-task retry bug that silently degrades to once-per-day, and task leaks on processor restarts.

**Findings:**

1. **[P1] A panic permanently kills a supervised processor with no restart and no signal** — `worker-processors/src/bin/worker.rs:39-44` — `match start().await { Ok(()) => … return, Err(e) => { …restart… } }`. `supervise` only handles `Err`; a panic unwinds through `start()` → `supervise` → kills the spawned task (`bin/worker.rs:404-410`), and the `JoinHandle`s are only awaited at shutdown (`bin/worker.rs:623-629`), never monitored. Meanwhile the heartbeat task (`bin/worker.rs:361`) and the health/metrics server (`bin/worker.rs:563-577`, `/health` → `"OK"`) keep running, so Kubernetes and the control plane see a healthy worker delivering nothing. A concrete in-path panic source exists: `worker-processors/src/webhook/processor.rs:627` — `.expect("pinned webhook client construction cannot fail …")` inside `deliver_webhook`. Impact: silent total or partial outage of email/webhook/analytics processing until container restart. Fix: wrap the `start()` future in `FuturesUnordered` monitored by a supervisor that also polls the `JoinHandle` (or use `catch_unwind` on `AssertUnwindSafe`), emit `apexmail_processor_dead{processor=…}` and stop the heartbeat capability entry when a task dies.

2. **[P1] Automatic failover is dead code — nothing ever calls `report_failure`** — `ha/src/failover.rs:129-171` — `pub async fn report_failure(&self, component: &str) … if count >= self.config.failover.threshold { … initiate_failover(FailoverType::Automatic, …) }`. A workspace-wide grep finds **zero** production callers (only `#[cfg(test)]` modules). The health cron in `ha/src/bin/server.rs:126-134` merely does `tracing::warn!(… "Health check reported non-healthy state")`. So the entire threshold → Detecting → initiate pipeline, including the carefully tested per-component counter isolation (B.6), never executes. Impact: a failed primary is never failed over automatically; the "HA" service is a dashboard. Fix: in the health cron, map each `Unhealthy` component to `failover.report_failure(component)` and `Healthy` to `reset_failures_for(component)` (with flap damping), or delete the automatic path and its config to stop implying it exists.

3. **[P1] `initiate_failover` promotes nothing — it swaps metadata and declares victory** — `ha/src/failover.rs:192-325` — the body acquires the lock, probes a target, fences the old primary in Redis, writes claims/events, sets `*p = target` … and never executes a promotion or repoints any client. Actual `pg_promote` exists only as a separate manual HTTP route (`ha/src/routes.rs:139` → `replication_promote` → `ha/src/replication.rs:161-169` `SELECT pg_promote(wait := true)`), unconnected to the failover state machine. The emitted event says `state: "completed"` with `to_node` promoted (`failover.rs:276-294`) while every api-server/worker keeps writing to the configured `DATABASE_URL` primary. Impact: an operator running `/api/v1/failover/initiate` gets `FailedOver` state and audit events describing a topology change that never happened; worse, if someone later runs the promote route manually, fencing order and lag verification are bypassed. Fix: either execute promotion (via the replication service) inside the locked failover sequence and repoint consumers (or front them with a proxy that reads the Redis primary claim), or rename this to a planning/dry-run API and stop writing `state: "completed"`.

4. **[P1] STONITH fencing is advisory — enforced only on the HA service's own HTTP routes** — `ha/src/failover.rs:800-827` — `ensure_not_fenced` … consulted solely by `fence_guard` in `ha/src/routes.rs:73-105`. No data-plane service (api-server, worker-processors, mta) references `ha:fenced:*` or `ha::failover` at all (grep confirms). During failover the "fenced" old primary keeps accepting API traffic and mail writes through its own processes; the Redis key only makes the HA server on that node return 503. The comment "Every write-acceptance point in this service refuses to serve" (`failover.rs:748-750`) is true only of the HA service itself. Impact: the split-brain window the fencing was built to close remains wide open at the layer that matters. Fix: enforce the fence where the writes happen — a middleware/gate in api-server and worker claiming that checks the node's fence key (or better, a Postgres-side mechanism: revoke role/pg_hole, or make writes fail via a fencing token checked in-transaction).

5. **[P2] `resolve_split_brain` neither fences the losers nor takes the lock** — `ha/src/failover.rs:513-555` — doc says "Resolve split-brain by fencing all but one node", but the body just `DEL`s every `ha:primary:*` claim and `SET`s the winner (`failover.rs:523-542`); no `ha:fenced:*` keys are created for losers, no `try_acquire_lock`. A loser node's in-memory state machine still thinks it is primary (only `resolve_split_brain`'s caller on THIS node updates `self.primary_node`), and it is never fenced, so it keeps acting — the exact split-brain the function claims to resolve. No lock means two concurrent resolves can interleave DEL/SET freely. Impact: the documented recovery path does not recover; it re-labels. Fix: acquire the failover lock, `fence_node()` every claim-holder except the winner, and only then rewrite claims; notify losers (they already fail-closed on `ensure_not_fenced` once fenced).

6. **[P2] Failover lock TTL is 60 s with no renewal; the work under it can exceed it** — `ha/src/failover.rs:16` (`const FAILOVER_LOCK_TTL: u64 = 60`) and `try_acquire_lock` at `failover.rs:676-710` (plain `SET NX EX`, no extension). Between acquire and release, `initiate_failover` runs `select_failover_target` probing each replica via `verify_replication_lag` on the shared pool (`failover.rs:477-487`) with no per-probe timeout, plus Redis and DB writes. Under a degraded DB (the very condition that triggers failover), probes can stall past 60 s; the lock lapses, a second coordinator acquires it, and both mutate claims/fences concurrently — the compare-and-delete release (`failover.rs:721-737`) correctly protects the lock itself but nothing serializes the side effects already in flight. Fix: renew the lock (watchdog loop) for the duration, and cap each replica probe with `tokio::time::timeout`.

7. **[P2] `detect_split_brain` has a built-in false-positive window during legitimate failover** — `ha/src/failover.rs:257-263` — `claim_primary(&target)` runs **before** `release_primary_claim(&current_primary)`, so two `ha:primary:*` keys legitimately coexist inside the locked sequence; `detect_split_brain` (`failover.rs:499-509`) counts keys via SCAN and sets `FailoverState::SplitBrain` on `keys.len() > 1` with no regard for the lock. A detection pass racing the failover wedges the state machine: `initiate_failover` then refuses (`failover.rs:212` `Cannot initiate failover in state: split_brain`) until someone runs the (broken, finding 5) resolve endpoint. Fix: have detection skip the window by checking the failover lock first, or compare-and-release the old claim atomically with claiming the new one (Lua), or tag claims with epoch and ignore claims older than the lock.

8. **[P2] Analytics buffer-cap evictions corrupt counts in both directions** — `worker-processors/src/analytics/processor.rs:249-257` — `if buffer.len() > MAX_EVENT_BUFFER_SIZE { … buffer.drain(0..dropped); … "dropped oldest events" }`. The "dropped" events were already fed to `update_aggregation` (line 271-273 runs for every event regardless of the drain), their queue rows stay claimed, and `fetch_events` reclaims them after 10 minutes (`processor.rs:161-165` `OR processing_at < NOW() - interval '10 minutes'`) → they are re-aggregated and the additive upsert (`processor.rs:632-641` `DO UPDATE SET sent = analytics_hourly.sent + EXCLUDED.sent`) **double-counts** them. Mirror image at `processor.rs:365-387`: when the aggregation map exceeds 10 000 keys, entries are evicted permanently, yet `flush_buffers_inner` still marks ALL buffered event ids processed (`processor.rs:503-513`) → silent **undercount**. Both paths trade correctness for memory with only a `warn!`. Fix: on hitting either cap, force a synchronous flush first (the flush already restores buffers on failure), and only drop/evict if the flush itself fails — and never mark events processed whose aggregation was evicted.

9. **[P2] `EmailProcessor::start` leaks two background loops per supervised restart** — `worker-processors/src/email/processor.rs:1701-1713` and `1724-1744` spawn the queue-depth metrics task and the F25 reconcile sweep at the top of `start()`, before `transport.verify()` (line 1747) which is the main `Err` return. `supervise` (`bin/worker.rs:37-55`) calls `start()` again on every failure; the old loops only exit on `shutdown.changed()` (never fired by restart), so a flapping transport yields an unbounded pile of 15 s/60 s loops, each running `reconcile_stuck_parents` + the acceptance sweep against the DB. Fix: spawn these once in `new()`/a dedicated `spawn_background()`, or guard with a `Once`/AtomicBool, or tear them down when `start()` errors.

10. **[P2] analytics-worker nightly retry logic never retries sooner — it waits a full day** — `analytics/src/bin/worker.rs:149-154` — `Err(e) => { error!(…); sleep(backoff); backoff = backoff_after_failure(backoff); continue; }` with the comment "skip the long sleep, retry sooner". But `continue` re-enters the loop whose first act is recomputing `next_scheduled_time(now, target_hour)` → tomorrow 02:00 and sleeping ~24 h (`worker.rs:123-132`). The exponential backoff (and its test at `worker.rs:344-353`) is dead in effect: a failed nightly compaction is retried once per day while the hot `events` table keeps growing. Fix: on failure, loop directly back to the `worker.run()` attempt (inner retry loop honoring the backoff), only returning to the scheduler after success or cap.

11. **[P2] HA's destructive endpoints accept the universal internal key** — `ha/src/routes.rs:53-61` — `check_api_key` passes on `timing_safe_compare(key, &config.internal_api_key) || timing_safe_compare(key, &config.admin_api_key)`. That authorizes `/api/v1/failover/initiate` (`routes.rs:226-233`), `/api/v1/replication/promote` (`routes.rs:547-556`), backup restore, and chaos-experiment start (`routes.rs:960-963`) with the same secret every internal service holds — the exact pattern the devex crate migrated away from (`devex-service/src/auth.rs:1-21` documents the per-workload rationale and refuses the universal token in production). Fix: require `admin_api_key` (distinct compare, still timing-safe) for failover/promote/restore/chaos, and adopt the devex per-workload pattern.

12. **[P3] `fence_guard` is the outermost layer — it runs before auth** — `ha/src/routes.rs:171-176` — the layer order (last added = outermost) means a mutating request from an unauthenticated caller gets the fenced-node 503 body ("node is fenced — writes refused", `routes.rs:90-100`) instead of 401, leaking fence state to anyone who can reach port 4300. Fix: move `fence_guard` inside the auth layer (add it per-route-group after auth).

13. **[P3] Alert-dispatch failures log the full webhook URL** — `observability-service/src/alerting.rs:151-161` — `webhook_url = %url` in both the non-2xx and transport-error arms. Operators routinely put tokens in query strings (`https://hooks.example/x?key=…`); those end up in JSON logs. The same discipline is already applied elsewhere in this crate (`bin/server.rs:329-336` redacts Redis URL credentials with `redact_url_credentials`). Fix: redact userinfo/query before logging, mirroring `redact_url_credentials`.

14. **[P3] `aggregate_by_dimension` percentages are relative to the top-100 subtotal** — `analytics/src/clickhouse_engine.rs:440-454` — the query has `GROUP BY dimension ORDER BY count DESC LIMIT 100` and then `let total: u64 = rows.iter().map(|r| r.count).sum();` with `percentage = r.count / total * 100.0`. When a dimension has more than 100 distinct values, percentages are inflated (they sum to 100 % over the top 100 instead of the true total). Fix: run a parallel `count()` over the same WHERE for the denominator, or return `percentage_of_top` and document it.

15. **[P3] `LogAggregator` worst-case memory is ~GBs** — `observability-service/src/log_aggregator.rs:36-39` (`with_capacity(500_000)`) with `ingest` storing full `LogEntry`s whose `context`/`metadata` maps are stored verbatim from the ingest route (`routes.rs:378-384`; only `message` is truncated to 10 000 chars at `routes.rs:371`, `MAX_LOG_INGEST_MESSAGE_CHARS` at `routes.rs:224`). With the 2 MB body limit and 1 000-entry batch cap (`routes.rs:220,115`), each entry can carry ~2 KB of untruncated maps → 500 k × ~2 KB ≈ 1 GB resident before eviction kicks in (eviction itself only drops 10 % per insert, `log_aggregator.rs:69-72`, and `Vec::drain` never shrinks allocation). Fix: cap `context`/`metadata` size at ingest and use a ring buffer / `shrink_to_fit` on eviction.

16. **[P3] edge-cases is a deployed 6.8 k-line service with no production consumers** — `edge-cases/src/lib.rs` exposes it as a real HTTP service (auth fail-closed at `routes/mod.rs:31-44`, 10 MB body limit, MX/greylist/autoresponder/loop heuristics in `services/delivery.rs`), yet the only workspace reference is `smoke-tests/tests/smoke_services.rs`. It duplicates SMTP-response classification, retry backoff, MX lookup, and loop detection that the MTA and email processor implement independently (`edge-cases/src/services/delivery.rs:200-272` vs worker's `classify_send_failure`) — behavior will drift, and its `calculate_retry_schedule` (`delivery.rs:252-268`: `greylist_retry_delay_secs`, `initial_delay_secs * multiplier^attempt`) is not the schedule the worker actually uses (`email/processor.rs:4036-4037` fixes 5-minute requeues). Fix: either wire it into the delivery path as the single classification source or delete the service; a classification oracle nobody consults is negative value.

17. **[P3] Reply handler claims a concurrency batch but processes it sequentially** — `worker-processors/src/reply_handler/processor.rs:337-355` — `for msg in messages { … self.process_message(msg).await … }` — `available` only caps the fetch; each message (classification, optional AI call) is awaited one at a time inside the loop, so effective concurrency is 1 regardless of `WORKER_CONCURRENCY`, and a slow AI call stalls every subsequent reply. Fix: `futures::stream::iter(messages).for_each_concurrent(available, …)` like the webhook processor (`webhook/processor.rs:130-136`).

**Top 5 improvements:**
1. **Make supervision panic-aware** (`bin/worker.rs`): monitor the processor `JoinHandle`s continuously, restart on `JoinError::is_panic`, export a `processor_alive` gauge, and drop the heartbeat capability when a processor is dead — today a panic is a silent full outage behind green health.
2. **Make the HA failover real or remove the pretense** (findings 2-4): wire the health cron into `report_failure`, execute/coordinate actual promotion under the renewed lock, and enforce fencing in the data plane; a metadata-only failover that records `state: "completed"` is worse than none.
3. **Fix `resolve_split_brain` to actually fence losers under the lock**, and close the claim/reclaim false-positive window (findings 5, 7) — both are cheap Lua/lock-ordering fixes to code that is otherwise carefully reasoned.
4. **Replace cap-eviction with forced flush in the analytics processor** (finding 8) so memory caps can never double-count or silently drop counted events; same treatment for the analytics-worker nightly retry loop (finding 10).
5. **Adopt the devex per-workload credential pattern in ha** (finding 11) and restrict failover/promote/restore/chaos to the admin key; move `fence_guard` inside auth (finding 12).

## SM11 — UI Foundation & Frontend (ui-foundation, apps/marketing-zola, templates/)

**Verdict:** This is an unusually disciplined zero-JavaScript SSR surface: hand-rolled Rust string templating (`leptos_views.rs` — no Leptos dependency, just format!) with a consistent `html_escape` discipline on auth pages, shells, sales views, and form-field replay; signed flash + confirmation cookies (HMAC-SHA256, TTL, size caps); CSRF double-submit injected into every `/web/*` POST form; a genuine allowlist sanitizer for campaign HTML preview; served CSP of `script-src 'none'`; no tokens in any storage; strong cache tiers with real Zola cachebust hashes; legal templates validated by a CI script. The one serious hole is that the `StatusIndicator`/`Badge` primitive renders unknown status strings **unescaped**, breaking the module's own "every variant is escaped" contract for DB-sourced columns (`event_type`, suppression `reason`, alert `severity`) — a latent stored XSS one unrecognized status value away. Secondary issues: a marketing-page normalization cache keyed effectively by document length alone (silent wrong-page-serving on collision), stale pricing claims in 3 of 4 locales of the Resend comparison page, dead/misleading CSP constants, and minor drift (indigo favicon, duplicated compiled stylesheets, dead config keys, stray empty `<label>` in the sales form).

**Findings:**

1. **[P1] Unknown status strings render unescaped — stored XSS sink on every data table** — `services/mail-server/crates/ui-foundation/src/primitives.rs:2063` and `primitives.rs:899-907`. The vocabulary map falls back `_ => (status, "secondary", DOT_OUTLINE)` — returning the *raw* status string as the badge label — and `Badge::render_html` interpolates it without escaping: `"...>{}<\/div>", ..., self.text` (line 906). This is reached from `DataCell::Status` (`view_data.rs:401-403`: `crate::primitives::StatusIndicator { status }.render_html()`), which the api-server feeds with raw DB VARCHARs: `DataCell::status(&event_type)` (`crates/api-server/src/routes/web/data.rs:1430` and `:1686`), `DataCell::status(&reason)` for suppressions (`data.rs:2338`), `DataCell::status(&severity)` (`data.rs:2731`). The module's own contract says the opposite — `view_data.rs:50-52`: "`Raw` cells are trusted, pre-escaped HTML …; every other variant is escaped at render time" (note: no `Raw` variant even exists; stale comment). Event types and suppression reasons are ingestion-sourced (provider webhooks), not a fixed enum; any future writer that stores markup in those columns fires XSS on the console list pages (mitigated only by the served `script-src 'none'` CSP — but attribute-breakout markup injection and `style-src-attr 'unsafe-inline'` remain). The only test covers a known status (`primitives.rs:3394-3402`). **Fix:** `html_escape(label)` inside `Badge::render_html` (or in the fallback arm), add a regression test with `status: "<img src=x onerror=alert(1)>"`, and delete the phantom `Raw` comment.

2. **[P2] Marketing page cache keyed by length + identical 64-byte prefix — colliding documents serve each other's content** — `services/mail-server/crates/ui-foundation/src/axum_router.rs:682-715`. `marketing_normalize_cache` keys on `(document.len(), first 64 bytes)`, with the comment "which uniquely identifies every document in the static set" — but I verified every built page starts with the same minified prefix (`public/index.html`, `public/cookies/index.html`, `public/de/index.html` all begin `<!doctype html><html class=scroll-smooth data-theme=apex dir=ltr…`), so the key degenerates to **document length alone**. Two Zola pages of equal byte length (one routine content edit away across 116+ embedded pages; the cache holds 32 entries) silently returns the *other page's fully normalized HTML* for this page's URL — wrong locale/legal/pricing content served with no error. No two pages currently collide (I checked all lengths), which is luck, not a guard. **Fix:** key on a hash of the full document (it's already in memory), or drop the memo — the normalization of ~116 static documents at startup or per-route-compile is trivial.

3. **[P2] Resend comparison page: 3 of 4 locales carry 4-month-stale pricing with drifted plan vocabulary** — `apps/marketing-zola/content/compare/resend/index.md:12` (`pricing_as_of = "2026-09-05"`, line 30: "…1 included on Growth, 3 on Business") vs `index.de.md:12` / `index.fr.md:12` / `index.es.md:12` (`pricing_as_of = "2026-05-09"`; `index.de.md:30`: "…1 enthalten ab Growth, 3 ab Scale"). "Scale" is the old plan vocabulary — current `data/pricing.json` names the `scale` id "Business". German/French/Spanish visitors see outdated pricing structure presented under the same comparison table, and the per-page verification date (rendered under the table via `templates/partials/compare/table.html:54`) is a stale 2026-05-09. **Fix:** CI gate failing when a compare page's locale variants' `pricing_as_of` diverge from the canonical variant, then re-translate the three pages.

4. **[P3] Console favicon is indigo while the brand is pinned red** — `services/mail-server/crates/ui-foundation/src/leptos_views.rs:39`: `FAVICON_SVG … fill="#4f46e5"` (indigo-600), rendered into every web/CP root layout via `favicon_link_html()` (`leptos_views.rs:88-93`, `:73`). `lib.rs:98-151` (`brand_palette_is_red_and_black`) pins `#dc2626` and explicitly asserts indigo values "must not appear" — the favicon escaped that purge and is the one indigo artifact users see on every tab. **Fix:** derive the favicon fill from the brand token (`#dc2626`) and add it to the palette pin test.

5. **[P3] Dead, misleading CSP constants that contradict the actually-served policy** — `services/mail-server/crates/ui-foundation/src/shell.rs:87-109`: `shell_csp_header()` returns `script-src 'self' 'strict-dynamic'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:` and `render_csp_meta_tag()` wraps it — **zero callers anywhere in the repo** (verified by grep; the api-server serves `script-src 'none'` via `browser_csp_header_with_sources`, `api-server/src/app.rs:964-974`). 8. **[P3] Duplicated compiled marketing stylesheets drifting** — `services/mail-server/crates/ui-foundation/baselines/rust-ui/css/styles.css` (89,951 bytes) vs `apps/marketing-zola/static/css/styles.css` (89,939 bytes), same for `input.css` (72,045 vs 72,033). (Also confusingly, `baselines/rust-ui/manifest.json` is a 70 KB visual-fixture manifest while `static/manifest.json` is the 322-byte PWA manifest — same filename, unrelated content.) **Fix:** regenerate baselines from the build in CI or make the parity test compare against the build output, not a committed copy.

9. **[P3] Confirmation-signature payload is delimiter-ambiguous** — `services/mail-server/crates/ui-foundation/src/flash.rs:161` and `:184`: `format!("{intent}:{resource_id}:{expires_at}")`. A token signed for `(intent="delete-campaign", id="c:1")` verifies for `(intent="delete-campaign:c", id="1")` since both produce `delete-campaign:c:1:<exp>`. Today's fixed intent vocabulary contains no `:` so it isn't exploitable, but the construction breaks the "a token for one action cannot be replayed against another" guarantee the doc comment (line 152-154) makes, the moment an id-bearing intent or a free-form id is introduced. **Fix:** length-prefix or HMAC over a serialized tuple (`serde_json` of `[intent, id, exp]`).

10. **[P3] Inconsistent `X-XSS-Protection` across the three marketing header copies** — `apps/marketing-zola/nginx.conf:46` sets `X-XSS-Protection "1; mode=block"` (the deprecated, in some legacy browsers attack-enabling value) while the api-server correctly pins `"0"` (`api-server/src/app.rs:793-794`) and `static/_headers` omits it. The nginx file's own comment mandates lockstep for CSP across the three copies; the XSS-protection header drifted the same way. **Fix:** set `"0"` (or drop it) in `nginx.conf` and the edge vhost.

1. 4. Consolidate security constants: delete or correct `shell_csp_header`/`render_csp_meta_tag`, and generate the three marketing CSP/header copies from one source — findings 5 and 10.
5. De-drift the duplicated artifacts: favicon fill from the brand token (added to the palette pin test), baseline stylesheets regenerated from the build, dead config/parity-doc references pruned — findings 4, 7, 8.

## SM12 — Test Suites (smoke, functional, integration, perf, fuzz, load + browser tests)

**Verdict:** This is a tale of two test estates. One estate is genuinely excellent: `schema_contract_tests.rs`, `core_security_tests.rs` (RBAC/XSS/webhook-signing), `functional_sales.rs`, the Playwright captcha suite (~219 tests, stable data-attribute selectors, `retries: 0`, local PHP router), and the k6 scripts (real VU stages, hard thresholds, baselines + a comparison script) show deliberate, audited engineering — including a soft-skip gate that panics in release CI (`migrator/src/lib.rs:154`) and a CI log-gate that fails a run containing skip markers. The other estate is manufactured green: roughly **130 of the ~427 Rust tests (30%) verify toy reimplementations defined inside the test files themselves, not production code** — an entire 851-line "stub detection" suite that is itself a stub, a "property-based" suite that properties over local copies, a "concurrency fixes" suite that re-types production SQL instead of calling it, an empty `load_isolation.rs` containing only a doc comment, and "perf" tests that measure discarded boolean comparisons. These suites inflate coverage numbers while guaranteeing that regressions in rate limiting, circuit breaking, wallet idempotency, SSRF protection, and tenant isolation pass CI. Critical paths with no direct tests here: billing HTTP endpoints (explicitly skipped), SMTP delivery/retry/bounce, SSO flows beyond serde, and the Redis-backed rate-limit path (the harness deliberately points Redis at an unreachable port so the in-memory fallback is all that's ever exercised).

**Findings:**

1. **[P0] Entire "Stub and Bug Detection" suite tests its own toys, zero production code** — `services/mail-server/crates/integration-tests/tests/stub_detection_tests.rs:45-47` — `let xfo = "DENY"; assert_eq!(xfo, "DENY", ...)`: compares a literal to itself. All 32 tests are like this: `TestRateLimiter` (l.91-112), `TestCircuitBreaker` (l.177-206), XOR "encryption" (l.338-343, "NOT cryptographically secure"), toy `HealthChecker` (l.253-277), toy `AuditLog` (l.416-458), toy `GracefulShutdown` (l.529-570), local `validate_email`/`has_null_bytes` (l.656-678), and `concurrency_bug_tests` that verify stdlib `AtomicU64`/`RwLock` (l.804-851). The header (l.8-9) claims "Each test verifies that the implementation actually performs its intended function" — nothing in the file imports a workspace crate. Impact: the file whose stated job is catching stubbed implementations is itself the largest stub in the repo; a rate-limiter or circuit-breaker regression is invisible to it. Fix: delete or rewrite every module against the real crates (`apexmail_rate_limiter`, `worker_processors::common::CircuitBreaker`, `apexmail_lib::crypto`, `apexmail_lib::validation`).

Impact: "property-based coverage" is fictional; e.g., the real `SlidingWindowCounter`'s window-rollover semantics have no property coverage at all. Fix: retarget each `proptest!` block at the production types and add the crate deps.

3. **[P0] "Concurrency race-condition fix" tests re-type the SQL instead of calling the fixed code** — `services/mail-server/crates/integration-tests/tests/concurrency_tests.rs:329-340` — the `INSERT ... ON CONFLICT (reference) ... DO NOTHING` claimed to validate "RC-TEST-01 admin_apply_credit idempotency" is hand-written inside the test, not a call to `billing_service`. 4. **[P0] `load_isolation.rs` is an empty promise — doc comment only, no tests** — `services/mail-server/crates/load-tests/tests/load_isolation.rs:1-12` — the entire file is a module doc promising noisy-neighbour verification ("Tenant B p50 ≤ 2× baseline ... tput ≥ 50% baseline") with thresholds, and contains not one `#[test]`. ## SM13 — Deploy & Runtime Infrastructure (deploy/, docker-compose*, Dockerfiles, scripts/, Makefile, env examples)

**Verdict:** This is an unusually well-hardened single-host compose deployment — non-root users everywhere, read-only rootfs + no-new-privileges on nearly every service, secrets via Docker-secret files bridged by a competent entrypoint wrapper, network segmentation with an `internal: true` data plane, encrypted+verified backups with rollback, fail-fast `:?` guards on every prod secret, and a carefully hardened nginx edge. The real damage is concentrated in three places: **the observability pipeline has three independent dead legs** (a blackbox `prober: smtp` that does not exist in the pinned exporter version, a Prometheus alert job that is never scraped, and a Loki tenant mismatch that 401s every log push), **the dev override silently re-publishes Postgres/Redis/ClickHouse on 0.0.0.0** due to a variable-semantics contradiction with `.env.example`, and **nested `secrets/` + `dump.rdb` inside `services/mail-server/` ship in every Docker build context**, defeating the `.dockerignore`'s own stated goal. `data/` contains only untracked local AI-training JSONL (~9 MB, gitignored); no runtime state is committed.

**Inventory:** base compose 33 services (+monitoring profile), prod overlay adds nginx/certbot/marketing/status-server/mailstore/migrator/4 backup sidecars and re-pins ~20 services to locally-built `ghcr.io/...:latest` images with a digest-override render in `deploy.sh` Step 3.5; mail-server dev stack (10 services) duplicates the root stack on a single flat `apexmail` network.

### Findings

1. **[P1] `prober: smtp` does not exist in blackbox_exporter v0.25.0 — the whole `blackbox-smtp` job permanently fails, two critical alerts fire forever, and mail-TLS expiry monitoring is dead** — `deploy/blackbox.yml:93-98` (`smtp_starttls: prober: smtp … tls: true`) vs `deploy/prometheus.yml:212-225` (targets `smtp.apexmail.ee:25,587,465,993`). 2. **[P1] Both outbound-MTA alerts are dead rules — the durable-retry daemon has zero Prometheus coverage** — `deploy/alerting-rules.yml:38-46` (`up{job="apexmail-outbound-mta"} == 0`) and `:48-60` (`apexmail_outbound_mta_pending_oldest_age_seconds > 1800`), but `deploy/prometheus.yml` defines no `apexmail-outbound-mta` scrape job (jobs list, lines 20-262) — an empty selector can never fire — and even if it did, the metric is served only on the loopback-bound health listener (`docker-compose.prod.yml:1190` `OUTBOUND_MTA_HEALTH_ADDR: 127.0.0.1:8093`; route mounted at `crates/outbound-mta/src/main.rs:343`), unreachable from the Prometheus container. Impact: the only component draining `outbound_relay_ledger` (the file's own words: "mail with transient failures stalls in pending") can die silently. Fix: set `OUTBOUND_MTA_HEALTH_ADDR: 0.0.0.0:8093` (internal networks only) and add a 15s scrape job `outbound-mta:8093`.

3. **[P1] Loki receives zero logs in every environment: `auth_enabled: true` + loki exporter with no tenant header** — `deploy/loki/loki-config.yaml:24` (`auth_enabled: true` → every push requires `X-Scope-OrgID`) vs `deploy/otel-collector/config.yaml:64-77` (loki exporter has no `headers:` and no `loki.tenant` hint). The exporter's own docs (v0.112.0 README, "Tenant information") show the required `headers: {"X-Scope-OrgID": …}` form — it is absent here. Grafana's datasource queries *do* send the header (`deploy/grafana/provisioning/datasources/loki.yml`, `httpHeaderName1: X-Scope-OrgID: apexmail`), so dashboards query tenant `apexmail` while all pushes 401 against it: every "Logs" panel and the Tempo→Loki trace-to-logs link are permanently empty. Secondary: the loki exporter is deprecated (removal announced, contrib issue #33916) — migration to the `otlphttp` exporter (Loki 3.0 native OTLP) is the correct fix and solves the header via Loki's `X-Scope-OrgID` pass-through config.

4. **[P1] Dev override + `.env.example` port semantics republish Postgres/Redis/ClickHouse on 0.0.0.0** — `docker-compose.override.yml:23` `"${POSTGRES_PORT:-127.0.0.1:5432}:5432"` (and `:47` Redis, `:108-109` ClickHouse): the default embeds `host:port`, but a bare port value — which `.env.example:21/33/41` literally ship (`POSTGRES_PORT=5432`, `REDIS_PORT=6379`, `CLICKHOUSE_HTTP_PORT=8123`) — expands to `5432:5432`, i.e. **all-interfaces**. The base file uses the opposite convention (`docker-compose.yml:41` `127.0.0.1:${POSTGRES_PORT:-5432}:5432`), and `.env.example:19-20` even asserts "Local port bindings are ALWAYS loopback … set a bare port number" — false for the override path. The repo's own live `.env:24` (`REDIS_PORT=6379`) means the current dev machine runs Redis on 0.0.0.0:6379 with the (hashed-ACL) dev password. This is the exact `GRAFANA_PORT` footgun the team fixed at `docker-compose.yml:1519-1524`, reintroduced. Fix: copy the base form `127.0.0.1:${POSTGRES_PORT:-5432}:5432` into the override (and load-test compose already does it right).

5. **[P2] Nested `services/mail-server/secrets/` and `dump.rdb` are tarred into every Docker build context and COPY'd into builder image layers** — `.dockerignore:24-26` uses root-anchored patterns (`secrets/`, `dump.rdb`, matched from context root only), while `services/mail-server/Dockerfile:40/77/95` does `COPY services/mail-server .` — pulling in `services/mail-server/secrets/postgres_password` (28 B) and `secrets/redis_password` (35 B) (real credential files, present on disk) plus `services/mail-server/dump.rdb` (a genuine Redis RDB v0015, 89 B) into the chef/planner/deps/builder layers. The `.dockerignore` header (lines 8-11) states "Everything below MUST stay excluded so no image build context ever tar-ships plaintext prod secrets" — the nested tree defeats exactly that. Runtime targets are unaffected, but builder layers persist in the daemon cache / CI builders and ship in `docker save` of any builder stage. `.gitignore` gets this right (`**/secrets/`, line 75). Fix: add `**/secrets/` and `**/dump.rdb` to `.dockerignore`.

6. **[P2] Tempo span-metrics remote-write is dead: Prometheus has no remote-write receiver** — `deploy/tempo/tempo.yaml:57-64` (`metrics_generator.storage.remote_write.url: http://prometheus:9090/api/v1/write`) vs the Prometheus command at `docker-compose.yml:1441-1446`, which sets no `--web.enable-remote-write-receiver` (the flag is the only way to enable it; the rendered `web.yml` at `deploy/scripts/render-prometheus-web-config.sh` only ever contains `basic_auth_users`). Every remote-write 404s; the metrics-generator produces nothing reachable, and the one alert family that would depend on span metrics has no data source. Fix: add `--web.enable-remote-write-receiver` (bind is compose-network + loopback only, so exposure risk is nil) or delete the generator block.

7. **[P2] Prod Redis: maxmemory == container memory limit, and volatile-lru can never evict the queue keys that matter** — `docker-compose.prod.yml:269-270` (`REDIS_MAXMEMORY: "1gb"`, `volatile-lru`) inside a container capped at `memory: 1G` (`:273-279`). Zero headroom for the AOF rewrite fork / copy-on-write — the classic path to cgroup OOM-kill of the shared Redis. Worse, the keys the alerts watch (`apexmail:events:pending` WAL, `apexmail:events:dead` DLQ — `deploy/alerting-rules.yml:317-339`) are list keys with no TTL, so `volatile-lru` behaves like `noeviction` for them: at 1 GB the tracking pipeline's RPUSHes fail rather than evict. Dev's `allkeys-lru` (`docker-compose.yml:90`) is the opposite failure — it can silently evict the durable WAL/DLQ lists. Fix: limit `REDIS_MAXMEMORY` to ~75% of the container cap (e.g. `768mb` in 1G) and give queue keys explicit TTLs or switch to `allkeys-lfu` with the WAL moved to a non-evicting keyspace/DB.

8. **[P2] Two trusted-proxy variables, only one wired in prod — the DDoS/WAF layer never trusts nginx** — base sets `DDOS_TRUSTED_PROXIES: ${DDOS_TRUSTED_PROXIES:-}` (empty = "headers never trusted", `docker-compose.yml:348-352`); the prod overlay sets only `TRUSTED_PROXIES` (`docker-compose.prod.yml:368-372`) and leaves `DDOS_TRUSTED_PROXIES` unset/empty. `.env.production.example` ("DDOS_TRUSTED_PROXIES= … NOTE … set BOTH to the same value") documents the trap but nothing enforces it. Consequence in prod: whatever middleware reads `DDOS_TRUSTED_PROXIES` keys every client on the nginx container IP — one global rate-limit bucket, so per-client brute-force limits and WAF keying are degenerate (the compose comment at `:368-372` explains precisely this failure for the other var). Fix: set `DDOS_TRUSTED_PROXIES` from the same `${TRUSTED_PROXIES}` value in the prod overlay (and pin the compose networks with explicit `ipam` blocks so the hardcoded `172.18/20/21` CIDRs can't drift from Docker's allocation order).

9. **[P2] "Per-workload dedicated tokens" are documented as REQUIRED-in-production but wired into no container** — `.env.production.example` (Per-workload section): "Each internal service REFUSES TO BOOT in production without its DEDICATED token … PROD_*_FILE compose bridge for these four is not wired yet — set them as plain .env values" — but plain `.env` values are not injected into any service either: the prod `pdf-renderer` receives only `INTERNAL_SERVICE_TOKEN_FILE: /run/secrets/internal_service_token` (`docker-compose.prod.yml:596-621`), `ai-embeddings` isn't in the prod compose at all, and the api-server caller side likewise has no `PDF_RENDERER_AUTH_TOKEN` env. Either the refusal logic exists and pdf-renderer crash-loops in prod (breaking every invoice render — the file's own comment at `:591-595` says all invoice paths go through it), or it doesn't and the documented credential-separation model is not actually deployed. Both readings are shipping-state bugs. Fix: add the four `*_AUTH_TOKEN` env/secret bridges to their services or delete the REQUIRED lines from the example until they're real.

10. **[P3] Duplicate disk-alert families double-page the same condition** — `NodeDiskSpaceWarning/Critical/PredictedFull` (`deploy/monitoring/alerts/disk-space.yml:23-60+`) are byte-identical in expression to `HostDiskSpaceWarning/Critical/PredictedFull` (`deploy/prometheus/alerts/infrastructure-alerts.yml:76-107`) — same `node_filesystem_*{job="node"}` selector, different alert names, so a full disk fires four alerts (two warning + two critical) through both rule files. Likewise `LowDiskSpace` (`deploy/alerting-rules.yml:493-501`) is a third copy. Keep one family; delete the rest.

11. **[P3] Enterprise scrape target is dev/prod drift — `EnterpriseServiceDown` permanently firing in dev** — `deploy/prometheus.yml:39` (`enterprise:3008`, the prod port) vs base/dev `PORT: 3002` (`docker-compose.yml:457`). Prod is correct; any dev machine running the monitoring profile gets a dead `up{job="apexmail-enterprise"}` and a critical alert after 2 min (`deploy/alerting-rules.yml:72-80`). 12. **[P3] Prod healthchecks downgrade real probes to bare TCP** — base/Dockerfile use application-level probes (tracking: `wget http://127.0.0.1:3001/health`, `docker-compose.yml:297`; api-server image: `nc -z 127.0.0.1:3000`, worker metrics-only), but the prod overlay replaces them with `bash -c 'exec 3<>/dev/tcp/…'` (`docker-compose.prod.yml:450, 321, 1473`) — a port is "healthy" while the router wedges, the DB pool is dead, or the worker loops are stuck as long as the metrics listener binds. Fix: use `wget -q --spider http://127.0.0.1:PORT/health` where the binary serves one (wget ships in the same images).

13. **[P3] Monitoring containers + certbot have no memory limits; `deploy.restart_policy` blocks are dead config** — `alertmanager` (`docker-compose.yml:1586-1639`), `postgres-exporter` (`:1644-1670`), `redis-exporter` (`:1675-1704`), `node-exporter` (`:1747-1768`), `blackbox-exporter` (`:1773-1800`) and prod `certbot` (`docker-compose.prod.yml:182-204`) define no `deploy.resources`; the prod overlay adds limits to app services but not these. Also every `deploy.restart_policy: {condition: on-failure, max_attempts: 5}` (e.g. `docker-compose.prod.yml:462-465`) is Swarm-only and ignored by plain compose — the effective policy is the `restart:` key, so the "5 attempts" semantics are fiction. Low risk (small containers), but inconsistent with the otherwise-complete OOM posture.

A laptop dev stack becomes a LAN-reachable SMTP endpoint. Intentional for local mail-flow tests or not, it should be opt-in via a bind variable like the sibling file.

15. **[P3] Dual-source Redis credential in dev monitoring — silent `RedisDown`** — dev `redis-exporter` takes `REDIS_PASSWORD: ${REDIS_PASSWORD:?…}` from `.env` (`docker-compose.yml:1675-1694`) while redis itself and every app take `secrets/redis_password.txt`. 16. **[P3] ClickHouse per-query memory budget exceeds its container cap** — `deploy/clickhouse/users.xml` profiles set `max_memory_usage: 10000000000` (10 GB) for both `default` and `readwrite`, while the container is limited to `memory: 4G` (`docker-compose.prod.yml:1872-1878`). ## SM14 — CI/CD & Release Engineering (.woodpecker.yml, ci/, .github, pre-commit, scanners)

**Verdict:** This is an unusually disciplined self-hosted CI system — fail-closed tool policy, a release-evidence manifest with digest pinning and SHA256SUMS tamper checks, lockstep-reviewed RUSTSEC ledgers, narrowly-scoped scanner triage with dated justifications, untracked `ci/runs/` (0 files tracked, 15 MB local, pruned to 30), no competing GitHub Actions (absence is itself enforced by `validate`), and honest loud-skip contracts. But it has one foot in a paper architecture: the "hermetic" executor image **cannot be built from the repo** (its Dockerfile COPYs two files that don't exist), the required WCAG/layout gates depend on a `node_modules/` tree that no automated path provisions and `.gitignore` excludes, the executor path silently drops stage timeouts and every docker-dependent gate (compose contract, fresh-DB migration chain, image scans) while still posting "release gates GREEN", and the recently-fixed "partial green blessing" (commit 24234a5e) still has a hole: advisory-failed stages bless a SHA recorded with a hardcoded `passedStages` list. Ignore-file hygiene is far above average but retains two whole-tree gitleaks exemptions (migrations/, apps/ai/src) and a globally-ignored jackson-databind RCE.

**Findings:**

1. **[P1] The hermetic CI image is unbuildable as committed** — `ci/ci-image/Dockerfile:99-100` — `COPY toolchain-versions.env /etc/apexmail-ci/toolchain-versions.env` / `COPY toolchain.sh /usr/local/bin/apexmail-ci-toolchain`. Fix: commit both files (generate `toolchain-versions.env` from the ARGs) or derive them in-image.

2. **[P1] Required contrast/layout gates run against an unprovisionable prerequisite** — `ci/stages/test.sh:753-754, 808-809` — `_cg_missing="tools/contrast-audit/node_modules (playwright) missing — run '(cd tools/contrast-audit && npm install)'"` → gate returns `CI_EXIT_FAIL` when absent. `tools/contrast-audit/node_modules` is gitignored (`.gitignore:170`), no script in `ci/`, `.woodpecker.yml`, or `gate.sh`/`layout-gate.sh` runs `npm install` (verified by grep — only the error strings mention it), and the CI image installs playwright browsers globally in `/tmp` (Dockerfile:92-96), not the workspace `node_modules` the gate checks. On a fresh clone (this dev box included — `node_modules` absent locally) the REQUIRED WCAG contrast and layout-spill gates hard-fail; any "green" executor run implies an undeclared, hand-bootstrapped persistent workspace. Fix: `npm ci` in the stage (or gate.sh) from the committed `package-lock.json`.

3. **[P2] Blessing hole: advisory-failed/skipped stages still bless, and `passedStages` is hardcoded** — `ci/pipeline.sh:270-271, 311` — `ok|skip|advisory-fail) ;;` … `printf '{"sha":"%s","pipelineConfigHash":"%s","passedStages":["validate","ui","test","security"],…}'`. Commit 24234a5e ("partial lanes can no longer bless") only checks stage **membership in the run list** (lines 303-308), not outcomes. A run with `--advisory security`, or `CI_ADVISORY_STAGES` set via `/etc/apexmail/pipeline.conf` (sourced at pipeline.sh:50-53, outside repo review), that *fails* security still ends `_overall=ok` and writes `.last-good-sha` claiming security passed — after which `fetch.sh:79-83` skip-unchanged no-ops every poll for that SHA. Fix: derive `passedStages` from the manifest's actual per-stage statuses and refuse to bless if any of the four is `advisory-fail`/`skip`.

4. **[P2] Executor path drops the timeout contract entirely** — `ci/woodpecker/stage.sh:59` — `sh "$_script" >>"$_CI_STAGE_LOG" 2>&1 || _stage_rc=$?` runs the stage bare; the host runner wraps the identical script in `ci_timeout` with `CI_TIMEOUT_*` budgets (`ci/pipeline.sh:249`, contract documented at pipeline.sh:24-29: "124 = timeout"). No Woodpecker per-step timeout is set either, so a hung nextest/cargo run parks the pipeline indefinitely on the executor while the host path would have killed it at 5400 s. Fix: reuse `ci_timeout "$_es_tmo"` (or set Woodpecker step timeouts) in stage.sh.

5. **[P2] Docker-dependent gates silently vanish in the "hermetic" executor while it posts GREEN** — `ci/stages/security.sh:225` — `ci_docker_ok || { ci_warn "docker unavailable — migration validation skipped"; return "$CI_EXIT_OK"; }`, and `ci/stages/validate.sh:66-67` — `command -v docker >/dev/null 2>&1 || { ci_warn "docker CLI missing — compose config check skipped"; return "$CI_EXIT_OK"; }`. The CI image installs no docker CLI (Dockerfile:44-53 apt list), so on every PR the compose contract gate, the fresh-DB `sqlx migrate run` ×2 chain validation, and `trivy_images` never run — yet `.woodpecker.yml:196-200` posts `GITHUB_STATUS_STATE=success` … "release gates GREEN". `CI_MISSING_TOOLS=fail` does not cover these (`ci_docker_ok` isn't gated by it), contradicting the file's own fail-closed doctrine (header lines 17-23). Partially mitigated by the migrator fresh-DB regression test using the `postgres-fresh` service. Fix: make docker-absence a hard failure under `CI_MISSING_TOOLS=fail`, or wire the chain-apply to the provided `TEST_FRESH_DATABASE_URL`.

6. **[P2] SQL injection vector in the failure-email enqueue** — `ci/stages/notify.sh:102, 128` — `_ne_tail=$(tail -c 4000 "$_ne_log" … | sed "s/'/''/g" …)` then `\$body\$${_ne_body}\$body\$`. Only single quotes are escaped, but the body is dollar-quoted: a stage-log tail containing the literal `$body$` (perfectly possible in cargo/test/dependency output) terminates the string early and the remainder executes as raw SQL against the production postgres as root (`docker compose exec -T postgres psql`, notify.sh:119-121). 8. **[P2] Whole-tree gitleaks exemptions over production SQL and ordinary source** — `.gitleaks.toml:39, 69` — `"(^|/)migrations/"` and `"(^|/)apps/ai/(training|src)/"`. 9. **[P2] Executor image pinned by a mutable tag, holding the GitHub token** — `.woodpecker.yml:83` (and all steps) — `image: ghcr.io/sbelakho2/apexmail-ci:1`. ## SM15 — SDKs, Packages, Protocol & Docs

**Verdict:** The five first-party SDKs (Go, Java, PHP, Python, Ruby — all hand-written, no generator) are transport-level excellent: HTTPS enforced by constructor, default timeouts, bounded jittered retries honoring Retry-After, auto idempotency keys on POSTs, response-size caps, masked key reprs, and endpoint paths that match the api-server routers on every one of my sampled cross-checks (messages/batch/cancel, webhooks rotate-secret/test, templates render/duplicate/rollback, suppressions/bulk, analytics dashboard/volume/engagement/deliverability/subject-line/export, api-keys at /v1/auth/api-keys). The kiwicaptcha family is disciplined — all 10 Lua scripts and all 9 widget assets are byte-identical across the three/four copies with CI parity gates, and Rust/PHP protocol constants are in parity (MAX_PROTOCOL_VERSION=4 both sides). The real problems are drift, not design: all five SDKs ship a webhook-event vocabulary that no longer matches the server (client-side gates now block valid events), four of five SDK changelogs claim a 1.0.1 release their code constants never shipped, docs/marketing/pricing.md quotes prices that contradict the billing authority by up to ~2x, the enterprise docs document endpoint paths that don't exist on the shipped enterprise router, and packages/smtp-auth-proxy is a dead stub carrying four unused dependencies and a wrong pointer.

**Findings:**

1. **[P1] All five SDKs ship a stale webhook-event vocabulary; Python and Java actively block server-valid events** — `packages/sdk-python/src/apexmail/resources/webhooks.py:29-45` — the list `("email.delivered", "email.bounced", "email.complained", "message.sent", ..., "bounce", "complaint", "inbound", "*")` is annotated "Event names the server accepts (webhooks.rs KNOWN_WEBHOOK_EVENTS). Any other name is rejected with 422", but the server list at `services/mail-server/crates/api-server/src/routes/webhooks.rs:110-130` accepts `message.accepted/queued/attempted/deferred/delivered/bounced/complained/suppressed/opened/clicked/cancelled, recipient.unsubscribed, placement_test.completed, inbound, *` — it contains none of `email.*`, `message.sent`, `bounce`, `complaint` (legacy aliases removed in commit 411f2a63, 2026-09-08; SDK lists last touched cfaa7812, 2026-08-29). Python's client-side gate at `webhooks.py:69-75` (`invalid = [event for event in events if event.strip() not in KNOWN_WEBHOOK_EVENTS]` → raises `ValidationError`) makes `message.accepted` and `message.cancelled` impossible to subscribe to, while `email.delivered` passes the gate and 422s server-side. Same stale list in `packages/sdk-go/apexmail.go:1457-1473`, `packages/sdk-java/src/main/java/ee/apexmail/Webhooks.java:27` (enforced at :67-69), `packages/sdk-php/src/Resources/Webhooks.php:17-33`, `packages/sdk-ruby/lib/apexmail.rb:733-749`, and the Python enum `packages/sdk-python/src/apexmail/models.py:47-58`. Fix: regenerate the list in all five SDKs from `KNOWN_WEBHOOK_EVENTS` (ideally via the shared-contract pattern already used for send-contract.json) and drop or relax the client-side gates to a warning.

2. **[P2] docs/marketing/pricing.md price table contradicts the billing authority and the shipped site it claims to describe** — `docs/marketing/pricing.md:16-24` — table shows "Free €0 / 30,000 emails/mo; Starter €25 / €250yr; Pro €65; Growth €150; Scale €350; Enterprise €3,000 / €30,000yr", while the file's own declared source of truth `docs/pricing.md:22-29` and the runtime authority `services/mail-server/crates/billing-service/src/plans.rs:102,111,134-246` say Free 3,000 emails/mo (also a 10x difference in the free tier), Developer €29/€290, Pro €89/€890, Growth €229, Business €699, Enterprise €1,750/€17,500.
