# PostgreSQL Read Replicas

> **SCALE-H-02** | Owner: Platform Engineering | Last updated: 2026-05-17

## Overview

PostgreSQL read replicas provide horizontal read scalability for ApexMail. By offloading read-only queries (analytics, reporting, health checks, dashboard queries) to replica nodes, the primary database is reserved for write-heavy and consistency-critical operations such as email submission, delivery status updates, and transactional workflows.

This document covers:
- Configuring read replicas with the ApexMail Helm chart
- Read/write splitting using `sqlx::PoolPair`
- Connection pooling strategies
- RDS read replica configuration (AWS-managed)

---

## 1. Read Replica Architecture

```
┌──────────────┐      ┌──────────────┐      ┌──────────────┐
│   Primary    │──────│  Replica 1   │──────│  Replica 2   │
│  (writes)    │  WAL │  (reads)     │  WAL │  (reads)     │
└──────────────┘      └──────────────┘      └──────────────┘
        │                     │                      │
        │                     │                      │
        ▼                     ▼                      ▼
┌──────────────────────────────────────────────────────────┐
│                  Application Layer                         │
│                                                           │
│  Write Pool ──► Primary (rw)                              │
│  Read Pool  ──► Replicas (ro, round-robin or random)     │
└──────────────────────────────────────────────────────────┘
```

Replication uses PostgreSQL's native **streaming replication** via WAL (Write-Ahead Log). Replicas connect to the primary and continuously apply WAL changes.

## 2. Helm Chart Configuration

The ApexMail Helm chart at [`deploy/helm/apexmail/`](../../deploy/helm/apexmail/) supports read replica configuration through `values.yaml`.

### 2.1 Enabling Replicas

```yaml
# deploy/helm/apexmail/values.yaml (excerpt)
postgresql:
  # Primary configuration
  primary:
    persistence:
      size: 100Gi
    resources:
      requests:
        cpu: 2
        memory: 4Gi

  # Read replica configuration
  readReplicas:
    enabled: true
    count: 2
    replica:
      persistence:
        size: 100Gi
      resources:
        requests:
          cpu: 2
          memory: 4Gi
    # Replication settings
    synchronousReplication: false   # Async replication (recommended for replicas)
    walKeepSegments: 32            # WAL segments retained for replica catch-up
```

### 2.2 Connection Strings via ConfigMap

The Helm chart generates a ConfigMap with separate connection strings:

```yaml
# Generated by the Helm chart
apiVersion: v1
kind: ConfigMap
metadata:
  name: apexmail-postgres-config
data:
  DATABASE_URL: "postgres://apexmail:password@postgres-primary:5432/apexmail"
  DATABASE_READ_URL: "postgres://apexmail:password@postgres-replica:5432/apexmail"
  # If multiple replicas, a load-balanced endpoint or comma-separated list:
  DATABASE_READ_URLS: "postgres://apexmail:password@postgres-replica-0:5432/apexmail,postgres://apexmail:password@postgres-replica-1:5432/apexmail"
```

### 2.3 Service Topology

```
Services created by Helm:
- postgres-primary:5432   → Primary node (read/write)
- postgres-replica:5432   → Single endpoint → load-balanced across replicas
- postgres-replica-0:5432 → Individual replica 0 (for dedicated connections)
- postgres-replica-1:5432 → Individual replica 1
```

For production, place replicas behind an internal TCP load balancer (e.g., AWS NLB) rather than relying on Kubernetes Service round-robin, which does not account for replica lag.

## 3. sqlx PoolPair — Read/Write Splitting

### 3.1 Concept

`sqlx::PoolPair` is a concept (not yet an `sqlx` built-in) for managing two separate connection pools: a **write pool** (primary) and a **read pool** (replicas). The application explicitly routes queries to the appropriate pool based on whether they are read-only or read-write.

While `sqlx` does not ship with a `PoolPair` type as of v0.8, the pattern is straightforward to implement:

```rust
/// A pair of connection pools for read/write splitting.
#[derive(Clone)]
struct PgPoolPair {
    /// Write pool — connects to the PostgreSQL primary.
    /// Used for all INSERT, UPDATE, DELETE, and transactional queries.
    write: PgPool,

    /// Read pool — connects to PostgreSQL read replicas.
    /// Used for SELECT queries that can tolerate bounded staleness.
    read: PgPool,
}

impl PgPoolPair {
    /// Returns the write pool for mutation queries.
    fn writer(&self) -> &PgPool {
        &self.write
    }

    /// Returns the read pool for read-only queries.
    /// In the future, this could implement replica lag awareness:
    /// if the application requires strong consistency for a specific
    /// read, fall back to the write pool.
    fn reader(&self) -> &PgPool {
        &self.read
    }
}
```

### 3.2 Usage Pattern

```rust
// ── Initialisation ──────────────────────────────────────────────
let write_pool = PgPoolOptions::new()
    .max_connections(50)
    .connect(&std::env::var("DATABASE_URL")?)
    .await?;

let read_pool = PgPoolOptions::new()
    .max_connections(100)  // Replicas handle more concurrent readers
    .connect(&std::env::var("DATABASE_READ_URL")?)
    .await?;

let pools = PgPoolPair { write: write_pool, read: read_pool };

// ── Writes always go to the primary ────────────────────────────
sqlx::query("INSERT INTO emails (id, from_address, to_address, subject, body)")
    .bind(&email.id)
    .bind(&email.from)
    .bind(&email.to)
    .bind(&email.subject)
    .bind(&email.body)
    .execute(pools.writer())
    .await?;

// ── Reads can go to replicas ────────────────────────────────────
let analytics = sqlx::query_as::<_, EmailStats>(
    "SELECT DATE(created_at) as day, COUNT(*) as count
     FROM emails
     WHERE created_at >= NOW() - INTERVAL '30 days'
     GROUP BY DATE(created_at)
     ORDER BY day"
)
    .fetch_all(pools.reader())
    .await?;

// ── Strongly-consistent reads ──────────────────────────────────
// For reads that must see the latest write, use the write pool:
let recent_email = sqlx::query_as::<_, Email>(
    "SELECT * FROM emails WHERE id = $1"
)
    .bind(&email_id)
    .fetch_optional(pools.writer())  // Primary guarantees up-to-date data
    .await?;
```

### 3.3 When to Use Which Pool

| Query Type | Pool | Rationale |
|-----------|------|-----------|
| `INSERT`, `UPDATE`, `DELETE` | **Write** | Mutations must go to the primary |
| `SELECT ... FOR UPDATE` | **Write** | Row-level locking needs the primary |
| `SELECT` in a transaction | **Write** | Transactional consistency |
| `SELECT` (dashboard/reports) | **Read** | Tolerates seconds of staleness |
| `SELECT` (recent user data) | **Read** | Replication lag < 100ms typically acceptable |
| `SELECT` (post-write read) | **Write** | Must see own writes (read-your-writes consistency) |

### 3.4 Replica Lag Awareness

For workloads that require bounded staleness, implement a **lag-aware reader**:

```rust
/// Returns the read pool if replica lag is below the threshold,
/// otherwise falls back to the write pool.
fn lag_aware_reader(&self, max_lag: Duration) -> &PgPool {
    let lag = self.measure_replica_lag().await;
    if lag <= max_lag {
        &self.read
    } else {
        tracing::warn!(replica_lag_ms = %lag.as_millis(), "Replica lag exceeds threshold, falling back to primary");
        &self.write
    }
}

/// Measure replication lag by comparing a write timestamp across
/// primary and replica (requires a heartbeat table).
async fn measure_replica_lag(&self) -> Duration {
    // Simple heuristic: query a heartbeat timestamp from both pools
    // and compute the difference.
    // In production, use pg_stat_replication on the primary or
    // a dedicated heartbeat table updated every second.
    Duration::from_millis(50)  // Placeholder
}
```

## 4. Connection Pooling Strategies

### 4.1 PgBouncer (Sidecar Pattern)

Deploy PgBouncer as a sidecar container alongside each application pod for local connection pooling:

```yaml
# Kubernetes sidecar example
containers:
  - name: api-server
    image: apexmail/api-server:latest
    env:
      - name: DATABASE_URL
        value: "postgres://apexmail:password@localhost:6432/apexmail"  # Via local PgBouncer
  - name: pgbouncer
    image: bitnami/pgbouncer:latest
    env:
      - name: PGBOUNCER_DATABASE_URL
        value: "postgres://apexmail:password@postgres-primary:5432/apexmail"
      - name: PGBOUNCER_MAX_CLIENT_CONN
        value: "200"
      - name: PGBOUNCER_DEFAULT_POOL_SIZE
        value: "25"
      - name: PGBOUNCER_POOL_MODE
        value: "transaction"  # Transaction pooling (recommended)
```

**Pool mode options:**

| Mode | Behaviour | Use Case |
|------|-----------|----------|
| `session` | Connection held until client disconnects | Legacy apps, prepared statements |
| `transaction` | Connection returned to pool after each transaction | Recommended for most workloads |
| `statement` | Connection returned after each statement | Rarely used; breaks prepared statements |

### 4.2 Application-Level Pooling (sqlx PgPool)

```rust
// Write pool: conservative sizing to avoid overwhelming the primary
let write_pool = PgPoolOptions::new()
    .max_connections(50)           // Primary handles writes + some reads
    .min_connections(10)           // Keep warm connections ready
    .acquire_timeout(Duration::from_secs(5))
    .max_lifetime(Duration::from_secs(1800))  // 30 min
    .idle_timeout(Duration::from_secs(600))   // 10 min
    .connect(&write_dsn)
    .await?;

// Read pool: higher concurrency for scaled-out replicas
let read_pool = PgPoolOptions::new()
    .max_connections(100)          // Replicas are scaled horizontally
    .min_connections(20)
    .acquire_timeout(Duration::from_secs(5))
    .max_lifetime(Duration::from_secs(1800))
    .idle_timeout(Duration::from_secs(600))
    .connect(&read_dsn)
    .await?;
```

### 4.3 Pool Sizing Guidelines

| Service | Write Pool | Read Pool | Rationale |
|---------|-----------|-----------|-----------|
| API Server | 30–50 | 50–100 | Handles user-facing requests |
| Worker | 20–30 | 30–50 | Batch processing |
| Analytics | 5–10 | 20–50 | Heavy read queries, few writes |
| Health Probes | 5 | 10 | Lightweight, high frequency |

Total connections to PostgreSQL should not exceed `max_connections` (default: 100 in Helm chart; tune per node). Formula:

```
total_connections = (write_pool_max × write_pods) + (read_pool_max × read_pods)
```

Ensure this is well below PostgreSQL's `max_connections` (recommended: ≤ 80% of limit).

## 5. AWS RDS Read Replica Configuration

### 5.1 Creating Read Replicas

```hcl
# Terraform example: RDS PostgreSQL with read replicas
resource "aws_db_instance" "apexmail_primary" {
  identifier           = "apexmail-primary"
  engine               = "postgres"
  engine_version       = "16.3"
  instance_class       = "db.r6g.large"
  allocated_storage    = 100
  storage_type         = "gp3"
  storage_encrypted    = true
  db_name              = "apexmail"
  username             = "apexmail"
  password             = var.db_password
  backup_retention_period = 7
  backup_window        = "03:00-04:00"
  maintenance_window   = "sun:05:00-sun:06:00"
  skip_final_snapshot  = false
  final_snapshot_identifier = "apexmail-primary-final-${formatdate("YYYYMMDD", timestamp())}"
  multi_az             = true   # Primary HA via Multi-AZ
  deletion_protection  = true
}

resource "aws_db_instance" "apexmail_replica" {
  count                = 2
  identifier           = "apexmail-replica-${count.index}"
  engine               = "postgres"
  engine_version       = "16.3"
  instance_class       = "db.r6g.large"
  allocated_storage    = 100
  storage_type         = "gp3"
  storage_encrypted    = true
  replicate_source_db  = aws_db_instance.apexmail_primary.identifier
  backup_retention_period = 7
  backup_window        = "04:00-05:00"
  maintenance_window   = "sun:06:00-sun:07:00"
  skip_final_snapshot  = true
  deletion_protection  = false
}
```

### 5.2 RDS-Specific Considerations

| Consideration | Detail |
|---------------|--------|
| **Replication type** | RDS uses asynchronous replication (default) |
| **Replica lag** | Typically < 100ms in same region; cross-region may be 1–5s |
| **Read endpoint** | RDS provides a reader endpoint that load-balances across replicas |
| **Promotion** | Read replica can be promoted to primary in < 1 minute during DR |
| **Backup** | Replicas must be promoted to primary before taking snapshots |
| **Upgrades** | Engine version upgrades must be applied to replicas before primary |

### 5.3 Connection String with RDS Reader Endpoint

```
# Primary endpoint (read/write)
DATABASE_URL=postgres://apexmail:password@apexmail-primary.xxxxxx.us-east-1.rds.amazonaws.com:5432/apexmail

# Reader endpoint (load-balanced across replicas)
DATABASE_READ_URL=postgres://apexmail:password@apexmail-primary.cluster-ro-xxxxxx.us-east-1.rds.amazonaws.com:5432/apexmail
```

## 6. Monitoring Replica Health

### 6.1 Key Metrics

| Metric | Query | Alert Threshold |
|--------|-------|-----------------|
| Replica lag | `SELECT EXTRACT(EPOCH FROM pg_last_wal_receive_lsn() - pg_last_wal_replay_lsn())` | > 10s (warning), > 60s (critical) |
| Replica status | `SELECT pg_is_in_recovery()` | Should return `true` for replicas |
| WAL generation rate | `pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0')` | > 100 MB/min indicates high write load |
| Replication slots lag | `pg_replication_slots` view | > 1 GB may cause primary WAL accumulation |

Refer to [`deploy/prometheus/alerts/infrastructure-alerts.yml`](../../deploy/prometheus/alerts/infrastructure-alerts.yml) for pre-configured replication lag alerts.

## 7. Limitations and Caveats

1. **Read-your-writes consistency**: Applications must route post-write reads to the primary pool or tolerate replica lag.
2. **DDL operations**: Schema migrations (`sqlx migrate run`) must target the primary only. Replicas apply DDL via WAL replay automatically.
3. **Sequences and generated values**: `nextval()` calls on replicas will fail — use the write pool for any operation involving sequence generation.
4. **Temporary tables**: Not replicated — created on a per-connection basis.
5. **Prepared statements**: With PgBouncer transaction pooling, prepared statements are discarded between transactions. Use the write pool or direct connections for heavy prepared-statement usage.
