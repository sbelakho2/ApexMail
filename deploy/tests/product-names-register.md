# ApexMail Official Product Names Register

**Owner:** Product lead
**Last updated:** 2026-07-29
**Approval required:** Yes, product lead sign-off

## Locked Names

| Official Name | Capitalization | Used In | Notes |
|---------------|---------------|---------|-------|
| ApexMail | PascalCase | All pages, marketing, documentation | Primary brand name. Never "Apexmail" or "apexmail" except in domain/email contexts. |
| ApexMail API | PascalCase "API" | Developer docs, pricing, features | REST API product. Never "ApexMail api" or "apexmail-api". |
| ApexMail Cloud | PascalCase | Architecture docs, comparison pages | SaaS multi-tenant platform. Never "apexmail cloud" or "Cloud". |
| ApexMail Private Cloud | PascalCase | Private Cloud page, enterprise docs | Self-hosted option. Never "private cloud apexmail" or "apexmail private". Always capitalized. |
| ApexMail Enterprise | PascalCase | Enterprise solutions, pricing | Enterprise plan tier. Never "apexmail enterprise" or "Enterprise plan". |
| ApexMail Dashboard | PascalCase | User docs, API docs | Web application UI. Never "apexmail dashboard" or "Dashboard". |
| Message Events | PascalCase (two words, both caps) | API docs, webhook docs | Event stream for email delivery tracking. Never "message events" or "Message events". |
| Dynamic Allocation | PascalCase (two words, both caps) | Architecture, features | Routing optimization engine. Never "dynamic allocation" or "Dynamic allocation". |

## Naming Rules

1. Capitalization is consistent across all surfaces — navigation, documentation, marketing, billing.
2. Navigation labels match documentation section titles.
3. Pricing plan names match billing configuration (`config.toml` plan keys).
4. SDK package names use approved branding (`apexmail-php`, `apexmail-python`, etc.).
5. Deprecated names must redirect or be removed from all public surfaces.
6. Third-party references must use correct capitalization.
