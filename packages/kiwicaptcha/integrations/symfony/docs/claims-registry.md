# Claims registry

Every factual claim made in this documentation is listed here with its
scope, assumptions, and the test that evidences it. A claim without an
owning test is not made. "Last reviewed" is the date the claim was checked
against the implementation and its tests.

| Claim | Scope | Assumptions | Evidence | Owning test/document | Last reviewed |
|-------|-------|-------------|----------|----------------------|---------------|
| **No third-party requests** | The default widget execution path: challenge issuance (POST to the application's own `{prefix}/challenge`), solving (embedded WASM/JS — no network), and token submission (the application's own form POST). All widget assets (CSS, WASM solver, driver) are inlined at render time. Optional integrations do not change this: the risk engine, siteverify, and chained challenges are server-side (Redis) only; the driver refuses cross-origin challenge endpoints at runtime; a configured worker URL (`data-kiwi-worker-src`) must be same-origin — cross-origin worker URLs are never fetched. | The application does not configure third-party endpoints itself; the browser allows same-origin requests. | `Privacy Strict: zero external requests and empty telemetry` (`tests/browser/specs/widget.spec.mjs`) asserts the widget page performs no request outside the app origin; `testRenderEmbedsAllAssetsAndEndpoint` (`TwigRuntimeTest.php`) pins the inline embedding. | `tests/browser/specs/widget.spec.mjs`; `tests/TwigRuntimeTest.php`; [SECURITY.md](../../../../../SECURITY.md#csp--worker-requirements) (cross-origin worker URLs never fetched) | 2026-08-20 |
| **Behavioral telemetry off by default** | The widget telemetry mode defaults to `off`; `privacy_mode: strict` forces `off` regardless of operator config; the default widget sends an empty telemetry payload (`{}`). | The operator does not opt a page into `minimal`/`full` telemetry; strict mode is not disabled. | The same widget spec asserts the default solve's telemetry payload equals `{}`; `testTelemetryRenderedFromRuntimeDefaultAndContext` (`TwigRuntimeTest.php`) pins the default render; `testAuditDefaultsArePrivacyFirst` (`ConfigurationTest.php`) pins the config defaults. | `tests/browser/specs/widget.spec.mjs`; `tests/TwigRuntimeTest.php`; `tests/ConfigurationTest.php` | 2026-08-20 |
| **No device-capability or screen-size signals unless the coarse client-context opt-in is enabled** | The widget sends a client-context descriptor only when BOTH `risk.client_context` is enabled AND the app renders `data-kiwi-risk-context="coarse"` on the widget container; without the attribute the field is never sent; `privacy_mode: strict` refuses the opt-in at compile time and never renders the attribute. | The operator does not render the opt-in attribute under strict mode. | `without the opt-in attribute no client_context is ever sent` (`tests/browser/specs/risk-v2.spec.mjs`) asserts the challenge request carries no client_context by default; `testClientContextOptInRendersTheAttributeAndDefaultsAreOff` and `testStrictPrivacyModeRefusesClientContext` / `testStrictPrivacyModeRendersNoOptInAttributeEvenWithTheRenderOverride` (`ChainingWiringTest.php`) pin the render and strict-mode behavior. | `tests/browser/specs/risk-v2.spec.mjs`; `tests/ChainingWiringTest.php` | 2026-08-20 |
| **The widget collects no canvas/audio/font/GPU fingerprints** | The coarse client-context descriptor is bounded to four coarse classes (viewport class, pointer class, language family, timezone class) with a bounded wire pattern (`[a-z0-9+_,=:-]{1,64}`); no canvas/audio/font-list/GPU signals and no stable identifiers exist in the tag; a missing capability contributes nothing. | The descriptor is generated by the shipped widget driver (not by application code). | `the challenge request carries the coarse client_context descriptor under the explicit opt-in` (`tests/browser/specs/risk-v2.spec.mjs`) asserts the bounded pattern and the `v/t/l/z` classes; `testTagFollowsTheCoarseCapabilityDescriptor` and `testTagWidthIsDeliberatelyCoarse` (`ClientContextTagTest.php`) pin the tag's composition and coarseness server-side. | `tests/browser/specs/risk-v2.spec.mjs`; `tests/ClientContextTagTest.php` | 2026-08-20 |
| **Challenge tokens are single-use** | A token may derive a successful outcome at most once; with `RedisStorage` the pending→consumed Lua transition is atomic under concurrency (exactly one winner among parallel consumers); a re-verify of a consumed record returns the stored deterministic outcome instead of re-deriving, and a replay without the matching idempotency identity resolves to `timeout-or-duplicate` (siteverify) or `invalid_or_expired` (native). | A storage with atomic consumed-state transition semantics is used (RedisStorage; PSR-6 single-use is best-effort by design). | `testEndToEndOneShotReplayRejected` and `testGetdelFiftyParallelConsumersExactlyOneWinner` (`RealRedisIntegrationTest.php`); `testReplayResolvesToTheStoredDeterministicOutcome` (`SiteVerifyTest.php`); `testReplayOfAValidOutcomeReturnsValidWithoutRedoingWork` (`packages/kiwicaptcha-php/tests/ConsumedStateRetryTest.php`). | `tests/RealRedisIntegrationTest.php`; `tests/SiteVerifyTest.php`; `packages/kiwicaptcha-php/tests/ConsumedStateRetryTest.php` | 2026-08-20 |
| **A replayed token reproduces the same application-level disposition** | Within the disposition store's retention horizon, a replayed VALID proof returns the same `PostSolveDisposition` (`PASS`/`DENY`/`STEP_UP`/`CHAIN_REQUIRED`) stored under the nonce; `DENY`, `STEP_UP` and `CHAIN_REQUIRED` can never be replayed into a `PASS`; a chain-required replay re-signs with the original expiry. | The post-solve policy/store is available (risk layer configured for the scope). | `testFreshDenyReplaysAsDenyNeverPass`, `testFreshStepUpReplaysAsStepUp`, `testFreshPassReplaysAsPassWithTheSameApplicationOutcome` and `testChainRequiredDispositionReplaysWithTheSameChainId` (`ValidatorTest.php`); `testChainRequiredDispositionReplayReSignsWithTheOriginalExpiry` (`ChainedChallengeTest.php`). | `tests/ValidatorTest.php`; `tests/ChainedChallengeTest.php` | 2026-08-20 |

Maintenance rule: when a claim's behavior changes, the evidence must change
first (the owning test is updated or replaced), and this registry's row —
including the scope and assumptions — must be updated in the same change.
The glossary ([glossary.md](glossary.md)) defines the terms used in the
scope columns.
