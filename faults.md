# ApexMail Codebase Fault Scan

> Generated by line-by-line repository audit across all major packages, apps, and services.

---

## 🔴 Critical Bugs

- [ ] **`packages/db/src/transaction.ts` (line 107) — Connection leak detection bypassed**
  `withTransaction()` uses `pool.connect()` directly instead of `db.getClient()`. This means the G-210 connection leak tracking in `DatabasePool.getClient()` is never activated for any transaction. If a transaction throws before `client.release()` in the `finally` block, the leak won't be detected. Every transaction in the system is affected.

- [ ] **`packages/db/src/repositories/users.ts` (lines 168–184) — `verifyCredentials` doesn't SELECT `metadata` but types claim it exists**
  The SQL query for credential verification does not include the `metadata` column, but the TypeScript type assertion includes `metadata: string`. When `mapRow()` runs, `row.metadata` is `undefined`, which passes through `typeof row.metadata === 'string'` as false, then casts `undefined as unknown as Record<string, unknown>`. The returned `User.metadata` will be `undefined` at runtime, causing potential crashes in downstream code that does `user.metadata.someKey`.

- [ ] **`packages/lib/src/crypto/index.ts` (line 269) — `verifyPassword` crashes on mismatched key lengths**
  `timingSafeEqual(storedKey, derivedKey)` throws `ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH` if buffer lengths differ. If a stored hash was generated with a different `SCRYPT_KEYLEN` (e.g., during a migration), the function will throw an unhandled exception instead of returning `false`. This would crash any login attempt for affected users.

- [ ] **`packages/db/src/repositories/api-keys.ts` (lines 262–263) — `verify()` excludes `allowed_ips`/`allowed_domains` from SELECT**
  The optimized query selects only a subset of columns for verification but omits `allowed_ips` and `allowed_domains`. When the row is passed to `mapRow()`, those fields will be `undefined`. The IP whitelist check on lines 320–328 then checks `apiKey.allowedIps && apiKey.allowedIps.length > 0`, which evaluates to false for `undefined`, silently **bypassing IP restrictions** on all API key verifications.

- [ ] **`packages/db/src/fingerprint.ts` (line 49) — `statement_timeout` query option silently ignored**
  The `queryWithTimeout` function passes `statement_timeout` as a query option: `pool.query<T>({ text, statement_timeout: ... })`. The `pg` library's `query()` method does not support `statement_timeout` as an option — it is silently ignored. Schema fingerprinting queries have no effective timeout protection.

## 🟠 Significant Issues

- [ ] **`packages/db/src/repositories/api-keys.ts` — `rotate()` uses manual transaction management instead of `withTransaction`**
  The `rotate()` method manually calls `client.query('BEGIN')`, `COMMIT`, `ROLLBACK`. It doesn't use the `withTransaction` helper, so it misses automatic retry on serialization failures, isolation level configuration, and savepoint support. If the ROLLBACK itself fails (line 677), the error is swallowed.

- [ ] **`packages/db/src/repositories/api-keys.ts` (line 357) — SQL string interpolation for interval**
  `updateLastUsed` uses `INTERVAL '${...DEBOUNCE_MS / 1000} seconds'` via string interpolation inside the SQL string. While currently derived from a static constant, this pattern is fragile. A future developer might parameterize it incorrectly, introducing SQL injection.

- [ ] **`apps/billing/src/services/stripe-integration.ts` (lines 563–564) — No guard on empty `subscription.items.data`**
  `subscription.items.data[0]?.price.id` will be `undefined` if the subscription has no line items. This `undefined` value flows into a database INSERT as `stripe_price_id`, creating corrupted subscription records.

- [ ] **`packages/lib/src/validation/index.ts` (line 263) — Native `validateSyntax` incorrectly marks disposable emails as invalid syntax**
  The native fast-path returns `valid: result.valid && !result.isDisposable`, mixing disposable detection into syntax validation. If the native addon flags a domain as disposable, `validateSyntax` returns `valid: false` with `syntax: false`, which is semantically wrong. The user sees "Invalid email syntax" when the email is syntactically correct.

- [ ] **`packages/db/src/repositories/messages.ts` — `claimForSending` and `markDeferred` bypass state machine**
  Both methods directly UPDATE the status to 'sending'/'deferred' without checking `VALID_TRANSITIONS`. While this is intentional for bulk operations, it means a message in 'bounced' or 'failed' (terminal) state could theoretically be re-queued if the WHERE clause matches due to a race condition with the `FOR UPDATE SKIP LOCKED`.

- [ ] **`packages/lib/src/http/index.ts` (lines 207–214) — Double timeout mechanism**
  The code sets both an `AbortController` timeout and undici's `headersTimeout`/`bodyTimeout`. If the abort fires first, the error message says "Request timeout" but undici may also be trying to clean up, leading to confusing error handling.

- [ ] **`apps/billing/src/app.ts` (line 151) — Port fallback inconsistent with schema default**
  `config.port` getter returns `3000` on NaN, but the Zod schema defaults to `'4100'`. If PORT env var contains non-numeric characters that parse to NaN, the billing service silently starts on port 3000 instead of 4100.

- [ ] **`apps/billing/src/routes/billing.ts` (lines 56–74) — `isAllowedRedirectUrl` vulnerable to homograph attacks**
  The domain check uses exact string comparison (`hostname === 'apexmail.ee'`). Internationalized domain names using lookalike characters (e.g., Cyrillic 'а' instead of Latin 'a') could bypass this check.

- [ ] **`apps/billing/src/config.ts` (lines 187–188) — Insecure default telemetry salt**
  `viralTelemetryHashSalt` falls back to `'apexmail-telemetry'` when `VIRAL_TELEMETRY_HASH_SALT` is not set. This hardcoded salt is publicly visible in the source code, completely defeating the purpose of pseudonymization.

- [ ] **`packages/db/src/transaction.ts` (line 255) — Advisory lock BigInt precision loss**
  `Number(lockKey >> BigInt(32))` and `Number(lockKey & BigInt(0xFFFFFFFF))` can lose precision for BigInt values exceeding `Number.MAX_SAFE_INTEGER` (2^53), producing incorrect lock keys and potential lock collisions.

## 🟡 Minor Issues / Code Quality

- [ ] **`packages/db/src/repositories/tenants.ts` — `suspend()` doesn't verify row was affected**
  The `suspend` method (line 194) wraps the UPDATE in `withTransaction` but never checks `rowCount`. If the tenant ID doesn't exist, the operation silently succeeds, returning `Result.ok(undefined)`.

- [ ] **`packages/db/src/pool.ts` (lines 97, 102, 115–117) — Non-null assertions on DEFAULT_CONFIG**
  Multiple lines use `DEFAULT_CONFIG.host!`, `DEFAULT_CONFIG.port!` etc. While the values are defined, the non-null assertions suppress TypeScript's protection against future regressions if defaults are changed to `undefined`.

- [ ] **`packages/lib/src/validation/index.ts` — `InMemoryRateLimiter` timer never destroyed in `createEmailValidator`**
  `createEmailValidator()` returns an `EmailValidator` but doesn't expose a way to call `destroy()`. The internal `setInterval` keeps the process alive and leaks memory in tests or short-lived processes.

- [ ] **`apps/billing/src/services/plans.ts` (line 247) — PAYG rounding may overcharge**
  `Math.floor((emailCostMillicents + 500) / 1000)` rounds up by adding 500 millicents before floor division. This always rounds up to the nearest cent, potentially overcharging by up to 0.5 millicents per calculation.

- [ ] **`packages/db/src/repositories/messages.ts` (lines 1001+) — `getStats` has dual parameter names**
  The `getStats` method accepts both `since`/`until` and `startDate`/`endDate` with fallback logic (`options.startDate ?? options.since`). This dual API surface is confusing and should be deprecated in favor of one naming convention.

- [ ] **`apps/billing/src/services/stripe-integration.ts` — `getOrCreateCustomer` race condition complexity**
  The race condition handling (SELECT → create Stripe customer → INSERT with ON CONFLICT → delete duplicate) is complex and failure-prone. If the duplicate Stripe customer deletion fails, it logs as "CRITICAL" but still returns success to the caller.

- [ ] **`packages/lib/src/http/index.ts` (line 275) — Full URL logged on failure**
  The catch block on line 275 logs `url: fullUrl` which may include sensitive query parameters (API keys, tokens). The `safeLogUrl` sanitization is only used for successful requests.

- [ ] **`apps/billing/src/config.ts` (lines 189–190) — Fake phone number fallback in production**
  `billingCompanyPhone` falls back to `'+37200000000'`. While the IBAN is validated in production, the phone number is not, so production invoices could display a fake phone number.

## 🔵 Cosmetic / Documentation

- [ ] **`packages/db/src/repositories/api-keys.ts` — Duplicate row type definitions**
  The `ApiKeyRow` type shape is repeated 6+ times inline (create, verify, findById, update, rotate, listByTenant, listByUser). Should be extracted into a shared type alias for maintainability.

- [ ] **`packages/db/src/repositories/messages.ts` — `MESSAGE_COLUMNS` and `MESSAGE_COLUMNS_NO_BODY` string constants**
  These are long, fragile strings that must be kept in sync with the `MessageRow` type and `mapRow()` function. A mismatch would silently drop or misinterpret columns.

- [ ] **`apps/billing/src/routes/billing.ts` (lines 379, 394, 409) — Compressed error handling formatting**
  Several catch blocks have the `logger.error` and `return` on the same line, reducing readability.

- [ ] **`services/mail-server/src/` — Empty directory**
  The mail-server source directory is empty. If this is intentional (Rust code elsewhere), a README should explain. If not, it's a missing implementation.
